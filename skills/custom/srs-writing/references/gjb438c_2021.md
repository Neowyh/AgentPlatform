本文档为 srs-writing 技能的标准参考，涵盖章节结构、需求表述规范、需求分类、验证方法与追踪矩阵要求。

## 需求章节编号与 ID 对齐规则

- 功能项编号采用任务书章节号：任务书 `5.2.1` → 功能项 `F-5.2.1`，对应的 SRS 需求章节按其进入正文的位置映射为 `3.x` 系列。
- 需求 ID `F-<功能章节号>-<序号>`，如任务书 5.2.1 节第 3 条需求 → `F-5.2.1-3`。
- ID 一经分配永不改号：修改不换 ID，拒绝不回收；缺口/派生项保留标注位。
- 需求在 SRS 第 3 章中的章节号 = 按最终排版自动分配的 `3.x.y`，并在追踪矩阵中标注（需求项侧显示 SRS 章节号 + ID）。

## 需求类型与第 3 章分类组织

第 3 章按类型分小节组织（每条需求带 type 字段）：

- 功能需求（核心）：任务书功能项转化为可操作的行为需求。
- 性能需求：任务书中以明确指标/约束出现的条款（吞吐、时延、容量、精度等）。
- 接口需求：外部/内部接口、协议、数据交换（任务书明确出现时）。
- 数据需求：数据项、数据格式、存储（任务书明确出现时）。
- 安全保密需求：任务书以安全/保密条款形式出现时。
- 其他/派生：不属于以上、或由分析派生而来。

**广度约束**：功能需求为主线，不主动发散任务书未提及的需求类型；但每个功能项须做一次覆盖度检查，把「任务书提到但未转化为需求」的条款列为提示项。

## 需求表述规范（修改/重写时执行）

每条采纳/修改的需求应满足：

1. **主语明确**：谁来执行（系统/软件/用户/操作员）。
2. **行为可操作**：描述可观测、可执行的系统行为，避免空泛形容词。
3. **约束可量化**：性能、容量、时延等要有数值或明确边界。
4. **可验证**：能通过某种方法证明已满足（对应验证方法字段）。
5. 避免歧义词：尽量不用“及时、适当、高效、尽量”等无量化约束。

## 验证方法（合格性规定字段）

每条需求标注一种验证方法（用于第 4 章合格性规定汇总）：

- **检查**（Inspection）：审查文档/代码/配置。
- **分析**（Analysis）：建模、仿真、计算推导。
- **演示**（Demonstration）：运行可观测操作。
- **试验**（Test）：按测试用例执行并记录结果。

## 追踪矩阵要求

- 两级追踪：任务书功能项 ↔ 已采纳需求；不含测试/设计层级。
- 正向矩阵（功能→需求）：每行一个功能项，列：功能项编号、功能项名称、任务书章节号、覆盖需求 ID 列表（含 SRS 章节号）。
- 逆向矩阵（需求→功能项）：每行一条需求，列：需求 ID、需求名称、SRS 章节号、来源功能项编号、来源任务书章节号。
- 异常标注
  - 需求缺口：任务书中功能项在已采纳需求中无覆盖 → 单独列「需求缺口清单」。
  - 派生需求：无来源功能项的需求 → 标记「派生/未分配」，给出派生依据。
- 多对多：需求可挂多个功能项（逆向矩阵每行保留一个主来源，附加来源以 `+` 列或备注说明），并按实际挂接生成矩阵。
- 被拒绝的需求不在矩阵中出现，仅在需求目录（requirement-catalog.md）记录拒绝原因。
