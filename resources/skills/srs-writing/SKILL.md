# SRS 需求规格说明生成工作流

## 工作目标

解析用户上传的软件任务书，识别功能项并逐项完成需求分析，经用户逐条采纳/修改/拒绝后，按 GJB438C-2021 生成《软件需求规格说明书》（.docx）和《需求追踪矩阵》（.docx）。需求内容必须经用户逐项确认后才能进入最终文档。

## 输入资料读取规则

1. 首先枚举 `/mnt/user-data/uploads/`，定位任务书文件。
2. 任务书格式与读取方式：
   - `.doc` / `.docx` / `.pdf`：调用 `read_document` 工具转 Markdown 后读取（分段读取，遇截断标记用 `page_range` 或分段继续）。
   - `.md` / `.txt`：直接用 `read_file` 读取。
3. 文档读取后检测空文本：PDF 转换结果被判定为扫描件（空白或无正文）时，回复 `FAILED: 任务书无法解析，疑似扫描件，请提供电子版任务书` 并停止，不得猜测内容。
4. 长文档按章节分段读取，不一次性吞入无关内容；记录每个功能项在任务书中的章节位置和原文位置（用于追踪矩阵）。
5. 缺少关键输入时调用 `ask_clarification`，不得用假设替代资料。

## 固定执行阶段（按序流转）

### 1. task_book_parsing 解析
- 读取任务书，识别全部功能项，建立「功能项清单」：功能项编号、名称、任务书章节、原文摘要。
- 功能项编号规范化：沿用任务书章节号（如 `5.2.1` → 功能项编号 `F-5.2.1`）；任务书编号缺失/不规范时，按章节顺序在解析阶段规范化重排。
- 解析完成后**先把「任务书章节 ↔ 功能项」映射表展示给用户确认一次**（复用或改编号），确认后才进入需求分析。

### 2. requirement_analysis 需求分析
- 逐个功能项完成需求分析，生成候选需求（每条含：ID、描述、类型、优先级、验证方法、来源功能项、来源任务书章节）。
- 覆盖广度：功能需求为主线；任务书中以性能/接口/数据/安全条款形式**明确出现**的内容同样生成需求项（标注类型）；不主动发散任务书未提及的需求类型。
- 每个功能项完成后检查任务书覆盖度，把「任务书提及但尚未转化为需求」的条款列为提示项（防遗漏不自动补）。
- 需求 ID 规则：`F-<功能章节号>-<序号>`（如 `F-5.2.1-3`），同功能项下序号递增；**ID 一经分配永不改号**（修改不改 ID，拒绝不回收）。
- 候选需求一次性写入阶段产物，随后进入确认阶段。

### 3. interactive_confirmation 逐项确认（核心）
- **展示粒度**：每次展示一个功能项的候选需求（表格：ID / 描述 / 类型 / 优先级 / 验证方法 / 来源），附进度「已确认 x/N 个功能项」。
- 用户可对该功能项内任意一条进行：采纳 / 修改 / 拒绝；
  - **采纳**：锁定，写入已确认集。
  - **修改**：用户可直接给新文本，也可给修改意见；按要求重写（GJB438C 表述规范：主语＋行为＋约束＋可验证），**展示终稿一次**不再循环确认，用户可继续微调。
  - **拒绝**：可选附原因，记录到需求目录，不进入追踪矩阵与正文。
- 支持批量操作（如「全部采纳」），批量操作执行前先确认一次。
- 一个功能项全部处理完（无待决条目）后才进入下一功能项；用户说「下一个」推进。
- **每个决策后立即更新 progress.json**（见恢复规则），保证任意时刻中断可恢复。

### 4. matrix_generation 追踪矩阵
- 两级追踪（功能 ↔ 已采纳需求），不涉及测试/设计层级。
- 正向矩阵：功能项 → 覆盖它的需求 ID 列表；逆向矩阵：需求 → 来源功能项 + 来源任务书章节。
- **正逆向矩阵均标注功能项的任务书章节号和需求项的 SRS 章节号**。
- 支持一对多与多对多映射；映射关系由自动解析方案 + 用户可在确认表格中调整，采纳即映射生效。
- 显式标注异常：
  - 无需求覆盖的功能项 →「需求缺口」；
  - 无来源功能项的需求 →「派生需求/未分配」。
- 表格的文档章节号规则（见 references/gjb438c_2021.md）。

### 5. document_generation 文档生成
- 生成前先探测工具：`command -v officecli`（同时覆盖沙箱挂载与本地安装两种形态，不依赖固定绝对路径；`OFFICECLI_SKIP_UPDATE=1`）。探测失败即按「失败契约」处理：以 `FAILED:` 一句话说明 officecli 缺失，回退提示用 `requirement-catalog.md` 人工整编，不写占位或空文件。
- 探测通过后，产物生成一律用 `officecli`，产出 `.docx`。
- 默认模式：用 officecli 从零搭建 GJB438C-2021 标准结构（封面 + 1 引言 / 2 引用文件 / 3 需求 / 4 合格性规定 / 5 需求可追踪性 / 6 注释）。
  - 封面：从任务书提取项目名称、文档编号；单位、密级留空待填。
  - 1 引言 / 2 引用文件：生成草稿（目的、范围、术语、参考标准），引言供用户确认阶段顺带修订，引用文件只放固定标准项 + 留两行人工追加位。
  - 3 需求：按确认后的需求按类型组织分类（功能/性能/接口/数据/其他），章节号对齐 ID 规则。
  - 4 合格性规定：从每条需求验证方法字段汇总成表。
  - 5 需求可追踪性：嵌入追踪矩阵（与矩阵文档同一内容）。
  - 6 注释：缩写词表（从任务书抽取），可人工追加。
- 模板模式：若 `/mnt/skills/srs-writing/templates/` 存在 `*.docx` 模板（单位模板），改为「打开模板 → 在占位符标记处插入生成内容」流程（见 templates/README.md 占位符约定）；模板模式的生成同样先过上方探测，成稿后同样走下方视觉自检。
- 视觉自检（强制）：两份 docx 全部生成后、调用 `present_files` 交付前执行，由智能体自己发现并修复表格断裂、样式问题：
  1. 布局诊断：对 `srs_document.docx` 与 `traceability-matrix.docx` 分别执行 `officecli view <docx> issues --json`，逐条检查表格断裂、样式与结构问题；
  2. 渲染抽查：对两份 docx 分别执行 `officecli view <docx> html -o /mnt/user-data/workspace/<文件名>.html`（渲染产物写工作区，不进交付子目录），读取 HTML 核对表格完整性与章节样式；
  3. 发现问题即用 officecli 修复，修复后重跑布局诊断与渲染抽查复查；复查不通过不得交付（与 review 阶段「校验未通过不得交付」同一门槛），不得调用 `present_files`。

### 6. review 审阅
- 输出前自检：需求无遗漏（缺口清单检查）、追踪无断裂（矩阵一致性）、ID 无重复。
- 自行运行随 skill 包分发的离线校验器：`python /mnt/skills/srs-writing/scripts/validate_srs_outputs.py --outputs-dir /mnt/user-data/outputs/srs-<当前任务书子目录>`，并向用户逐条解读校验结果（通过项与问题项），不要让用户运行该脚本。校验未通过（存在 error）时不得交付最终文档，须修复后重跑校验直至通过；warning 项仅向用户提示、不阻塞交付。全库巡检（父目录 `/mnt/user-data/outputs`）仅在确需检查全部任务时使用，解读时按子目录分段归属各任务。

## 输出文件（写入 `/mnt/user-data/outputs/srs-<任务书>/`）

每份任务书使用独立子目录 `srs-<任务书文件名规范化>/`，并行处理多份任务书时各写各的子目录、互不覆盖。子目录命名规则：取任务书主文件名（不含扩展名）转小写，仅保留 ASCII 的 `a-z 0-9 _ . -`，其余字符（含空格与中文等全部非 ASCII 字符）替换为 `-`，连续 `-` 合并，去除首尾 `-`，整名截断到 48 字符（截断产生的尾随 `-` 一并去除）；规范化结果为空（如纯中文任务书名）时，用 `srs-<原文件名（含扩展名）sha256 前 8 位十六进制>` 兜底，保证不同任务书仍互不覆盖。子目录内文件：

1. `srs_document.docx` — 需求规格说明书（GJB438C-2021 结构）
2. `traceability-matrix.docx` — 功能/需求双向追踪矩阵（正向+逆向两张表）
3. `requirement-catalog.md` — 需求条目明细表（含拒绝项及原因）
4. `progress.json` — 进度文件（对话中断恢复用，见下）

写完后调用 `present_files` 展示产物路径。

## 进度与恢复规则

- `progress.json` 每轮用户决策后**立即更新**（阶段、当前功能项序号/数量、每条需求 ID/状态/内容、映射表、章节映射表），写入该任务书自己的 `srs-*` 子目录。`stage` 字段取值依次为 `task_book_parsing`、`requirement_analysis`、`interactive_confirmation`、`matrix_generation`、`document_generation`、`review`，全部交付完成后写 `complete`。
- 同一对话线程中：检测到任一 `srs-*/progress.json` 存在且阶段未完成 → 列出各未完成任务书名，主动询问「检测到未完成任务书，继续哪一份」；被选中的那份优先恢复，其余任务书目录保持原样不动。
- 恢复仅限同一对话线程 + 同一任务书：只读取并续写该任务书 `srs-*` 子目录内的进度，不得把一份任务的进度写入另一份的子目录。
- 阶段未完成时**不**产出最终文档；未确认的需求不得进入最终文档。
- 新对话线程（uploads 目录不同）或新任务书不自动恢复，提示从头开始。

## 失败契约

- 解析失败 / 阶段无法完成 / 输出缺失时，一句话以 `FAILED:` 开头说明原因，并写明缺失项，严禁写入占位或空文件。
- 生成前 `command -v officecli` 探测失败或输出 docx 生成失败（officecli 不可用）时，回退提示用户可先用已生成的 `requirement-catalog.md` 人工整编，并注明 officecli 缺失。
