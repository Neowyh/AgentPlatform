# 文档审查：过度设计与冗余分析

## 审查结论

当前文档存在 **5 处过度设计** 和 **3 处冗余**，建议精简以降低系统复杂度。

---

## 一、过度设计（建议删除或简化）

### 1. user_notifications 表和通知 API — 过度设计

**问题：** 新增 `user_notifications` 表 + 3 个通知 API + 1 个前端页面，但当前系统没有任何通知基础设施（无 WebSocket、无消息队列、无邮件服务）。

**影响：**
- 需要新增消息推送机制（轮询/WebSocket/SSE）
- 需要新增通知中心前端页面
- 增加了系统复杂度，但核心功能（资源管理、visibility 审批）不依赖通知

**建议：** 删除通知相关设计。审批结果通过 API 状态查询即可获取，不需要独立的通知系统。如后续确实需要，可在 Phase 2 再加。

### 2. user_favorites 表和收藏 API — 过度设计

**问题：** 新增 `user_favorites` 表 + 4 个收藏 API + 1 个前端页面。但收藏/置顶只是列表排序的快捷方式，不是核心功能。

**影响：**
- 增加了一张新表和 4 个 API
- 前端需要新增收藏列表页面
- 对核心的资源管理和 visibility 审批没有帮助

**建议：** 删除收藏相关设计。列表页的搜索和筛选已经足够。如后续用户反馈需要，可在 Phase 2 再加。

### 3. audit_log 表和审计日志 API — 过度设计

**问题：** 新增 `audit_log` 表 + 2 个审计日志 API + 1 个前端页面 + 保留 3 年的清理策略。但当前系统没有审计需求，且 3 年保留期意味着数据量会持续增长。

**影响：**
- 需要新增 cron job 定期清理 3 年前的日志
- 审计日志的 action 枚举值定义了 15+ 种操作类型，增加了维护成本
- super_admin 专用的审计日志查看页面使用频率极低

**建议：** 删除审计日志相关设计。核心的 visibility 变更记录已在 `visibility_applications` 表中保留。如后续合规要求需要审计，可在 Phase 2 再加。

### 4. 软删除机制 — 过度设计

**问题：** 引入 `is_deleted`/`deleted_at` 字段 + 3 个软删除 API（查看已删除、恢复、彻底删除）+ cron job 自动清理。

**影响：**
- `resource_metadata` 表需要额外的 `is_deleted`/`deleted_at` 字段
- 需要额外的 API 端点处理软删除逻辑
- 需要 cron job 定期清理超过 30 天的已删除资源
- 增加了查询复杂度（所有查询都需要过滤 `is_deleted=FALSE`）

**建议：** 简化为硬删除。删除操作直接删除数据，不提供恢复功能。如确实需要恢复，通过数据库备份即可。

### 5. 审批行锁（SELECT ... FOR UPDATE）— 过度设计

**问题：** 审批接口使用 `SELECT ... FOR UPDATE` 行锁确保并发安全，但：
- 审批是低频操作（不会有两个 admin 同时审批同一个申请）
- 当前系统是 SQLite（不支持 `SELECT ... FOR UPDATE`）
- 即使未来迁移到 PostgreSQL，用乐观锁（version 字段）也足够

**影响：**
- 引入了数据库级别的锁机制，增加了死锁风险
- SQLite 不支持行锁，需要额外处理兼容性

**建议：** 删除行锁设计，仅使用乐观锁（version 字段）。审批时校验 version 一致即可。

## 二、冗余（建议删除或合并）

### 1. Tool 列表和详情接口重复定义

**问题：** 通用接口表中已定义了 `GET /api/{resource}` 和 `GET /api/{resource}/{id}`，Tool 专属接口表中又重复定义了 `GET /api/tools` 和 `GET /api/tools/{name}`。

**建议：** 删除 Tool 专属接口表中的列表和详情行，统一使用通用接口。

### 2. Skill/Workflow/Agent 的导入导出接口重复定义

**问题：** 通用接口表中已定义了导出和导入接口，Skill/Workflow/Agent 专属接口表中又重复定义了导出和导入行。

**建议：** 删除专属接口表中的导出和导入行，统一使用通用接口。

### 3. Tool 的 MCP 配置导出说明冗余

**问题：** Tool 的导入/导出格式表和数据存储形式表都提到了"MCP 配置可导出 JSON"，但 Tool 本身不支持导入导出。

**建议：** 仅在导入/导出格式表中保留 MCP 配置说明，删除数据存储形式表中的重复说明。

---

## 三、建议保留的部分

以下部分是必要且精确的，建议保留：

1. **resource_metadata 表** — 统一存储四种资源的元数据，替代分散的 `.meta.json` 文件，是核心设计
2. **visibility_applications 表** — 替代现有的 `skill_applications`，支持所有资源类型的审批，是核心设计
3. **通用 API 接口** — 统一的 CRUD + 导入导出接口，减少了代码重复
4. **乐观锁（version 字段）** — 简单有效的并发控制方案
5. **前端页面改造清单** — 明确了每个页面需要做什么
6. **迁移方案** — 分阶段迁移，有回滚方案
