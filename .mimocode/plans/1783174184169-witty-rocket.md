# 权限模型重构 — 遗留问题修复方案

## 背景

权限模型重构文档（主文档、API规范、数据库设计、迁移方案）已定义完整的新权限体系。数据库表（resource_metadata、visibility_applications）已创建，迁移脚本已实现，核心权限函数已统一。但仍有以下遗留问题需要修复。

---

## 问题清单与修复方案

### 问题 1：Workflow API 未迁移到 resource_metadata

**现状：** `workflows.py` 的 CRUD 直接操作 `workflow_runs` 表中的 sentinel 行（`run_id = "def:{name}"`），没有 owner、visibility、version 字段，没有权限过滤。

**修复方案：**

#### 1.1 后端 `backend/app/gateway/routers/workflows.py`

**创建 workflow（POST /api/workflows）：**
- 移除 `@require_role(DEPARTMENT_ADMIN, SUPER_ADMIN)` 限制，改为所有可写角色（user/dept_admin/super_admin）可创建
- 创建成功后，同步往 `resource_metadata` 插入一条记录（resource_type="workflow"，visibility="private"，owner_id=current_user.id）

**查询 workflow 列表（GET /api/workflows）：**
- 从 `resource_metadata` 表 JOIN 查询，获取每条 workflow 的 visibility 和 owner_id
- 调用 `check_resource_access()` 按用户角色过滤

**查询 workflow 详情（GET /api/workflows/{name}）：**
- 从 `resource_metadata` 表查询 visibility 和 owner_id
- 调用 `check_resource_access()` 检查权限

**编辑 workflow（PUT /api/workflows/{name}）：**
- 从 `resource_metadata` 表查询 owner_id
- 调用 `check_resource_modify()` 仅允许 owner 编辑
- 编辑时同步更新 resource_metadata.version（+1）

**删除 workflow（DELETE /api/workflows/{name}）：**
- 从 `resource_metadata` 表查询 owner_id
- 调用 `check_resource_modify()` 仅允许 owner 删除
- 删除时同步设置 resource_metadata.deleted_at（soft delete）

#### 1.2 前端 `frontend/src/core/workflows/types.ts`

在 `WorkflowSummary` 接口中增加：
```typescript
visibility: string;
owner_id: string | null;
department_id: string | null;
```

#### 1.3 前端 workflow 详情页

在 `frontend/src/app/workspace/workflows/[workflow_name]/page.tsx` 增加：
- visibility 标签显示
- 导出按钮
- "申请变更 visibility" 按钮（调用 `/api/visibility-applications`）

#### 1.4 前端 workflow 编辑页

在 `frontend/src/app/workspace/workflows/[workflow_name]/edit/page.tsx` 增加：
- owner 校验（非 owner 隐藏编辑按钮或跳转）

### 问题 2：Tool API 未按 visibility 过滤

**现状：** `tools.py` 的 `list_tools` 直接返回 registry 中的所有工具，不查 `resource_metadata` 表，不过滤 visibility。

**修复方案：**

#### 2.1 后端 `backend/app/gateway/routers/tools.py`

**列表接口（GET /api/tools）：**
- 查询 `resource_metadata` 表获取所有 resource_type="tool" 的记录
- 对每个 tool，调用 `check_resource_access()` 按用户角色过滤
- 如果 resource_metadata 中没有某个 tool 的记录（新注册的 tool），默认 visibility=public

**测试接口（POST /api/tools/{tool_name}/test）：**
- 增加 visibility 检查：只有对当前用户可见的 tool 才能测试

**配置更新接口（PUT /api/tools/{tool_name}/config）：**
- 从 `resource_metadata` 表查询 owner_id
- 调用 `check_resource_modify()` 仅允许 owner 修改配置

### 问题 6：创建资源时同步插入 resource_metadata

**现状：** 创建 workflow 时没有同步插入 resource_metadata 记录。

**修复方案：**

在以下创建操作后增加 resource_metadata 插入：

#### 6.1 `backend/app/gateway/routers/workflows.py` — create_workflow
```python
resource = ResourceMetadata(
    id=str(uuid.uuid4()),
    resource_type="workflow",
    resource_id=name,
    owner_id=str(current_user.id),
    department_id=current_user.department_id,
    visibility="private",
    version=1,
)
session.add(resource)
```

#### 6.2 已确认的部分
- Agent 创建：`agents.py` 的 `_save_agent_meta()` 已在创建时插入 resource_metadata ✅
- Skill 安装：`skills.py` 的 `_save_skill_meta()` 已在安装时插入 resource_metadata ✅
- Tool：第一期不新增创建端点，仅在迁移时通过脚本补充

## 实施顺序

1. **后端 workflow 迁移**（核心）— workflows.py 增加 resource_metadata 集成
2. **后端 tool visibility**（核心）— tools.py 增加 visibility 过滤
3. **后端 admin stats**（小改）— admin.py 从 resource_metadata 统计
4. **前端清理**（小改）— 删除废弃页面，更新导航
5. **前端 workflow 支持**（中等）— 类型定义、详情页、编辑页
6. **验证 agent/skill 创建时同步插入**（验证）
