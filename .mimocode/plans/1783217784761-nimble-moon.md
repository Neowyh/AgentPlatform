# 权限模型重构 — 遗留问题修复计划

## 问题清单与修复方案

---

### 问题 1：资源编辑缺少乐观锁（严重度：高）

**是什么：** 文档要求编辑资源时必须带上一个"版本号"（version）。比如你打开一个 skill 文件，此时 version=3。你改完保存时，必须告诉服务器"我是基于 version=3 改的"。服务器会检查："现在实际 version 是不是 3？"如果是，才允许保存，然后把 version 改成 4。如果不是，说明在你改的同时别人也改了，服务器会拒绝你的保存，返回"版本冲突，请刷新重试"。

**现在的问题：** Skill、Agent、Workflow 的编辑接口完全没做这个检查。两个人可以同时改同一个资源，后保存的人会无声无息地覆盖前一个人的修改，造成数据丢失。

**修复方案：**

- 在 skill/agent/workflow 的编辑请求体中增加 `version` 字段（必填）
- 编辑时先查 resource_metadata 表的当前 version
- 如果请求中的 version ≠ 数据库中的 version，返回 409 错误："版本冲突，请刷新后重试"
- 如果一致，正常保存，同时将 version + 1

**涉及文件：**
- `backend/app/gateway/routers/skills.py` — `update_custom_skill` 端点
- `backend/app/gateway/routers/agents.py` — agent 编辑端点
- `backend/app/gateway/routers/workflows.py` — workflow 编辑端点
- 前端对应的编辑表单，需在提交时携带 version

### 问题 2：错误码没有按规范返回（严重度：中）

**是什么：** 文档定义了 12 个标准错误码，比如 `PERMISSION_DENIED`（没权限）、`VERSION_CONFLICT`（版本冲突）、`RESOURCE_NOT_FOUND`（资源不存在）等。规范要求返回格式为：
```json
{
  "success": false,
  "error": { "code": "PERMISSION_DENIED", "message": "无权限执行该操作" }
}
```

**现在的问题：** 代码里全部是直接写 HTTP 状态码 + 随意的 detail 字符串，比如 `raise HTTPException(status_code=403, detail="You do not have permission to modify this resource")`。前端无法通过统一的错误码来判断错误类型，只能靠猜字符串。

**修复方案：**

- 在 `backend/app/gateway/` 下创建一个 `error_codes.py` 定义所有错误码常量和对应的 HTTP 状态码
- 创建一个统一的 `ApiException(HTTPException)` 类，携带 `code` 字段
- 在全局异常处理器中捕获 `ApiException`，按 `{success, data, error: {code, message}}` 格式返回
- 逐步替换各端点中的 `HTTPException` 为 `ApiException`

**涉及文件：**
- 新建 `backend/app/gateway/error_codes.py`
- `backend/app/gateway/app.py` 或 main app — 添加全局异常处理
- 所有路由文件中的异常抛出点

### 问题 3：用户删除时没有做资源重分配（严重度：中）

**是什么：** 文档规定：超级管理员要删除一个用户之前，必须先把这个用户名下的资源（skill、agent、workflow 等）转移给别人。可以转移给超级管理员自己，也可以指定给其他用户。转移完才能删除用户。

**现在的问题：** 管理员直接删除用户，用户创建的资源就变成了"孤儿"——owner 指向一个已经不存在的人。这些资源没人能编辑，也没人能管理。

**修复方案：**

- 在用户管理的删除接口中，先查询该用户是否拥有资源（查 resource_metadata 表）
- 如果有资源，要求请求中携带 `transfer_to` 参数（目标用户 ID），或者设置为管理员自己
- 检查目标用户是否存在
- 批量更新 resource_metadata 中该用户所有资源的 owner_id
- 更新 department_id（如果目标用户属于不同部门）
- 完成后才执行用户删除

**涉及文件：**
- `backend/app/gateway/routers/admin.py` — 用户删除接口
- 新建 `backend/app/gateway/routers/admin_user_lifecycle.py`（或放在 admin.py 中）

### 问题 4：用户调岗时没有降级部门级资源（严重度：中）

**是什么：** 文档规定：用户从 A 部门调到 B 部门时，这个用户名下所有 `department` 级别的资源（只有同部门才能看到的）要自动降级为 `private`（只有自己能看到）。因为调到新部门后，原来部门的人不应该再看到这些资源了。

**现在的问题：** 用户调岗后，他原来的部门级资源仍然对原部门所有人可见，这不符合权限设计。

**修复方案：**

- 在管理员修改用户部门的接口中，检测部门是否发生变化
- 如果变化了，查询 resource_metadata 中该用户所有 `visibility = 'department'` 的资源
- 将这些资源的 visibility 更新为 `private`
- （通知功能在第二期，目前先记录日志）

**涉及文件：**
- `backend/app/gateway/routers/admin.py` — 用户部门修改接口

---

### 问题 5：部门删除前没有处理资源（严重度：中）

**是什么：** 文档规定：删除一个部门之前，必须先处理该部门下所有部门级资源。具体规则：
- `public` 级资源：不动，保持 public
- `private` 级资源：不动，保持 private
- `department` 级资源：全部降级为 `private`（因为部门没了，"同部门可见"就没意义了）

**现在的问题：** 直接删除部门后，这些 department 级资源的 department_id 指向一个不存在的部门，权限判断会出问题。

**修复方案：**

- 在管理员删除部门的接口中，先查询该部门下的资源
- 将所有 `visibility = 'department'` 且 `department_id = 该部门` 的资源降级为 `private`
- 清空这些资源的 department_id（设为 NULL）
- 完成后才执行部门删除

**涉及文件：**
- `backend/app/gateway/routers/admin.py` — 部门删除接口

---

### 问题 6：管理员人数上限没有校验（严重度：中）

**是什么：** 文档规定：超级管理员全局不能超过 2 人，每个部门的部门管理员不能超过 3 人。把一个普通用户提升为管理员之前，要先检查人数有没有超限。

**现在的问题：** 管理员可以把任意数量的用户设为 super_admin 或 dept_admin，没有人数限制。

**修复方案：**

- 在用户角色变更接口中，修改前先统计当前各角色人数
- 如果要把用户设为 super_admin：统计当前 super_admin 人数，≥ 2 则拒绝，返回 `ADMIN_LIMIT_EXCEEDED`
- 如果要把用户设为 dept_admin：统计该部门当前 dept_admin 人数，≥ 3 则拒绝
- 如果是从 admin 降级为普通用户，不受限制

**涉及文件：**
- `backend/app/gateway/routers/admin.py` — 用户角色变更接口

### 问题 7：资源删除时没有自动驳回 pending 申请（严重度：低）

**是什么：** 文档规定：如果一个资源正在等待 visibility 变更审批（status=pending），此时资源被删除了，这个 pending 申请应该自动变成 rejected 状态。

**现在的问题：** 资源删除后，对应的 pending 申请仍然留在数据库里，状态还是 pending。审批人看到一个已经不存在的资源的申请，会很困惑。

**修复方案：**

- 在资源删除的端点中（skill/agent/workflow），删除前查询 visibility_applications 中该资源是否有 pending 申请
- 如果有，将 status 更新为 rejected，review_comment 写"资源已删除，申请自动关闭"
- （通知功能第二期实现）

**涉及文件：**
- `backend/app/gateway/routers/workflows.py` — delete_workflow
- `backend/app/gateway/routers/skills.py` — delete_custom_skill
- `backend/app/gateway/routers/agents.py` — delete_agent

---

### 问题 8：用户禁用/删除时没有处理 pending 申请（严重度：低）

**是什么：** 文档规定：用户被禁用或删除时，如果这个用户有待审批的申请：
- 作为申请人：申请自动驳回
- 作为审批人：申请自动重新分配给同部门其他管理员或超级管理员

**现在的问题：** 用户被禁用后，他提交的申请还是 pending 状态，没人处理也没人驳回。

**修复方案：**

- 在用户禁用/删除接口中，查询 visibility_applications 中该用户相关的 pending 申请
- 作为申请人的：status → rejected
- 作为审批人的：重新分配给同部门其他 dept_admin 或 super_admin（如果有的话），没有则自动驳回

**涉及文件：**
- `backend/app/gateway/routers/admin.py` — 用户禁用/删除接口

---

### 问题 9：导入流程中仍有安全扫描逻辑（严重度：低）

**是什么：** 文档规定第一期不做安全扫描，第二期才做。所以导入相关的安全扫描代码应该移除。

**现在的问题：** Skill 编辑接口中仍然调用了 `scan_skill_content` 进行安全扫描。虽然错误码 `SECURITY_SCAN_FAILED` 已经移除了，但扫描逻辑本身还在运行。

**修复方案：**

- 检查 `scan_skill_content` 调用是否影响编辑功能（目前是阻断式的，扫描不通过就拒绝编辑）
- 如果第一期确实不需要安全扫描，注释掉或移除扫描调用
- 保留函数签名和接口，方便第二期重新接入

**涉及文件：**
- `backend/app/gateway/routers/skills.py:350`

---

### 问题 10：部分资源详情响应中缺少 version 字段（严重度：低）

**是什么：** 编辑资源时前端需要知道当前版本号是多少，才能在保存时带上正确的 version（配合问题 1 的乐观锁）。所以资源详情接口的响应必须包含 version。

**现在的问题：** `_load_skill_meta` 和 `_load_agent_meta` 返回的字典中没有 version 字段，只有 `_load_workflow_meta` 有。

**修复方案：**

- 在 `_load_skill_meta` 和 `_load_agent_meta` 返回的字典中加上 `version` 字段
- 在资源详情 API 的响应 schema 中加入 version 字段

**涉及文件：**
- `backend/app/gateway/routers/skills.py` — `_load_skill_meta`
- `backend/app/gateway/routers/agents.py` — `_load_agent_meta`

## 修复优先级建议

| 优先级 | 问题 | 理由 |
|---|---|---|
| P0（必须修） | 问题 1（乐观锁） | 核心并发安全机制，不修会导致数据覆盖丢失 |
| P1（应该修） | 问题 3、4、5（生命周期） | 用户/部门删除不处理资源会造成孤儿数据 |
| P1（应该修） | 问题 6（管理员人数限制） | 安全约束，不校验可能导致权限滥用 |
| P2（可以修） | 问题 2（错误码） | 影响前端错误处理体验 |
| P2（可以修） | 问题 7、8（pending 申请清理） | 数据一致性问题 |
| P3（建议修） | 问题 9、10（扫描 + version 响应） | 小问题，顺手修 |

## 验证方式

每个问题修复后，通过对应的 API 测试验证：
1. 乐观锁：同时发送两个编辑请求，验证第二个返回 409
2. 错误码：验证所有错误响应包含 `code` 字段
3. 用户删除：创建用户 → 创建资源 → 删除用户 → 验证资源已转移
4. 调岗降级：调岗后验证 department 级资源变为 private
5. 部门删除：删除部门前验证 department 级资源降级
6. 管理员限制：添加第 3 个 super_admin 时验证返回错误
7. pending 清理：删除资源后验证 pending 申请状态变为 rejected
