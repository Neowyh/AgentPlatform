# DeerFlow 禁公网内网离线部署作业指导书

## 1. 这份文档给谁看

这份文档面向不熟悉 Docker 和 Linux 的部署人员。你可以把它当成“照着敲命令”的操作手册。

本文会把每一步拆成：

- 要做什么
- 输入什么命令
- 正常会看到什么
- 这一步的原理
- 常见错误怎么处理

## 2. 部署整体流程

整个离线部署分两台机器：

| 机器 | 是否能访问公网 | 做什么 |
| --- | --- | --- |
| 构建机 | 可以访问公网或企业依赖源 | 打包 Docker 镜像和源码 |
| 内网服务器 | 不能访问公网 | 导入镜像并启动 DeerFlow |

流程图：

```text
构建机打包
  -> 得到 dist/intranet/deer-flow-<version>/
  -> 拷贝整个目录到内网服务器
  -> 内网服务器执行 prepare
  -> 填写模型配置
  -> 启动服务
  -> 浏览器访问
```

原理说明：

- 内网服务器不能联网，所以不能现场拉取镜像和依赖。
- 构建机先把需要的镜像打成 `tar` 文件。
- 内网服务器用 `docker load` 导入镜像，不需要访问公网。

## 3. 路径约定

本文示例部署目录是：

```text
/home/<user>/deer-flow
```

其中 `<user>` 是内网服务器上的实际用户名，例如 `zhangsan`、`admin` 或你的登录账号。后文所有命令里的 `<user>` 都要替换成真实用户名。

这不是强制目录。也可以换成其他部署目录，例如：

```text
/data/apps/deer-flow
/srv/deer-flow
```

后文命令都以 `/home/<user>/deer-flow` 为例。如果你换了目录，要把命令里的路径一起替换。

推荐做法：

```bash
mkdir -p /home/<user>/deer-flow
cd /home/<user>/deer-flow
```

原理说明：

- `mkdir -p` 表示目录不存在就创建，存在也不报错。
- `cd` 表示进入这个目录。
- 后续脚本会在当前目录下生成 `source/`、`runtime/` 和 `env.intranet`。
- 离线包里的 `deploy-intranet.sh` 默认会把“脚本所在目录”当成部署根目录，也就是 bundle root。
- 换句话说，如果 `deploy-intranet.sh` 放在 `/home/<user>/deer-flow/` 下，直接执行 `./deploy-intranet.sh prepare` 时，bundle root 就是 `/home/<user>/deer-flow/`。
- 如果你是从源码仓库的 `scripts/deploy-intranet.sh` 运行脚本，默认 bundle root 是源码仓库根目录。
- 如果你已经 `cd /home/<user>/deer-flow`，直接执行 `./deploy-intranet.sh prepare` 即可，不需要额外加 `--bundle-root`。

如果你不想进入该目录，也可以显式指定部署根目录：

```bash
./deploy-intranet.sh --bundle-root /home/<user>/deer-flow prepare
./deploy-intranet.sh --bundle-root /home/<user>/deer-flow up
```

或使用环境变量：

```bash
DEER_FLOW_BUNDLE_ROOT=/home/<user>/deer-flow ./deploy-intranet.sh up
```

## 4. 构建机准备

在构建机上确认 Docker 可用：

```bash
docker version
docker compose version
docker info
```

正常情况：

- `docker version` 能显示 Docker 客户端和服务端版本。
- `docker compose version` 能显示 Compose v2 版本。
- `docker info` 能输出很多 Docker 信息，并且没有 permission denied。

如果 `docker info` 报权限错误：

```text
permission denied while trying to connect to the docker API
```

可以执行：

```bash
sudo systemctl start docker
sudo usermod -aG docker "$USER"
```

然后退出当前登录会话，重新登录，再执行：

```bash
docker info
```

原理说明：

- Docker daemon 是系统级服务。
- 普通用户需要加入 `docker` 组才能直接执行 Docker 命令。
- `usermod` 后必须重新登录，权限才会生效。

## 5. 在构建机打包

进入 DeerFlow 仓库根目录：

```bash
cd /path/to/deer-flow
```

把 `/path/to/deer-flow` 换成真实源码目录。

执行打包：

```bash
scripts/package-intranet-offline.sh --version 20260527-intranet --force
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `--version 20260527-intranet` | 给这次离线包起版本名，可按日期命名 |
| `--force` | 如果同名输出目录已存在，允许覆盖 |
| `--no-cache` | 强制重新构建镜像，通常只有依赖变化时才用 |
| `--require-clean` | 要求 Git 工作区干净，适合正式发版 |

正常输出目录：

```text
dist/intranet/deer-flow-20260527-intranet/
```

检查文件：

```bash
ls dist/intranet/deer-flow-20260527-intranet
```

应至少看到：

```text
deer-flow-images-20260527-intranet.tar
deer-flow-source-20260527-intranet.tar.gz
deploy-intranet.sh
MANIFEST.txt
SHA256SUMS
禁公网内网离线部署作业指导书.md
```

原理说明：

- `deer-flow-images-*.tar` 是 Docker 镜像包。
- `deer-flow-source-*.tar.gz` 是运行需要的源码、脚本、基础配置和归零排故智能体预置可用配置。
- `deploy-intranet.sh` 是内网服务器上的统一入口。
- 根目录不再提供参考 Compose 或参考 env 文件，真实 Compose 和真实 env 都由 `prepare` 阶段确定，避免部署人员误用参考文件。

## 6. 拷贝离线包到内网服务器

把整个输出目录拷贝到内网服务器的部署目录。可以用 U 盘、堡垒机、scp、文件传输系统等方式。

如果可以用 `scp`，示例命令：

```bash
scp -r dist/intranet/deer-flow-20260527-intranet/* <user>@<内网服务器IP>:/home/<user>/deer-flow/
```

把 `<内网服务器IP>` 换成真实 IP。

到内网服务器上检查：

```bash
cd /home/<user>/deer-flow
ls
```

应看到：

```text
deer-flow-images-20260527-intranet.tar
deer-flow-source-20260527-intranet.tar.gz
deploy-intranet.sh
...
```

原理说明：

- 需要拷贝目录内的所有文件，不要只拷贝镜像 tar。
- `deploy-intranet.sh` 会自动找到镜像 tar 和源码 tar。

## 7. 在内网服务器校验文件完整性

进入部署目录：

```bash
cd /home/<user>/deer-flow
```

校验文件：

```bash
sha256sum -c SHA256SUMS
```

正常情况会看到每个文件后面显示：

```text
OK
```

如果显示 `FAILED`，说明文件传输可能损坏，需要重新拷贝。

原理说明：

- `SHA256SUMS` 是构建机生成的文件指纹。
- 内网服务器重新计算指纹，能判断文件是否被传坏。

## 8. 导入 Docker 镜像

执行：

```bash
docker load -i deer-flow-images-20260527-intranet.tar
```

确认镜像已导入：

```bash
docker images | grep deer-flow
docker images | grep nginx
```

正常情况能看到 `deer-flow-gateway`、`deer-flow-frontend` 和 `nginx` 相关镜像。

原理说明：

- `docker load` 把离线 tar 包里的镜像导入到本机 Docker。
- 后续启动容器时不会再去公网拉镜像。

## 9. 准备运行目录

执行：

```bash
./deploy-intranet.sh prepare
```

正常输出会提示：

```text
prepared source: /home/<user>/deer-flow/source
prepared runtime: /home/<user>/deer-flow/runtime
env file: /home/<user>/deer-flow/env.intranet
```

检查生成的目录：

```bash
ls -la runtime
ls runtime/data
```

应看到：

```text
config.yaml
.env
frontend.env
extensions_config.json
```

注意：`.env` 是隐藏文件，普通 `ls runtime` 可能看不到。确认它是否存在时请用：

```bash
ls -l runtime/.env
```

`runtime/data` 下应看到：

```text
.better-auth-secret
.internal-auth-token
```

原理说明：

- `prepare` 先查找 `deer-flow-source-*.tar.gz` 和 `deer-flow-images-*.tar`，如果命令中指定了 `--version`，就按版本精确查找。
- `prepare` 使用的 bundle root 默认来自 `deploy-intranet.sh` 所在目录；如果脚本放在离线包根目录，bundle root 就是离线包根目录。
- 在源码仓库调试时，如果从 `scripts/deploy-intranet.sh` 运行，默认 bundle root 是仓库根目录。
- 也可以用 `--bundle-root` 或 `DEER_FLOW_BUNDLE_ROOT` 显式指定部署根目录，显式指定时优先级最高。
- `prepare` 会把源码包解压到 `source/`。真正使用的 Compose 文件在 `source/docker/docker-compose.intranet.yaml`。
- `prepare` 会创建 `runtime/` 和 `runtime/data/`，并从 `source/` 里的模板生成真实运行配置。
- `prepare` 会生成或复用两个密钥文件，保证重复执行不会轻易改变会话密钥和内部鉴权 token。
- `prepare` 会生成 `env.intranet`，记录当前部署目录的绝对路径、镜像名、端口和配置文件位置。
- `prepare` 会把源码包随附的归零排故智能体预置可用配置安装到 `runtime/data/agents/fault-zeroing/`，并把五个 custom subagent 合并进 `runtime/config.yaml`。
- `prepare` 最后会检查这些文件是否存在，并检查 `runtime/config.yaml` 里的 `models` 必须是列表。
- `runtime/config.yaml` 默认会把模型列表写成合法的 `models: []`，避免配置格式错误。

`prepare` 生成或确认的配置文件清单：

| 文件 | 生成方式 | 主要作用 | 谁会读取 |
| --- | --- | --- | --- |
| `source/` | 从 `deer-flow-source-*.tar.gz` 解压 | 保存源码、脚本、Compose、配置模板和 skills | `deploy-intranet.sh`、Docker Compose |
| `runtime/config.yaml` | 从 `source/config.example.yaml` 生成，并把空 `models:` 改成 `models: []` | 后端主配置，配置模型、工具、沙箱、上传、数据库、记忆等 | Gateway 后端容器 |
| `runtime/.env` | 从 `source/.env.example` 复制，已存在则不覆盖 | 后端环境变量，放模型 key、搜索 key、数据库地址等敏感或环境相关值 | Gateway 后端容器 |
| `runtime/frontend.env` | 从 `source/frontend/.env.example` 复制，已存在则不覆盖 | 前端环境变量，放 `NEXT_PUBLIC_*`、前端服务端到 Gateway 的地址等 | Frontend 前端容器 |
| `runtime/extensions_config.json` | 优先从 `source/extensions_config.example.json` 复制；模板缺失时生成空配置 | MCP server、skills 等扩展工具配置 | Gateway 后端容器 |
| `runtime/data/agents/fault-zeroing/config.yaml`、`SOUL.md` | 从 `source/docs/fault-zeroing-agent/agent/` 的预置可用配置复制；已有相同内容则跳过 | 共享归零排故智能体，所有内网用户可见 | Agents API、Gateway 后端容器 |
| `runtime/data/.better-auth-secret` | 自动生成；已存在则复用 | 前端认证和会话签名密钥 | Frontend 前端容器 |
| `runtime/data/.internal-auth-token` | 自动生成；已存在则复用 | Gateway 多 worker 和内部调用鉴权 token | Gateway 后端容器 |
| `env.intranet` | 按当前部署目录自动生成；已有时只补缺失密钥项 | Docker Compose 总环境文件，记录端口、镜像名、宿主机配置路径 | `deploy-intranet.sh` 调用 Docker Compose 时读取 |

归零排故智能体安装规则：

- `prepare`、`up/start`、`restart` 默认自动安装；`status`、`logs`、`stop/down` 不触发安装。
- 如需临时关闭自动安装，可执行 `DEER_FLOW_INSTALL_FAULT_ZEROING=0 ./deploy-intranet.sh prepare`。
- 如果 `runtime/data/agents/fault-zeroing/` 已有不同内容，脚本会拒绝覆盖，避免覆盖现场定制；请先人工确认差异后再处理。
- 如果 `runtime/config.yaml` 中已有同名 custom subagent 但定义不同，脚本会失败并保留原配置；写入前会生成 `runtime/config.yaml.bak-fault-zeroing`。

不要手工新建根目录 Compose 文件，也不要直接运行 `docker compose`。后续启动、停止、查看日志都通过 `deploy-intranet.sh` 完成。

## 10. 配置模型

打开主配置文件：

```bash
nano runtime/config.yaml
```

如果没有 `nano`，可以用 `vi`：

```bash
vi runtime/config.yaml
```

找到：

```yaml
models: []
```

把它替换成你的模型配置。以下是内网 OpenAI-compatible 模型示例：

```yaml
models:
  - name: intranet-qwen
    display_name: Intranet Qwen
    use: langchain_openai:ChatOpenAI
    model: Qwen3-32B
    api_key: $OPENAI_API_KEY
    base_url: http://10.10.1.20:8000/v1
    request_timeout: 600.0
    max_retries: 2
    max_tokens: 8192
    temperature: 0.7
    supports_vision: false
```

把 `http://10.10.1.20:8000/v1` 改成你的模型服务地址。

然后编辑后端环境变量：

```bash
nano runtime/.env
```

增加或修改：

```bash
OPENAI_API_KEY=dummy
```

如果模型服务需要真实 key，就填真实 key：

```bash
OPENAI_API_KEY=sk-xxxxxxxx
```

原理说明：

- `runtime/config.yaml` 里的 `api_key: $OPENAI_API_KEY` 不是直接写 key，而是引用环境变量。
- 真正的 key 写在 `runtime/.env`。
- 如果内网模型服务不校验 key，很多客户端仍要求有这个字段，可以填 `dummy`。
- 容器里的 `localhost` 是容器自己，不是宿主机。模型服务在其他机器时，应写内网 IP。

检查配置里 `models` 是否是列表：

```bash
grep -n "models:" -A20 runtime/config.yaml
```

如果看到类似：

```yaml
models:
  - name: intranet-qwen
```

说明格式大体正确。

## 11. 启动服务

执行：

```bash
./deploy-intranet.sh up
```

脚本会自动做：

1. 检查配置文件是否存在。
2. 导入镜像。
3. 启动 `nginx`、`frontend`、`gateway`。
4. 检查 `/health`、`/api/v1/auth/setup-status` 和首页 `/`。

正常情况会看到类似：

```text
gateway is healthy: http://127.0.0.1:2026/health
auth setup-status is healthy: http://127.0.0.1:2026/api/v1/auth/setup-status
frontend is healthy: http://127.0.0.1:2026/
```

原理说明：

- `nginx` 对外提供统一入口，默认端口是 `2026`。
- `frontend` 是浏览器页面。
- `gateway` 是后端 API 和智能体运行服务。
- `/health` 和 `/api/v1/auth/setup-status` 证明后端可用。
- 首页 `/` 证明前端页面可用。
- 登录后进入主页时，前端需要通过 Gateway 校验登录状态，所以 Gateway 和 Frontend 都要健康。

## 12. 查看运行状态

查看容器状态：

```bash
./deploy-intranet.sh status
```

查看所有日志：

```bash
./deploy-intranet.sh logs
```

只看后端日志：

```bash
./deploy-intranet.sh logs gateway
```

只看前端日志：

```bash
./deploy-intranet.sh logs frontend
```

只看 nginx 日志：

```bash
./deploy-intranet.sh logs nginx
```

原理说明：

- 启动失败通常先看 `gateway`。
- 页面打不开再看 `nginx`。
- 页面能打开但交互异常，再看 `frontend` 和 `gateway`。

## 13. 浏览器访问

在浏览器打开：

```text
http://<内网服务器IP>:2026
```

例如：

```text
http://10.10.1.30:2026
```

首次访问通常会进入初始化页面，按页面提示创建管理员账号。

验证流程：

1. 打开页面。
2. 创建管理员账号。
3. 进入 `/workspace`。
4. 退出登录。
5. 用刚才的账号密码重新登录。
6. 再次进入 `/workspace`。

## 14. 修改模型配置后重启

如果修改了：

```text
runtime/config.yaml
runtime/.env
```

执行：

```bash
./deploy-intranet.sh restart
```

原理说明：

- 模型配置由 Gateway 使用。
- 修改模型后重启服务，能确保新配置被加载。

## 15. 停止服务

停止容器：

```bash
./deploy-intranet.sh stop
```

或：

```bash
./deploy-intranet.sh down
```

原理说明：

- 这会停止 Docker Compose 启动的服务。
- 不会删除 `runtime/` 里的配置和数据。

## 16. 升级版本

升级时建议：

1. 先备份 runtime：

```bash
cp -a runtime runtime.bak.$(date +%Y%m%d-%H%M%S)
```

2. 拷贝新版本离线包到部署目录。
3. 执行新版本镜像导入：

```bash
docker load -i deer-flow-images-<new-version>.tar
```

4. 用新版本脚本启动：

```bash
./deploy-intranet.sh --version <new-version> restart
```

原理说明：

- `runtime/` 是你的本地配置和运行数据，升级前先备份。
- 镜像和源码可以替换，runtime 尽量保留。
- 新版本随附的归零排故智能体预置可用配置会在 `restart` 时重新检查；如共享目录已有现场定制且内容不同，脚本会拒绝覆盖，需要人工确认后处理。

## 17. 回滚版本

如果新版本异常，回滚步骤：

1. 停止服务：

```bash
./deploy-intranet.sh stop
```

2. 重新导入旧镜像：

```bash
docker load -i deer-flow-images-<old-version>.tar
```

3. 使用旧版本重启：

```bash
./deploy-intranet.sh --version <old-version> restart
```

如果 runtime 也被改坏了，可以恢复备份：

```bash
rm -rf runtime
cp -a runtime.bak.<时间> runtime
```

## 18. 常见故障和处理

### 18.1 docker load 失败

先校验文件：

```bash
sha256sum -c SHA256SUMS
```

如果校验失败，重新拷贝离线包。

### 18.2 Docker 权限错误

现象：

```text
permission denied while trying to connect to the docker API
```

处理：

```bash
sudo systemctl start docker
sudo usermod -aG docker "$USER"
```

然后重新登录服务器。

### 18.3 gateway 启动失败

查看日志：

```bash
./deploy-intranet.sh logs gateway
```

重点检查：

- `runtime/config.yaml` 是否存在。
- `runtime/extensions_config.json` 是否存在。
- `models` 是否是列表。
- 模型服务地址是否能从内网服务器访问。

如果看到：

```text
models must be a list
```

检查：

```bash
grep -n "models:" -A20 runtime/config.yaml
```

正确格式应类似：

```yaml
models:
  - name: intranet-qwen
```

或临时保持：

```yaml
models: []
```

### 18.4 frontend 启动失败

检查：

```bash
ls runtime/frontend.env
grep '^DEER_FLOW_FRONTEND_ENV_FILE=' env.intranet
```

`DEER_FLOW_FRONTEND_ENV_FILE` 应指向当前部署目录下的 `runtime/frontend.env`。

### 18.5 登录后无法进入主页

按顺序执行：

```bash
./deploy-intranet.sh logs gateway
curl -fsS http://127.0.0.1:2026/health
curl -fsS http://127.0.0.1:2026/api/v1/auth/setup-status
curl -fsS http://127.0.0.1:2026/
./deploy-intranet.sh logs frontend
./deploy-intranet.sh logs nginx
```

原理说明：

- 登录后进入 `/workspace` 时，前端服务端会访问 Gateway 的 `/api/v1/auth/me`。
- 如果 Gateway 没启动或配置错误，页面可能表现为无法进入主页。

### 18.6 登录态经常失效

检查 secret 文件：

```bash
ls -la runtime/data/.better-auth-secret
grep '^BETTER_AUTH_SECRET=' env.intranet
```

不要删除：

```text
runtime/data/.better-auth-secret
```

原理说明：

- 这个文件用于保持登录会话密钥稳定。
- 删除后会生成新密钥，旧登录态会失效。

## 19. 不要做的事

- 不要直接编辑源码目录的 `frontend/.env` 来修复离线部署。
- 不要手工新建根目录 Compose 文件，也不要绕过 `deploy-intranet.sh` 直接运行 `docker compose`。
- 不要随便删除 `runtime/data/.better-auth-secret`。
- 不要随便删除 `runtime/data/.internal-auth-token`。
- 不要把真实 API Key 提交到 Git。
