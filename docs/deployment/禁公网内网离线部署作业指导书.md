## 1. 这份文档给谁看

这份文档面向不熟悉 Docker 和 Linux 的部署人员。你可以把它当成“照着敲命令”的操作手册。

本文会把每一步拆成：

- 要做什么
- 输入什么命令
- 正常会看到什么
- 这一步的原理
- 常见错误怎么处理

## 2. 部署整体流程

整个离线部署分两台机器：

| 机器 | 是否能访问公网 | 做什么 |
| --- | --- | --- |
| 构建机 | 可以访问公网或企业依赖源 | 打包 Docker 镜像和源码 |
| 内网服务器 | 不能访问公网 | 导入镜像并启动 iDeer |

流程图：

```text
构建机打包
  -> 得到 dist/intranet/ideer-<version>/
  -> 拷贝整个目录到内网服务器
  -> 内网服务器执行 prepare
  -> 填写模型配置
  -> 启动服务
  -> 浏览器访问
```

原理说明：

- 内网服务器不能联网，所以不能现场拉取镜像和依赖。
- 构建机先把需要的镜像打成 `tar` 文件。
- 内网服务器用 `docker load` 导入镜像，不需要访问公网。

## 3. 路径约定

本文示例部署目录是：

```text
/home/<user>/ideer
```

其中 `<user>` 是内网服务器上的实际用户名，例如 `zhangsan`、`admin` 或你的登录账号。后文所有命令里的 `<user>` 都要替换成真实用户名。

这不是强制目录。也可以换成其他部署目录，例如：

```text
/data/apps/ideer
/srv/ideer
```

后文命令都以 `/home/<user>/ideer` 为例。如果你换了目录，要把命令里的路径一起替换。

推荐做法：

```bash
mkdir -p /home/<user>/ideer
cd /home/<user>/ideer
```

原理说明：

- `mkdir -p` 表示目录不存在就创建，存在也不报错。
- `cd` 表示进入这个目录。
- 后续脚本会在当前目录下生成 `source/`、`runtime/` 和 `env.intranet`。
- 离线包里的 `deploy-intranet.sh` 默认会把“脚本所在目录”当成部署根目录，也就是 bundle root。
- 换句话说，如果 `deploy-intranet.sh` 放在 `/home/<user>/ideer/` 下，直接执行 `./deploy-intranet.sh prepare` 时，bundle root 就是 `/home/<user>/ideer/`。
- 如果你是从源码仓库的 `scripts/deploy-intranet.sh` 运行脚本，默认 bundle root 是源码仓库根目录。
- 如果你已经 `cd /home/<user>/ideer`，直接执行 `./deploy-intranet.sh prepare` 即可，不需要额外加 `--bundle-root`。

如果你不想进入该目录，也可以显式指定部署根目录：

```bash
./deploy-intranet.sh --bundle-root /home/<user>/ideer prepare
./deploy-intranet.sh --bundle-root /home/<user>/ideer up
```

或使用环境变量：

```bash
IDEER_BUNDLE_ROOT=/home/<user>/ideer ./deploy-intranet.sh up
```

## 4. 确认部署机（内网服务器）架构（重要）

Docker 镜像是按 CPU 架构区分的：`linux/amd64` 的镜像只能在 amd64（x86 64 位）架构的机器上运行，`linux/arm64` 的镜像只能在 arm64（aarch64）架构的机器上运行。离线包默认按 `linux/amd64` 打包（见第 6 节的 `--platform` 参数），如果内网服务器是 ARM 架构（例如鲲鹏、飞腾服务器），按默认包直接部署会在启动容器时报错。

在内网服务器上执行：

```bash
uname -m
```

或：

```bash
docker info --format '{{.Architecture}}'
```

结果对照：

| 命令输出 | 服务器架构 | 默认离线包是否适用 |
| --- | --- | --- |
| `x86_64` | amd64（x86 64 位） | 适用 |
| `aarch64` | arm64（ARM 64 位） | 不适用，需按 `--platform linux/arm64` 重新打包 |

原理说明：

- `docker info` 显示的是 Docker 守护进程实际运行的架构，容器由它运行，所以以它为准。
- 普通服务器上 `uname -m` 和 `docker info` 的结果一致；如果两者不一致，说明 Docker 运行在模拟或嵌套环境里，按 `docker info` 的结果打包。
- 每个离线包根目录都有 `MANIFEST.txt`，里面的 `Platform:` 一行就是这包镜像的目标架构，可在导入镜像后用于核对。
- 如果内网服务器不是 amd64，需要提前告诉构建机负责人，打包时用 `--platform` 指定服务器架构，而不是等在部署现场报错。

## 5. 构建机准备

在构建机上确认 Docker 可用：

```bash
docker version
docker compose version
docker info
```

正常情况：

- `docker version` 能显示 Docker 客户端和服务端版本。
- `docker compose version` 能显示 Compose v2 版本。
- `docker info` 能输出很多 Docker 信息，并且没有 permission denied。

如果 `docker info` 报权限错误：

```text
permission denied while trying to connect to the docker API
```

可以执行：

```bash
sudo systemctl start docker
sudo usermod -aG docker "$USER"
```

然后退出当前登录会话，重新登录，再执行：

```bash
docker info
```

原理说明：

- Docker daemon 是系统级服务。
- 普通用户需要加入 `docker` 组才能直接执行 Docker 命令。
- `usermod` 后必须重新登录，权限才会生效。

另外，随包的自定义技能取自构建机本地的 `resources/skills/` 目录（该目录大部分内容不随 Git 同步，只在构建机本地存在）。打包前请核对：

```bash
ls resources/skills/
```

确认这里包含所有需要随包分发的自定义技能（如 srs-writing、officecli、translate 等）。若某个技能在构建机上不存在，打包时会静默缺失；正式发版时建议配合 `--skills-manifest` 让缺失直接导致打包失败（见第 6 节）。

## 6. 在构建机打包

进入 iDeer 仓库根目录：

```bash
cd /path/to/ideer
```

把 `/path/to/ideer` 换成真实源码目录。

执行打包：

```bash
scripts/package-intranet-offline.sh --version 20260527-intranet --force
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `--version 20260527-intranet` | 给这次离线包起版本名，可按日期命名 |
| `--force` | 如果同名输出目录已存在，允许覆盖 |
| `--no-cache` | 强制重新构建镜像，通常只有依赖变化时才用 |
| `--require-clean` | 要求 Git 工作区干净，适合正式发版 |
| `--platform <架构>` | 镜像目标架构，默认 `linux/amd64`；内网服务器是 ARM 架构（第 4 节中 `uname -m` 输出 `aarch64`）时，改为 `--platform linux/arm64` |
| `--skills-manifest <清单>` | 期望随包的自定义技能名单（逗号分隔，如 `fault-zeroing,translate`）。构建机上若缺少其中任一技能，打包直接失败，避免静默缺失；正式发版建议使用 |

正常输出目录：

```text
dist/intranet/ideer-20260527-intranet/
```

检查文件：

```bash
ls dist/intranet/ideer-20260527-intranet
```

应至少看到：

```text
ideer-images-20260527-intranet.tar
ideer-source-20260527-intranet.tar.gz
deploy-intranet.sh
MANIFEST.txt
SHA256SUMS
禁公网内网离线部署作业指导书.md
```

核对随包技能与预期一致：

```bash
grep -A 20 '^Custom Skills' dist/intranet/ideer-20260527-intranet/MANIFEST.txt
```

`Custom Skills` 段列出实际打进源码包的自定义技能；若打包时使用了 `--exclude-skills`，还会附一行 `Excluded:` 记录被排除的技能。

原理说明：

- `ideer-images-*.tar` 是 Docker 镜像包，包含 `ideer-gateway`、`ideer-frontend`、`nginx` 三个运行时镜像，以及默认附带的沙箱镜像（打包后统一命名为 `ideer-sandbox:<版本>`，即 AI 执行代码/命令时使用的小容器模板）。
- `ideer-source-*.tar.gz` 是运行需要的源码、脚本、基础配置和预置可用配置（归零排故智能体、SRS 编写智能体、officecli 工具、fault-zeroing 工作流），并包含构建机本地 `resources/skills/` 下的自定义技能（部署后归属超级管理员、可见性为 `public`）。
- `deploy-intranet.sh` 是内网服务器上的统一入口。
- 根目录不再提供参考 Compose 或参考 env 文件，真实 Compose 和真实 env 都由 `prepare` 阶段确定，避免部署人员误用参考文件。
- 若打包时使用了 `--no-sandbox`，镜像包内不含沙箱镜像（MANIFEST.txt 会注明）；此时平台上"让 AI 写文件、跑命令"的功能会不可用，详见排障章节。

打包参数补充说明：

| 参数 | 含义 |
| --- | --- |
| `--sandbox-image <镜像>` | 指定要打进离线包的沙箱镜像源（默认官方镜像，企业自备沙箱镜像时可覆盖） |
| `--no-sandbox` | 不打包沙箱镜像（不推荐，沙箱相关功能将不可用） |

## 7. 拷贝离线包到内网服务器

把整个输出目录拷贝到内网服务器的部署目录。可以用 U 盘、堡垒机、scp、文件传输系统等方式。

如果可以用 `scp`，示例命令：

```bash
scp -r dist/intranet/ideer-20260527-intranet/* <user>@<内网服务器IP>:/home/<user>/ideer/
```

把 `<内网服务器IP>` 换成真实 IP。

到内网服务器上检查：

```bash
cd /home/<user>/ideer
ls
```

应看到：

```text
ideer-images-20260527-intranet.tar
ideer-source-20260527-intranet.tar.gz
deploy-intranet.sh
...
```

原理说明：

- 需要拷贝目录内的所有文件，不要只拷贝镜像 tar。
- `deploy-intranet.sh` 会自动找到镜像 tar 和源码 tar。

## 8. 在内网服务器校验文件完整性

进入部署目录：

```bash
cd /home/<user>/ideer
```

校验文件：

```bash
sha256sum -c SHA256SUMS
```

正常情况会看到每个文件后面显示：

```text
OK
```

如果显示 `FAILED`，说明文件传输可能损坏，需要重新拷贝。

原理说明：

- `SHA256SUMS` 是构建机生成的文件指纹。
- 内网服务器重新计算指纹，能判断文件是否被传坏。

## 9. 导入 Docker 镜像

执行：

```bash
docker load -i ideer-images-20260527-intranet.tar
```

确认镜像已导入：

```bash
docker images | grep ideer
docker images | grep nginx
```

正常情况能看到 `ideer-gateway`、`ideer-frontend`、`ideer-sandbox` 和 `nginx` 相关镜像（`ideer-sandbox` 仅在打包时未使用 `--no-sandbox` 时才存在）。

架构核对（推荐）：离线包默认按 `linux/amd64` 打包，导入后建议确认镜像架构与服务器一致：

```bash
docker image inspect ideer-sandbox:<版本> --format '{{.Os}}/{{.Architecture}}'
```

也可以直接查看离线包根目录的 `MANIFEST.txt`，其中 `Platform:` 一行记录了镜像的目标架构。若与服务器架构（第 4 节的 `docker info` 结果）不一致，不要继续部署，按第 19.8 节处理。

原理说明：

- `docker load` 把离线 tar 包里的镜像导入到本机 Docker。
- 后续启动容器时不会再去公网拉镜像。
- 沙箱镜像也随压缩包导入；导入后部署脚本会自动把它配置为平台使用的镜像，无需手工指定。

## 10. 准备运行目录

执行：

```bash
./deploy-intranet.sh prepare
```

正常输出会提示类似下面内容。路径会按你的实际部署目录变化；重复执行时结果保持一致（幂等）。

```text
extracting source tar...
[可能] enabling agents_api in /home/<user>/ideer/runtime/config.yaml ...
[可能] patching officecli mount host_path: /opt/ideer/vendor/officecli/officecli -> /home/<user>/ideer/source/vendor/officecli/officecli
prepared source: /home/<user>/ideer/source
prepared runtime: /home/<user>/ideer/runtime
env file: /home/<user>/ideer/env.intranet
```

用一条命令检查生成的运行文件：

```bash
find runtime -maxdepth 4 -type f | sort
```

至少应看到这些文件：

```text
runtime/.env
runtime/config.yaml
runtime/data/.better-auth-secret
runtime/data/.internal-auth-token
runtime/extensions_config.json
runtime/frontend.env
```

说明：`.env`、`.better-auth-secret`、`.internal-auth-token` 都是隐藏文件，普通 `ls` 命令可能看不到；统一使用上面的 `find ... | sort` 命令检查即可。

`prepare` 按时间顺序执行这些动作：

- 第 1 步：确定部署根目录。默认使用 `deploy-intranet.sh` 所在目录；也可以用 `--bundle-root` 或 `IDEER_BUNDLE_ROOT` 指定。
- 第 2 步：查找 `ideer-source-*.tar.gz` 和 `ideer-images-*.tar`。如果传入 `--version`，就按版本名精确查找。
- 第 3 步：把源码包解压到 `source/`。后续 Compose 文件来自 `source/docker/docker-compose.intranet.yaml`。
- 第 4 步：创建 `runtime/` 和 `runtime/data/`，并生成运行配置：`runtime/config.yaml`、`runtime/.env`、`runtime/frontend.env`、`runtime/extensions_config.json`。
- 第 5 步：把 `runtime/config.yaml` 的 `agents_api.enabled` 置为 `true`，并把 officecli 工具的挂载路径指向 `source/vendor/officecli/officecli`（仅当 bundle 带 officecli 且原路径不存在时）。
- 第 6 步：如果有内置沙箱镜像（`ideer-sandbox:<版本>`），把 `runtime/config.yaml` 里 `sandbox.image` 的占位值自动改写为 `ideer-sandbox:<版本>`，并把镜像名写入 `env.intranet` 的 `IDEER_SANDBOX_IMAGE`。如果你的 `sandbox.image` 已经被改成其它本地已存在的镜像名，脚本不会覆盖你的设置。
- 第 7 步：生成或复用 `runtime/data/.better-auth-secret` 和 `runtime/data/.internal-auth-token`，让重复执行 `prepare` 不会随意更换登录会话密钥和内部鉴权 token。
- 第 8 步：生成或补全 `env.intranet`，记录端口、镜像名、源码目录、运行目录和配置文件绝对路径，供 Docker Compose 启动时读取。
- 第 9 步：校验运行文件是否齐全，并检查 `runtime/config.yaml` 里的 `models` 是合法列表；默认会生成 `models: []`，后续再由你填写真实模型。

`prepare` 不安装任何智能体。随包预置的智能体（归零排故、SRS 编写）、自定义技能和工作流会在首次 `./deploy-intranet.sh up`（或 `restart`）时安装为**超级管理员账户的公开资源**（见第 12 节）。

**沙箱配置说明（重要）：**

沙箱是平台执行"写文件、跑命令"等操作时使用的独立小容器，模板是离线包里的 `ideer-sandbox:<版本>` 镜像。

- 正常部署时你**不需要**手工配置沙箱：`prepare` 已自动把 `sandbox.image` 改为包内镜像（第 6 步）。
- 若你希望使用企业自备的沙箱镜像（例如带特定软件环境的镜像），先在服务器上 `docker load` 导入该镜像，再把 `runtime/config.yaml` 中 `sandbox.image` 改成该镜像名（脚本会尊重你已配置的、本地存在的镜像名，不会覆盖）。
- 若打包时用了 `--no-sandbox`（镜像包里没有沙箱镜像），`deploy-intranet.sh up` 时会在校验阶段给出告警，提示你加载沙箱镜像或改用不需要镜像的执行模式。不要忽略该告警：忽略后表面一切正常，但一旦让 AI 写文件或跑命令就会报镜像不存在。

不要手工新建根目录 Compose 文件，也不要直接运行 `docker compose`。后续启动、停止、查看日志都通过 `deploy-intranet.sh` 完成。

## 11. 配置模型

打开主配置文件：

```bash
nano runtime/config.yaml
```

如果没有 `nano`，可以用 `vi`：

```bash
vi runtime/config.yaml
```

找到：

```yaml
models: []
```

把它替换成你的模型配置。以下是内网 OpenAI-compatible 模型示例：

```yaml
models:
  - name: intranet-qwen
    display_name: Intranet Qwen
    use: langchain_openai:ChatOpenAI
    model: Qwen3-32B
    api_key: $OPENAI_API_KEY
    base_url: http://10.10.1.20:8000/v1
    request_timeout: 600.0
    max_retries: 2
    max_tokens: 8192
    temperature: 0.7
    supports_vision: false
```

把 `http://10.10.1.20:8000/v1` 改成你的模型服务地址。

然后编辑后端环境变量：

```bash
nano runtime/.env
```

增加或修改：

```bash
OPENAI_API_KEY=dummy
```

如果模型服务需要真实 key，就填真实 key：

```bash
OPENAI_API_KEY=sk-xxxxxxxx
```

原理说明：

- `runtime/config.yaml` 里的 `api_key: $OPENAI_API_KEY` 不是直接写 key，而是引用环境变量。
- 真正的 key 写在 `runtime/.env`。
- 如果内网模型服务不校验 key，很多客户端仍要求有这个字段，可以填 `dummy`。
- 容器里的 `localhost` 是容器自己，不是宿主机。模型服务在其他机器时，应写内网 IP。

检查配置里 `models` 是否是列表：

```bash
grep -n "models:" -A20 runtime/config.yaml
```

如果看到类似：

```yaml
models:
  - name: intranet-qwen
```

说明格式大体正确。

## 12. 启动服务

执行：

```bash
./deploy-intranet.sh up
```

脚本会自动做：

1. 检查配置文件是否存在。
2. 导入镜像。
3. 启动 `nginx`、`frontend`、`gateway`。
4. 检查 `/health`、`/api/v1/auth/setup-status` 和首页 `/`。
5. 首次部署自动创建超级管理员账户：邮箱和密码默认均为 `super_admin@test.com`。可用环境变量 `IDEER_ADMIN_EMAIL` / `IDEER_ADMIN_PASSWORD` 覆盖；系统已有管理员时自动跳过（不会覆盖已有账号）。
6. 网关健康且管理员存在后，把随包预置资源安装为**超级管理员的公开资源**：
   - 归零排故、SRS 编写两个智能体以 canonical 资源（bundled 稳定 UUID）安装，资源归属超级管理员、可见性为 `public`，所有用户可用；
   - `resources/skills/` 下的自定义技能（srs-writing、officecli 等）归属超级管理员、可见性为 `public`；
   - `resources/skills/` 下的公开技能保持公开，所有用户都能使用；
   - fault-zeroing 工作流以管理员为创建者 seed 进工作流库（幂等，已存在则跳过）；
   - 从旧版本升级时，`runtime/data/agents/` 下残留的旧共享副本（与 bundle 完全一致）会被自动清理；有现场定制的共享副本会保留并告警，需人工确认。
   - 此外，`bundled-resources.json` 清单声明的预装资源（公开技能、agent、工作流）由超级管理员拥有、经 canonical 资源目录安装（`storage_kind="bundled"`），`system_owned` 按清单可选标记（默认否），管理员可按需编辑、申请/变更可见性，不再视为只读系统资产。
7. 关闭某个智能体安装可执行 `IDEER_INSTALL_FAULT_ZEROING=0 ./deploy-intranet.sh up` 或 `IDEER_INSTALL_SRS_WRITING=0 ./deploy-intranet.sh up`。第 5、6 步任何一步失败只告警、不阻止启动，可稍后重跑 `./deploy-intranet.sh restart` 补齐。

如果服务器没有安装 `curl`，脚本会自动尝试使用 `wget`、`python3` 或 `python` 做同样的 HTTP 健康检查。不要忽略健康检查失败；如果这里没有显示三条 `is healthy`，浏览器里可能表现为页面不完整、登录按钮无响应或登录后无法进入主页。

原理说明：

- `nginx` 对外提供统一入口，默认端口是 `2026`。
- `frontend` 是浏览器页面。
- `gateway` 是后端 API 和智能体运行服务。
- `/health` 和 `/api/v1/auth/setup-status` 证明后端可用。
- 首页 `/` 证明前端页面可用。
- 登录后进入主页时，前端需要通过 Gateway 校验登录状态，所以 Gateway 和 Frontend 都要健康。
- 默认管理员账号密码是公开的测试账号。内网部署后建议立即修改管理员密码，或部署时用 `IDEER_ADMIN_PASSWORD` 指定强密码。

## 17. 升级版本

> **资源目录（canonical）升级提示**：本版本为 Resource Governance V2 定案（canonical-only）。若当前运行版本仍为旧版（legacy/dual 模式），升级前必须先在**旧版本**上执行 `audit → migrate → verify`（见[迁移映射](../governance/resource-governance-v2-migration-map.md)）且三者 exit 0，再按本节升级；无存量数据可直接安装。升级后 `/api/agents`、`/api/skills`、`/api/workflows` 等旧名称接口不存在（404），外部集成需切换 `/api/resources`；`IDEER_RESOURCE_CATALOG_MODE` 环境变量已移除，无需（也不应）再设置。

升级时建议：

1. 先备份 runtime：

```bash
cp -a runtime runtime.bak.$(date +%Y%m%d-%H%M%S)
```

2. 拷贝新版本离线包到部署目录。
3. 执行新版本镜像导入：

```bash
docker load -i ideer-images-<new-version>.tar
```

4. 用新版本脚本启动：

```bash
./deploy-intranet.sh --version <new-version> restart
```

原理说明：

- `runtime/` 是你的本地配置和运行数据，升级前先备份。
- 镜像和源码可以替换，runtime 尽量保留。
- 新版本随附的归零排故智能体和 SRS 编写智能体会在 `restart` 时通过 canonical 资源目录安装为超级管理员的公开资源（bundled 稳定 UUID，见 `bundled-resources.json`）；若已有现场定制且内容不同，脚本会拒绝覆盖，需要人工确认后处理。
- `restart` 还会在网关健康后重新 seed fault-zeroing 工作流（幂等，已存在则跳过）。
- 预装资源升级冲突：默认 `keep`（管理员已修改的资源保持最新内容，跳过预装更新）；如需用安装包内容覆盖，加 `--bundled-conflict override`（被覆盖资源的历史版本保留，可回滚）：

```bash
./deploy-intranet.sh --version <new-version> --bundled-conflict override restart
```

也可用环境变量等价形式：

```bash
IDEER_BUNDLED_CONFLICT=override ./deploy-intranet.sh --version <new-version> restart
```

## 18. 回滚版本

如果新版本异常，回滚步骤：

1. 停止服务：

```bash
./deploy-intranet.sh stop
```

2. 重新导入旧镜像：

```bash
docker load -i ideer-images-<old-version>.tar
```

3. 使用旧版本重启：

```bash

```


## 19. 常见故障和处理

### 19.1 docker load 失败

先校验文件：

```bash
sha256sum -c SHA256SUMS
```

如果校验失败，重新拷贝离线包。

### 19.2 Docker 权限错误

现象：

```text
permission denied while trying to connect to the docker API
```

处理：

```bash
sudo systemctl start docker
sudo usermod -aG docker "$USER"
```

然后重新登录服务器。

### 19.3 gateway 启动失败

查看日志：

```bash
./deploy-intranet.sh logs gateway
```

重点检查：

- `runtime/config.yaml` 是否存在。
- `runtime/extensions_config.json` 是否存在。
- `models` 是否是列表。
- 模型服务地址是否能从内网服务器访问。

如果看到：

```text
models must be a list
```

检查：

```bash
grep -n "models:" -A20 runtime/config.yaml
```

正确格式应类似：

```yaml
models:
  - name: intranet-qwen
```

或临时保持：

```yaml
models: []
```

### 19.4 AI 执行写文件/跑命令时报镜像不存在

现象：对话中让 AI "写个文件"或"跑个命令"，反复重试后报错类似 `image ... was not found`、`Failed to start sandbox container`。

原因：沙箱镜像未加载或 `sandbox.image` 指向了本地不存在的镜像名。

排查：

```bash
# 1. 检查沙箱镜像是否已导入
docker images | grep sandbox

# 2. 检查运行配置里的 sandbox.image
grep -n -A3 "^sandbox:" runtime/config.yaml
```

处理（三选一）：

- 重新打包（不带 `--no-sandbox`），或重新 `docker load -i ideer-images-<版本>.tar`，然后 `./deploy-intranet.sh restart` 让 `prepare` 自动改写 `sandbox.image`。
- 手动 `docker load` 自备沙箱镜像，并把 `runtime/config.yaml` 的 `sandbox.image` 改成该镜像名，然后重启。
- 该机器不需要沙箱能力：把 `runtime/config.yaml` 的 `sandbox.use` 改为 `ideer.sandbox.local:LocalSandboxProvider`（本地直连执行，无容器隔离，仅建议在完全可信的单机环境使用）。

### 19.5 frontend 启动失败

检查：

```bash
ls runtime/frontend.env
grep '^IDEER_FRONTEND_ENV_FILE=' env.intranet
```

`IDEER_FRONTEND_ENV_FILE` 应指向当前部署目录下的 `runtime/frontend.env`。

### 19.6 登录后无法进入主页

按顺序执行：

```bash
./deploy-intranet.sh restart
./deploy-intranet.sh status
./deploy-intranet.sh logs gateway
./deploy-intranet.sh logs frontend
./deploy-intranet.sh logs nginx
```

原理说明：

- 登录后进入 `/workspace` 时，前端服务端会访问 Gateway 的 `/api/v1/auth/me`。
- 如果 Gateway 没启动或配置错误，页面可能表现为无法进入主页。
- `restart` 会重新执行 `/health`、`/api/v1/auth/setup-status` 和首页 `/` 检查；即使服务器没有 `curl`，脚本也会尝试用 `wget` 或 Python 检查。

### 19.7 登录态经常失效

检查 secret 文件：

```bash
ls -la runtime/data/.better-auth-secret
grep '^BETTER_AUTH_SECRET=' env.intranet
```

不要删除：

```text
runtime/data/.better-auth-secret
```

原理说明：

- 这个文件用于保持登录会话密钥稳定。
- 删除后会生成新密钥，旧登录态会失效。

### 19.8 容器反复重启或启动失败，日志报 exec format error

现象：`docker load` 导入镜像成功，但容器反复重启或启动失败，日志里出现类似：

```text
exec format error
standard_init_linux.go:... exec format error
```

也可能报 `no matching manifest` 或镜像找不到。

原因：镜像是按 CPU 架构区分的。离线包默认按 `linux/amd64` 打包，如果内网服务器是其他架构（例如 ARM 的 aarch64，常见于鲲鹏、飞腾服务器），容器无法运行。

排查：

```bash
# 1. 确认服务器架构
uname -m

# 2. 查看离线包镜像的目标架构
grep "^Platform" MANIFEST.txt
```

- `uname -m` 输出 `x86_64` 表示 amd64，输出 `aarch64` 表示 arm64。
- 若服务器架构与 `Platform:` 不一致，就是架构不匹配，不要继续部署。

处理（按服务器架构重新打包）：

1. 在构建机上重新打包，`--platform` 填服务器架构（例如 `linux/arm64`）：

```bash
scripts/package-intranet-offline.sh --version <新版本> --platform linux/arm64 --force
```

2. 把新离线包拷贝到内网服务器，重新执行 `sha256sum -c SHA256SUMS` 和 `docker load -i ideer-images-<新版本>.tar`，再 `./deploy-intranet.sh restart`。

## 20. 不要做的事

- 不要直接编辑源码目录的 `frontend/.env` 来修复离线部署。
- 不要手工新建根目录 Compose 文件，也不要绕过 `deploy-intranet.sh` 直接运行 `docker compose`。
- 不要随便删除 `runtime/data/.better-auth-secret`。
- 不要随便删除 `runtime/data/.internal-auth-token`。
- 不要把真实 API Key 提交到 Git。
- 不要把 `runtime/config.yaml` 的 `sandbox.image` 改成本地不存在的镜像名（会导致 AI 写文件、跑命令报镜像不存在）。
