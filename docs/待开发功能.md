## 1. MCP 配置管理页面（增删改）

### 背景

后端已提供完整的 MCP 配置 CRUD API（`PUT /api/mcp/config`），支持新增、修改、删除 MCP 服务器。前端 `ToolSettingsPage` 目前只实现了服务器列表展示和启用/禁用开关，缺少添加、编辑、删除操作。

### 后端就绪状态

**API**: `PUT /api/mcp/config` ✅ 已实现

请求体包含完整的服务器配置：

```json
{
  "mcp_servers": {
    "{server_name}": {
      "enabled": true,
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {"GITHUB_TOKEN": "$GITHUB_TOKEN"},
      "url": null,
      "headers": {},
      "oauth": null,
      "description": "GitHub MCP server for repository operations"
    }
  }
}
```

- 对应对象名(`mcp_servers` 的 key)即服务器唯一标识，新增/删除通过对 key 的增删实现
- `env` 和 `headers` 的值在前端用 `***` 回显，PUT 时自动从磁盘恢复原值（`_merge_preserving_secrets`）
- 配置写入 `extensions_config.json`，下次 Agent 运行自动生效（mtime 热加载）

**TypeScript 类型**: `frontend/src/core/mcp/types.ts` ✅ 已定义

```typescript
interface MCPServerConfig {
  enabled: boolean;
  type: "stdio" | "sse" | "http";
  command?: string;
  args: string[];
  env: Record<string, string>;
  url?: string;
  headers: Record<string, string>;
  oauth?: McpOAuthConfig;
  description: string;
}
```

**API 函数**: `frontend/src/core/mcp/api.ts` ✅ `loadMCPConfig()` + `updateMCPConfig()`
**React Query Hooks**: `frontend/src/core/mcp/hooks.ts` ✅ `useMCPConfig()` + `useEnableMCPServer()`

## 3. 对话中主动选择 Skill / Tool 机制

### 背景

当前项目中 skill 和 tool 的选择完全由 LLM 自主决定：

- **Skills**：启用的 skill 列表注入 system prompt 的 `<available_skills>` 块，LLM 根据 skill 描述自动匹配用户意图，然后通过 `read_file` 读取 SKILL.md 加载指令。用户无法在对话中显式指定"使用 XX skill"。
- **Tools**：所有 `config.yaml` 中配置的 tools 全量绑定到 agent。`tool_search` 模式下 MCP tools 延迟加载，但发现和激活也由 agent 自主发起，非用户驱动。

缺少用户主动选择 skill/tool 的能力，在以下场景下存在不足：

1. 用户明确知道需要哪个 skill/tool，但 LLM 未能自动匹配
2. 需要在特定任务中强制使用或排除某些 skill/tool
3. 专业用户希望精确控制 agent 的能力边界

### 现有相关机制

| 机制 | 位置 | 说明 |
|------|------|------|
| `<available_skills>` 注入 | `ideer/agents/lead_agent/prompt.py:594-623` | LLM 自动匹配 skill |
| `tool_search` | `ideer/tools/builtins/tool_search.py` | agent 延迟发现 MCP tools |
| `skill_manage` | `ideer/tools/skill_manage_tool.py` | agent 自演化（创建/编辑 custom skill） |
| `extensions_config.json` | 启用/禁用 skill | 管理员级静态配置，无运行时切换 |

### 需求设计

#### 3.1 协议层

在对话消息 metadata 中传递用户选择：

```typescript
// 前端消息 payload 新增字段
interface MessagePayload {
  // ...existing fields...
  selected_skills?: string[];    // 用户主动选择的 skill 名称列表
  selected_tools?: string[];     // 用户主动选择的 tool 名称列表
  exclude_skills?: string[];     // 用户明确排除的 skill
  exclude_tools?: string[];      // 用户明确排除的 tool
}
```

后端 agent 运行时（`ideer/agents/lead_agent/agent.py`）读取 metadata，动态调整：

- **Skill 注入**：优先加载 `selected_skills` 中的 skill 内容到 system prompt
- **Tool 绑定**：根据 `selected_tools` 过滤可用 tools（仅绑定用户选择的 tool）

#### 3.2 后端实现要点

| 组件 | 改动 |
|------|------|
| `ideer/agents/lead_agent/prompt.py` | `apply_prompt_template` 接受 `selected_skills` 参数，优先注入用户选择的 skill 内容 |
| `ideer/tools/tools.py` | `get_available_tools` 接受 `selected_tools` / `exclude_tools` 参数，过滤 tool 列表 |
| `backend/app/gateway/routers/thread_runs.py` | 解析消息 metadata 中的选择字段，传递给 agent 运行上下文 |

#### 3.3 前端实现要点

| 组件 | 改动 |
|------|------|
| 对话输入框 | 新增 skill/tool 选择器（可选的下拉或多选组件） |
| `frontend/src/core/messages/` | 消息发送时携带 `selected_skills` / `selected_tools` |
| Settings 页面 | 展示所有可用 skill/tool 列表，支持预设默认选择 |

UI 参考：

```
│ [🔍 搜索并输入...]                          │
│                                             │
│ Skill: [全部 ▾]  Tool: [全部 ▾]            │
│  ┌──────────┐  ┌──────────┐                 │
│  │ ☑ agent- │  │ ☑ web_   │                 │
│  │   reach  │  │   search │                 │
│  │ ☐ aihot  │  │ ☐ bash   │                 │
│  │ ☐ browse │  │ ☐ read_  │                 │
│  └──────────┘  │   file   │                 │
│                └──────────┘                 │
│                            [发送]           │
└─────────────────────────────────────────────┘
```

#### 3.4 与现有机制的关系

| 场景 | 行为 |
|------|------|
| 用户未选择任何 skill/tool | 保持现有 LLM 自动匹配行为 |
| 用户选择了 skill | 优先注入选中 skill 的 SKILL.md 内容，LLM 仍可读取其他 skill |
| 用户选择了 tool | 仅绑定选中 tool，LLM 无法调用未选中的 tool |
| 用户排除了 skill/tool | 从可用列表中移除，LLM 不会看到也不可调用 |
| `tool_search` + 用户选择 | 用户选择优先级高于 tool_search 的延迟发现 |

### 实现优先级建议

3. **P2 前端 UI**：输入框 skill/tool 选择器组件
4. **P3 前端设置**：Settings 页面预设默认选择

## 5. 可见性申请重复提交的 UX 优化

### 背景

用户在工作流详情页提交可见性变更申请时，若该资源已有 PENDING 状态的申请，后端返回 409 Conflict，前端展示 "Failed to submit visibility application: A pending application already exists for this resource"。问题在于：

1. **状态不透明**：用户无法知道自己的资源已有待审核申请
2. **无前置检查**：可见性弹窗中直接展示提交表单，用户填完所有内容后提交才被拒绝
3. **无恢复路径**：报错后用户不知道可以撤回旧申请或等待审核

### 当前已知边界场景（已处理）

| 场景 | 处理方式 | 位置 |
|------|---------|------|
| 工作流被删除后 PENDING 申请 | 自动标记为 `rejected`，附注"资源已删除，申请自动关闭" | `backend/app/gateway/routers/workflows.py:377-397` |

### 修复方案

#### 5.1 后端：新增查询接口

**目标文件**: `backend/app/gateway/routers/visibility_applications.py`

新增 `GET /api/visibility-applications/check`，用户可查询指定资源的 pending 申请状态（无需 admin 角色）：

```python
# 请求参数
resource_type: str  # tool | skill | workflow | agent
resource_id: str

# 响应
{
  "has_pending": bool,
  "application": ApplicationResponse | null  # 存在 pending 申请时返回详情
}
```

设计原则：
- 该接口是只读的，仅查询自己资源的申请状态（资源已存在于当前上下文中）
- 不需要 admin 权限，任何认证用户均可调用
- 不与现有 `GET /api/visibility-applications`（require_role 管理端）冲突

#### 5.2 前端：弹窗状态感知

**目标文件**: `frontend/src/app/workspace/workflows/[workflow_name]/page.tsx`

打开可见性弹窗时先调用查询接口，按状态展示不同 UI：

| 状态 | UI |
|------|-----|
| 无 pending 申请 | 正常提交表单（现有行为不变） |
| 有 pending 申请 | 展示"已有待审核申请"提示（提交时间、目标可见性），提供"撤回并重新申请"按钮 |

交互流程：

```
用户点击"申请可见性变更"
  → 检查该资源是否有 pending 申请
  → 无 → 显示正常提交表单
  → 有 → 显示状态卡片：
         "你于 2026-07-09 14:30 提交了 private → public 的申请，等待管理员审核。"
         [撤回并重新申请] [关闭]
           ↓ 点击撤回
           调用 withdraw API
           成功后关闭状态卡片，刷新为提交表单
```

**新增 API 函数**: `frontend/src/core/visibility-applications/api.ts`
```typescript
export async function checkVisibilityApplicationStatus(
  resourceType: string,
  resourceId: string,
): Promise<{ has_pending: boolean; application: VisibilityApplication | null }>
```

#### 5.3 错误兜底

若用户仍因竞态条件在提交时收到 409，保持现有错误提示，但确保响应体中包含已有申请的 ID 和 version，方便用户直接执行撤回。
