## 3. 可见性申请重复提交的 UX 优化

### 背景

用户在工作流详情页提交可见性变更申请时，若该资源已有 PENDING 状态的申请，后端返回 409 Conflict，前端展示 "Failed to submit visibility application: A pending application already exists for this resource"。问题在于：

1. **状态不透明**：用户无法知道自己的资源已有待审核申请
2. **无前置检查**：可见性弹窗中直接展示提交表单，用户填完所有内容后提交才被拒绝
3. **无恢复路径**：报错后用户不知道可以撤回旧申请或等待审核

### 当前已知边界场景（已处理）

| 场景 | 处理方式 | 位置 |
|------|---------|------|
| 工作流被删除后 PENDING 申请 | 自动标记为 `rejected`，附注"资源已删除，申请自动关闭" | `backend/app/gateway/routers/workflows.py:377-397` |

### 修复方案

#### 3.1 后端：新增查询接口

**目标文件**: `backend/app/gateway/routers/visibility_applications.py`

新增 `GET /api/visibility-applications/check`，用户可查询指定资源的 pending 申请状态（无需 admin 角色）：

```python
# 请求参数
resource_type: str  # tool | skill | workflow | agent
resource_id: str

# 响应
{
  "has_pending": bool,
  "application": ApplicationResponse | null  # 存在 pending 申请时返回详情
}
```

设计原则：
- 该接口是只读的，仅查询自己资源的申请状态（资源已存在于当前上下文中）
- 不需要 admin 权限，任何认证用户均可调用
- 不与现有 `GET /api/visibility-applications`（require_role 管理端）冲突

#### 3.2 前端：弹窗状态感知

**目标文件**: `frontend/src/app/workspace/workflows/[workflow_name]/page.tsx`

打开可见性弹窗时先调用查询接口，按状态展示不同 UI：

| 状态 | UI |
|------|-----|
| 无 pending 申请 | 正常提交表单（现有行为不变） |
| 有 pending 申请 | 展示"已有待审核申请"提示（提交时间、目标可见性），提供"撤回并重新申请"按钮 |

交互流程：

```
用户点击"申请可见性变更"
  → 检查该资源是否有 pending 申请
  → 无 → 显示正常提交表单
  → 有 → 显示状态卡片：
         "你于 2026-07-09 14:30 提交了 private → public 的申请，等待管理员审核。"
         [撤回并重新申请] [关闭]
           ↓ 点击撤回
           调用 withdraw API
           成功后关闭状态卡片，刷新为提交表单
```

**新增 API 函数**: `frontend/src/core/visibility-applications/api.ts`
```typescript
export async function checkVisibilityApplicationStatus(
  resourceType: string,
  resourceId: string,
): Promise<{ has_pending: boolean; application: VisibilityApplication | null }>
```

#### 3.3 错误兜底

若用户仍因竞态条件在提交时收到 409，保持现有错误提示，但确保响应体中包含已有申请的 ID 和 version，方便用户直接执行撤回。

#### 3.4 i18n 补充

| Key | en-US | zh-CN |
|-----|-------|-------|
| `workflows.pendingApplicationExists` | You have a pending application submitted at {time} | 你于 {time} 已提交待审核申请 |
| `workflows.withdrawAndResubmit` | Withdraw and Re-apply | 撤回并重新申请 |
| `workflows.withdrawSuccess` | Application withdrawn, you can now submit a new one | 申请已撤回，可以重新提交 |
| `workflows.checkingApplication` | Checking application status... | 正在检查申请状态... |

| 文件 | 说明 |
|------|------|

## 4. 用户删除功能

### 背景

当前平台只有用户禁用（`disabled = true`）机制，无法真正删除用户。删除用户时，需要处理其名下的所有资源（agents、skills、workflows、tools、threads、runs 等），以及关联的 visibility_applications、audit_logs 等记录的引用关系。

### 后端就绪状态

| 组件 | 状态 |
|------|------|
| 用户禁用 `PATCH /api/admin/users/{user_id}/status` | ✅ 已实现（仅 toggle `disabled`） |
| 用户真实删除 API | ❌ 不存在 |
| 资源级软删除 (`ResourceMetadata.deleted_at`) | ✅ 已实现 |
| Department 删除的资源转移模式 (`admin.py:delete_department`) | ✅ 已有参考实现 |
| `token_version` 使 JWT 失效 | ✅ 已有实现（password change 时使用） |

### 用户拥有的全部资源

| 资源类型 | 存储方式 | user 关联列 | FK 约束 | 处理策略 |
|---------|---------|-------------|---------|---------|
| **Agent** | 磁盘目录 + `resource_metadata` | `owner_id` | FK → `users_ext.id` (无 ON DELETE) | 可配置 |
| **Skill** | 文件 + `resource_metadata` | `owner_id` | FK → `users_ext.id` (无 ON DELETE) | 可配置 |

| **Thread** | DB(`threads_meta`) + 磁盘目录 | `user_id` | 无 FK | 硬删除 |
| **Run** | DB(`runs`) | `user_id` | 无 FK | 硬删除 |
| **RunEvent** | DB(`run_events`) | `user_id` | 无 FK | 硬删除 |
| **Feedback** | DB(`feedback`) | `user_id` | 无 FK | 硬删除 |
| **VisibilityApplication** | DB(`visibility_applications`) | `applicant_id`, `reviewed_by` | FK → `users_ext.id` | 申请撤回，审查人置 NULL |
| **AuditLog** | DB(`audit_logs`) | `actor_id` | FK → `users_ext.id` (ON DELETE SET NULL) | 置 NULL |
| **Agent Memory** | 磁盘文件 `users/{user_id}/agent-memory/` | 路径含 user_id | N/A | 删除目录 |
| **User Memory** | 磁盘文件 `users/{user_id}/memory.json` | 路径含 user_id | N/A | 删除文件 |

### API 设计

**新增端点**: `DELETE /api/admin/users/{user_id}`

请求参数（query params）：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `resource_strategy` | `"transfer" \| "delete" \| "soft_delete"` | 是 | 对 agents/skills/workflows/tools 的处理策略 |
| `target_user_id` | `string` | transfer 时必填 | 资源转移的目标用户 ID |

三种策略：

| 策略 | 对 resource_metadata 资源 | 对磁盘文件 |
|------|--------------------------|-----------|
| `transfer` | 将 `owner_id` 更新为目标用户 | 将 agent 目录移动到目标用户目录 |
| `delete` | 软删除（设置 `deleted_at`） | 删除 agent 目录 |
| `soft_delete` | 软删除（设置 `deleted_at`） | 保留磁盘文件 |

### 执行流程

```
1. 前置校验
   ├── 用户是否存在
   ├── 是否最后一名 super_admin（禁止删除）
   ├── 是否已 disabled（建议先禁用再确认删除）
   ├── resource_strategy 参数合法性
   └── transfer 时 target_user_id 是否存在且不是自己

2. 处理 resource_metadata 资源（按 strategy）
   ├── transfer: UPDATE owner_id + 移动 agent 磁盘目录
   ├── delete: shutil.rmtree(agent_dir) + soft-delete metadata
   └── soft_delete: UPDATE deleted_at = now()
                        （保留磁盘文件）

3. 处理 visibility_applications
   ├── applicant_id = user: 自动 withdraw（标记 withdrawn）
   └── reviewed_by = user: SET NULL

4. 硬删除历史数据
   ├── DELETE FROM threads_meta WHERE user_id = ?
   ├── 删除磁盘 threads/{thread_id}/ 目录
   ├── DELETE FROM runs WHERE user_id = ?
   ├── DELETE FROM run_events WHERE user_id = ?
   └── DELETE FROM feedback WHERE user_id = ?

5. 清理磁盘文件
   ├── shutil.rmtree(users/{user_id}/agents/)
   ├── shutil.rmtree(users/{user_id}/agent-memory/)
   ├── shutil.rmtree(users/{user_id}/threads/)
   ├── unlink users/{user_id}/memory.json
   └── rmdir users/{user_id}/ （如空）

6. audit_logs: UPDATE actor_id = NULL WHERE actor_id = ?

7. 删除用户行
   ├── DELETE FROM users_ext WHERE id = ?
   └── DELETE FROM users WHERE id = ?

8. 登出所有会话：token_version += 1

9. 写审计日志
```

### 关键实现细节

#### 4.5.1 Agent 目录转移

```python
src = paths.user_agent_dir(old_user_id, agent_name)
dst = paths.user_agent_dir(target_user_id, agent_name)
dst.parent.mkdir(parents=True, exist_ok=True)
shutil.move(str(src), str(dst))
```

#### 4.5.2 Bulk SQL 操作

```python
# 软删除所有 resource_metadata（参考 department delete 模式）
await session.execute(
    sql_update(ResourceMetadata)
    .where(
        ResourceMetadata.owner_id == user_id,
        ResourceMetadata.deleted_at.is_(None),
    )
    .values(deleted_at=datetime.now(UTC))
)
```

#### 4.5.3 历史数据硬删除

```python
# 删除 thread_meta 及关联磁盘目录
threads = await session.execute(
    select(ThreadMetaRow).where(ThreadMetaRow.user_id == user_id)
)
for t in threads.scalars():
    shutil.rmtree(paths.thread_dir(user_id, t.id), ignore_errors=True)

await session.execute(delete(ThreadMetaRow).where(ThreadMetaRow.user_id == user_id))
```

#### 4.5.4 事务与错误处理

推荐做法：**磁盘清理 → DB 事务**（含 `resource_metadata`/`threads`/`runs`/`users_ext`/`users` 操作）。磁盘清理先执行，任何步骤失败整体回滚。磁盘清理失败时不自动回滚已完成的 DB 操作，而是记录告警（at-least-once 策略）。

### 安全考虑

| 场景 | 措施 |
|------|------|
| 最后一名 super_admin 被删 | 禁止删除（参考 `admin.py:415-423`） |
| 用户有活跃 JWT | `token_version += 1` 使所有 token 立即失效 |
| 并发操作 | 单事务执行 |
| 转移目标用户不存在 | 400 Bad Request |
| 转移目标就是被删用户自己 | 400 Bad Request |
| 转移时目标目录已存在同名 agent | 报错由管理员处理 |
