## 3. 执行顺序与完成条件

### 步骤 A：固定候选版本，建立证据清单

1. 记录分支、HEAD、工作区差异；保留用户已有改动。若验收过程中候选代码改变，记录变化并重跑受影响验证。
2. 检查 GitNexus 对当前工作区的绑定与索引新鲜度。符号修改前执行 impact；HIGH/CRITICAL 先报告，UNKNOWN 补充源码核实；不得用过期图谱作为修改安全性的证明。
3. 建立 M0、M1、M2、M7、M8 的 Gate 清单，逐项关联实现、测试、历史报告及其候选版本。任务票勾选和 commit 标题只作为定位线索。
4. 检查可用的隔离测试数据库、RAGFlow、模型和设备环境，避免输出凭据；环境异常按仓库要求使用 `make doctor` 核实。

**完成条件：** 每项 Gate 均有可复核证据或明确缺口；本轮候选版本和可执行验证范围已记录。

### 步骤 B：优先核实 M3 的硬前置

| 对象 | 最低复核内容 | 判定要点 |
| --- | --- | --- |
| M0-T0.1 | 统一迁移单头；fresh/existing 隔离数据库升级；资源、版本和快照数据保留 | 在临时数据库或备份副本验证，不能修改用户运行库 |
| M1 | 定位历史真实检索、Receipt、脱敏、断网及标准 lane 记录；检查此后相关路径变更 | 对受 M2 改动影响的链路补验；不能将同协议替代模型报告写成生产模型验收 |
| M2 Gate 2 | KB 创建、可见性、owner/caller 权限、生命周期、provider 绑定不外泄、依赖声明与校验 | 确认走 canonical Resource 治理；不以 M4 未实现为由扩展本轮范围 |
| M2 Gate 3 | 装配与检索双层限制、raw dataset ID 注入拒绝、shared Agent caller/owner 交叉、Workflow 和 Sub-Agent 不扩权 | 在隔离 dev RAGFlow 上执行两 KB×两用户的正反场景；记录实际调用与拒绝证据 |

补验使用隔离用户、KB 和数据集，记录本轮创建的准确标识。清理仅针对本轮临时资产；不删除现有测试账户、用户文档或历史证据。无可用真实环境时保留缺口，mock 通过不能覆盖真实环境 Gate。

M0-T0.2 的 Workflow V2 双数据库验证作为后续 M10 前置核对；PATCH-009 是否可关闭仍按 Ledger 的移除条件判断，不强行关闭。

**完成条件：** M3 硬前置逐项为 PASS、FAIL 或 INCOMPLETE，且每个非 PASS 都有原因和解除条件。

### 步骤 C：核实 M7/M8 合入状态与安全闭环

按 [Local Runtime 测试矩阵](../local-runtime/TEST_MATRIX.md) 补核：

- 配对→上线→断连→撤销→重连拒绝；签名任务、回执、重放拒绝、协议协商和会话有效性。
- Allowed Roots 读写边界；路径穿越、链接逃逸；Local DENY 优先与请求 hash 绑定 consent。
- Python 执行、超时、取消、子进程回收、artifact 授权上传及结果脱敏。
- 无设备／离线时工具不可见，运行目标冻结，撤权后重新校验，终态 Receipt 接入 Tool Receipt／Run Evidence。

分别标记单元／模拟协议测试、真实进程与连接验收、真实设备／目标 OS 验收。Linux 测试不得标成 Windows 实测。缺设备、凭据或 OS 环境时记录 INCOMPLETE。

**完成条件：** M7/M8 的实现与验收状态分别明确。其独立缺口进入设备线待办；仅当缺陷影响共享认证、持久化、运行证据或要求的合并验收时，才列为 M3 阻塞。

### 步骤 D：处理阻塞并完成候选版本验证

发现既有缺陷时先定位公开行为边界，执行 GitNexus impact，以一个聚焦回归证明 RED，再作最小修复并验证 GREEN。修复造成新影响时追加必要验证；超出短收口范围的修复形成具体阻塞，不在本轮扩建功能。

验证遵循仓库当前 lane 合约：

- 聚焦阶段只运行对应测试及最窄 lint/typecheck；新增或移动测试后运行 `python3 scripts/test_inventory.py`。
- 最终候选版本运行一次后端标准 lane，以及 `bash scripts/run-test-lane.sh pr-standard`。同一候选已由父 lane 执行的子 lane 记录一次即可，不为文档补写重复运行。
- 涉及前端变更时按仓库规定选择前端标准／完整 lane；本地客户端测试单独记录，不能假设后端 lane 自动包含它们。
- backend 命令在受限环境使用 `UV_CACHE_DIR=/tmp/deer-flow-uv-cache`；直接运行 lane 前执行对应 preflight，lane runner 自带则不重复。
- 不运行 release 级 `core-full`；真实模型、真实设备和断网验证独立记录。

每条验证记录命令、候选版本、日期、耗时、退出码和摘要。`pr-standard` 记录全部子 lane 摘要及父级 `TEST_LANE_DURATION`。超时记录最后观察到的用例，状态为 INCOMPLETE；socket 被限制时按仓库规则在允许本地 socket 的环境重跑相同 lane，不改代码绕过环境限制。

**完成条件：** 最终候选的要求验证全部有终态记录；失败和未执行项均已分类，不以历史通过替代当前结果。

### 步骤 E：同步文档并判定 M3 开工状态

报告使用以下状态：

- **READY**：M0-T0.1、M1/M2 的适用 Gate 与当前候选要求的验证均通过，可提交 M3 计划供确认。
- **NOT READY**：硬前置存在已确认失败，列出修复顺序。
- **UNVERIFIED**：硬前置因环境或证据缺失仍有 INCOMPLETE，列出补验条件。

文档同步只更新实际已证明的事实：

- 总方案保留 2026-09-08 历史基线，增加本次状态报告入口和最新里程碑状态。
- 知识实现清单／测试矩阵、Local Runtime 清单和已定位任务票更新状态或指向报告。区分“实现已合入”和“Gate 全通过”。
- Patch Ledger 巡检实际移除条件；不因本轮需要“收口”而关闭仍需保留的 patch。
- 对 D1/D4 并行安排和设备模块目录差异，记录实际情况、后续材料与建议。只有找到明确维护者决策依据才登记为已接受修订；仅凭任务票或实现不能擅自改写已接受决策。

**完成条件：** 报告具有明确的 M3 开工判定；文档间不再把已实现写成未开始，也不把待验收写成已完成。

### 步骤 F：制定下一阶段计划，汇报后等待确认

依据本轮结论编写下一阶段文件：

- READY 时，计划以 M3 文档管理与 Knowledge Center 为主体：canonical API 子资源、管理侧 provider 适配、校验/hash/存储/上传/解析索引状态、真实列表详情、检索预算及 features 状态。
- 明确“创建→上传→解析→索引→授权检索→删除草稿文档”的验收闭环，并覆盖越权、非法文件、超限、provider 不可达、失败恢复与脱敏。
- 从当前实现和专项方案提取接口、数据模型、任务阻塞关系及测试要求；前端通过平台 API 获取知识数据。
- M4 不可变 Revision、M5 知识证据、M6 Eval 作为后续顺序；M9 并行作为待确认取舍，不提前执行。
- NOT READY／UNVERIFIED 时，下一阶段文件先列解除阻塞的工作，M3 实施保持被阻塞状态。

最终汇报包括：修改文件与用途、当前候选、完成的 Gate、各类测试结果、遗留缺口、M3 判定、下一阶段建议和需要用户确认的具体事项。

**停止条件：** 汇报与计划交付后等待用户确认，不自动创建 M3 实现分支、编写 M3 代码或启动下一阶段验收。
