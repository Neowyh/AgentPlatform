# 芯片软件开发包提取需求规格

> 状态：需求已确认，尚未实施
> 日期：2026-09-01

## Problem Statement

嵌入式开发者拿到一组芯片原厂资料后，需要快速获得可用于开始软件开发的可靠知识。目前 iDeer 可以读取并摘要文档，但没有芯片领域的文档集校验、结构化抽取、来源证据、封装消歧和不确定性治理。因此，用户无法把通用摘要作为时钟、启动、引脚复用、外设、中断或勘误分析的可信起点。

## Solution

提供一个可发现、可复用的“芯片软件开发包提取”专业 Skill，并允许由 Expert 编排执行。它以同一芯片型号、同一封装的 Chip software source set 为输入，生成 Chip software development package：

- 一份带文档名、章节或页码证据的 Markdown Embedded software knowledge brief；
- 一份受控结构化附表，供人工核验和后续自动化使用；
- 每项结论都带 Evidence status：`confirmed` 或 `review_required`。后者必须保留、显著标注“需人工复核”，但不得被下游自动化当作确定事实。

Skill 的最高测试接缝是一次用户可调用的 Skill 运行：给定合格文档集，运行对外产出两份可下载工件及可观察的证据状态；测试不依赖具体 PDF 转换器、提示词或模型内部调用顺序。

## User Stories

1. 作为嵌入式开发者，我想提交同一型号和封装的原厂文档集，以便获得与我的目标芯片一致的开发知识。
2. 作为嵌入式开发者，我想声明目标型号和封装，以便系统不会把其他封装或同系列型号的结论混入结果。
3. 作为嵌入式开发者，我想提交 datasheet、Reference Manual 或 Programming Manual 和勘误表，以便同时获得规格、寄存器级信息和已知问题。
4. 作为嵌入式开发者，我想在缺少某一类文档时收到明确缺口，以便补齐资料而非相信推测结果。
5. 作为嵌入式开发者，我想获得启动、复位和启动模式知识，以便建立正确的软件启动前提。
6. 作为嵌入式开发者，我想获得时钟源、时钟树和相关限制，以便配置系统时钟。
7. 作为嵌入式开发者，我想获得存储器布局、启动介质和地址空间信息，以便组织启动代码、链接脚本和存储访问。
8. 作为嵌入式开发者，我想获得指定封装的引脚、复用功能和关联外设，以便核对软件的引脚复用配置。
9. 作为嵌入式开发者，我想获得外设、寄存器入口、中断和 DMA 的开发前提，以便定位应阅读和配置的原厂章节。
10. 作为嵌入式开发者，我想看到勘误表对启动、时钟、外设和中断的影响，以便避免实现已知错误的初始化流程。
11. 作为嵌入式开发者，我想让每项关键结论链接到文档、章节或页码，以便能回到原厂资料复核。
12. 作为嵌入式开发者，我想看到 `confirmed` 与 `review_required` 的明确状态，以便知道哪些内容可作为可靠输入。
13. 作为嵌入式开发者，我想保留所有需人工复核的信息，以便在不确定处作出自己的工程判断。
14. 作为嵌入式开发者，我不想让缺失、冲突或跨封装的内容被自动补猜为确定事实，以便避免板级或固件风险。
15. 作为后续自动化的使用者，我想消费受控结构化附表，以便仅使用 `confirmed` 字段构建下一步工具链。
16. 作为审查者，我想在附表中看到引脚、信号、复用功能、外设、中断、来源和置信状态，以便快速审计抽取结果。
17. 作为平台管理员，我想让该能力遵守现有资源发布、可见性、运行快照和工具组授权规则，以便共享使用不越权。
18. 作为内网部署者，我想让该能力使用已打包的解析与 Skill 资产，以便不依赖运行时的外网服务。
19. 作为产品维护者，我想用含多封装、冲突勘误和复杂表格的脱敏样本回归验证，以便防止能力在升级后失真。
20. 作为嵌入式开发者，我不希望系统直接生成可上板的应用初始化代码，以便先补足开发板连接、晶振、电源和 SDK/HAL 等外部前提。

## Implementation Decisions

- 将“芯片软件开发包提取”作为专业 Skill 发布，并由可选 Expert 提供任务编排；它不是一段临时提示词，也不取代通用文档阅读能力。
- 输入仅接受原生文本 PDF 的 Chip software source set：同型号、同封装的 datasheet、Reference Manual 或 Programming Manual，以及适用的 errata。扫描件 OCR、混合型号和多封装合并不纳入首期保证范围。
- 复用现有文档读取能力、文件权限、工件交付、Skill/Agent 资源治理和离线资产打包；新能力只在其上增加领域抽取与验证，不重建通用文件系统或资源目录。
- 在现有工具组授权模型下运行，至少需要文档读取和受控文件输出；运行时有效工具集继续受资源声明、调用者权限和平台策略的交集限制。
- 提供一个领域抽取边界，输入为已验证的文档集和目标型号/封装，输出为知识条目、结构化附表、资料缺口和工件清单。该边界负责字段规范化、证据绑定、冲突检测和 Evidence status，不让这些规则散落在 Agent 提示词中。
- Markdown 简报至少覆盖：资料身份与覆盖范围、启动与复位、时钟、存储器、引脚复用、外设、寄存器查阅入口、中断、DMA、勘误影响、资料缺口和人工复核项。
- 结构化附表至少包含：`pin`、`signal`、`alternate_function`、`peripheral`、`interrupt`、`source`、`confidence`。可补充封装、页码/章节、寄存器入口和冲突说明，但不以未证实字段填充空值。
- `confirmed` 仅用于可由一致原厂资料直接支持、并具备文档和章节或页码证据的条目；发现适用勘误冲突时不得标为 `confirmed`。
- `review_required` 用于跨页合并、表格结构不确定、文档冲突、资料不完整或无法确定封装/型号的条目。该状态必须保留在两份工件中并显示“需人工复核”。
- 缺少板级晶振、供电、外设连接、启动外围电路、SDK/HAL 版本等不属于芯片文档集的前提时，记录为资料缺口；不得由 Skill 生成或暗示可直接上板的初始化代码。
- 知识包作为一次运行的可下载工件交付，并由现有线程/运行工件访问控制保护。后续自动化只能消费 `confirmed` 的结构化条目。
- 不新增此阶段的 ADR：该需求定义可通过资源版本和 Skill 内容迭代，尚未形成难以逆转的基础设施取舍。

## Testing Decisions

- 最高层行为测试：执行该专业 Skill，验证它针对合格文档集产出 Markdown 简报和结构化附表；检查每个关键条目有来源且具有允许的 Evidence status。测试只断言用户可见的工件、字段和状态，不断言具体模型回复、提示词或转换函数调用。
- 使用现有文档阅读工具测试作为文件格式、虚拟路径、页码范围、大小限制和拒绝路径的回归基础；专业 Skill 测试不重复这些底层实现细节。
- 使用现有资源发布/运行快照测试作为专用 Skill 的可见性、版本固定和工具组权限回归基础。
- 使用现有工件 API 测试作为生成简报和附表的可下载性、线程隔离和访问授权回归基础。
- 新增脱敏固定样本：单封装正常文档集、多封装混杂资料、datasheet 缺 Reference Manual、勘误与参考手册冲突、跨页引脚表和无法解析的复杂表格。
- 对每个样本断言外部结果：明确的资料缺口；不混用型号/封装；证据定位存在；冲突和不确定内容为 `review_required`；只有直接支持且一致的内容可为 `confirmed`。
- 代码变更遵循 TDD：先在“Skill 一次运行产出知识包”的接缝写一个红色行为测试，再最小实现并运行相应后端标准测试；涉及资源、Agent、Skill 或 Workflow 时追加 `pr-standard`。

## Out of Scope

- 扫描 PDF、图片或 OCR 优先的手册解析。
- 多型号、多封装自动合并或猜测目标型号/封装。
- 从非原厂网页、论坛或无版本控制的片段补充事实。
- 代替原厂资料、硬件原理图、PCB 数据库或硬件设计审查。
- 自动生成可上板的业务固件、完整初始化代码、链接脚本或驱动实现。
- 推断开发板晶振、电源、外设连线、启动电路或 SDK/HAL 版本。
- 把 `review_required` 或资料缺口内容提供给下游自动代码生成。

## Further Notes

- 当前平台已经具有文档读取、页码范围读取、受限文件访问、可配置工具组和工件交付能力；本需求的核心增量是芯片领域的语义抽取与可证明的质量门禁。
- 现有文档读取输出存在字符上限，因此实现必须按资料结构分段读取和提取，不能假设整本手册会一次性进入模型上下文。
- 交付前应选取一个可公开或脱敏的 MCU/SoC 文档集作为验收基准，并事先人工标注少量期望的 `confirmed` 与 `review_required` 条目。
