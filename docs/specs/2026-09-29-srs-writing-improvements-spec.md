# srs-writing 智能体与 Skill 改进

## Problem Statement

使用「软件需求规格编写专家」完成一次 SRS 编制的用户，会在多个环节遇到断点：

- 审阅阶段被指引"运行离线校验器脚本"，但该脚本不在 skill 包内、智能体运行环境不可达，用户和智能体都无法执行这条指令——产物质量检查环节形同虚设。
- 文档生成工具的位置被硬编码为一种部署形态，本地安装形态下按图索骥会失败；生成失败虽有回退说明，但缺少统一的探测步骤。
- 本地一键安装器默认打开宿主机 bash 授权，静默扩大智能体的权限面；安装器路径与官方 bundled 分发路径行为不一致。
- 逐条确认需求只能在聊天框打字回复，表述稍有偏差就得不到预期处理；大任务书逐条确认非常耗时。
- 生成的 Word 文档没有排版自检环节，表格断裂、样式问题要等用户打开文件才发现。
- 进度文件放在按用户共享的输出目录里，同一用户并行处理两份任务书会互相覆盖进度。

## Solution

- 离线校验器随 skill 包一起分发，智能体在审阅阶段自行运行并解读结果：错误项拦截交付、警告项提示用户。
- 文档生成工具改为运行时自动探测，兼容容器挂载与本地安装两种形态；探测失败按统一失败契约明确报告，并回退到需求目录供人工整编。
- 官方分发只走 Bundled resource seed；本地安装器降级为旧体系本地开发工具，宿主机 bash 默认关闭、显式开启并提示风险。
- 逐条确认改为结构化选择卡片（采纳/修改/拒绝 + 修改意见输入），支持批量多选与按章节分批确认，保留自由文本回退。
- 文档生成后强制视觉自检（布局诊断 + 渲染抽查），问题修复后再交付。
- 产物与进度文件迁入按任务书命名的独立子目录，恢复规则限定同线程同任务书。
- 校验器规则增强：模糊措辞警告、已采纳需求双向出现断言、需求目录一致性、完成态无未决条目。

## User Stories

1. 作为上传任务书的业务用户，我希望智能体在审阅阶段自动运行产物校验并解读结果，以便我不用自己去跑一个我无法访问的脚本。
2. 作为业务用户，我希望校验失败时得到具体失败项清单，以便我准确知道需要补确认或修复什么。
3. 作为业务用户，我希望生成的 Word 文档在交付前经过排版自检（表格完整性、样式问题），以便拿到的文档直接可用而不是表格断裂。
4. 作为业务用户，我希望文档生成工具不可用时得到明确失败说明和需求目录回退方案，以便我可以人工整编而不是收到空文件。
5. 作为业务用户，我希望逐条确认需求时通过选择卡片（采纳/修改/拒绝）操作，以便不依赖在聊天框里精确打字。
6. 作为业务用户，我希望修改需求时在卡片里直接填写修改意见，以便一次性表达完整意图。
7. 作为业务用户，我希望批量操作通过多选卡片完成并在执行前确认一次，以便大批量场景下高效且不误操作。
8. 作为业务用户，我希望大任务书可以按章节分批确认，以便不必一次面对几十条需求。
9. 作为业务用户，我希望确认过程始终标注进度（已确认 x/N 个功能项），以便我知道还剩多少工作。
10. 作为业务用户，我希望中断后回到同一线程能恢复到上次决策的位置，以便不重复已完成的确认。
11. 作为并行处理两份任务书的业务用户，我希望两个任务的进度互不覆盖，以便双会话并行互不干扰。
12. 作为业务用户，我希望含"及时/适当/高效/尽量"等模糊词的已采纳需求被标记警告，以便交付的需求可验证。
13. 作为业务用户，我希望被拒绝的需求不出现在正文与矩阵但保留在需求目录中，以便追溯决策历史。
14. 作为部署运维的管理员，我希望官方分发只走 Bundled resource seed，以便升级路径单一可预测。
15. 作为本地部署的管理员，我希望宿主机 bash 默认关闭、开启时显式选择并看到风险提示，以便不无意扩大智能体权限。
16. 作为管理员，我希望文档生成工具的位置被自动探测而非硬编码，以便容器与本地两种部署形态都能工作。
17. 作为智能体维护者，我希望离线校验器随 skill 包分发，以便校验规则与 skill 内容同版本演进。
18. 作为智能体维护者，我希望校验器区分错误与警告，以便致命问题拦截交付、措辞问题不阻塞。
19. 作为智能体维护者，我希望每条已采纳需求都能在正文与矩阵文档文本中被找到，以便双向追踪闭环可被机器验证。
20. 作为智能体维护者，我希望需求目录与进度状态一致、生成完成态无未决条目，以便产物集合自洽。
21. 作为测试/验收人员，我希望有 requires_llm 标记的端到端验收用例覆盖六阶段流程，以便真实模型行为被回归验证。
22. 作为测试/验收人员，我希望离线冒烟覆盖按任务书隔离的嵌套输出布局，以便不依赖真实模型也能验证流程接线。
23. 作为维护者，我希望"为何暂不做平台级 Result Contract"被记录为 ADR，以便后续读者理解该权衡并知道何时重评。
24. 作为维护者，我希望 Result Contract 后续立项登记进 backlog，以便该工作不被遗忘。

## Implementation Decisions

- 离线校验器脚本移入 srs-writing skill 包内（skill 目录整体以只读视图挂载进智能体运行环境），审阅阶段由智能体用 bash 自行运行并解读结果；错误影响退出码，警告不影响。
- officecli 在生成前用 `command -v` 探测，兼容容器挂载与本地用户目录两种形态，移除对固定绝对路径的依赖；探测失败走既有 `FAILED:` 失败契约并回退需求目录人工整编。
- 官方分发仅走 Bundled resource seed；安装器定位降级为旧体系本地开发工具：宿主机 bash 默认关闭，新增显式开启参数，开启时输出"授权智能体在宿主机执行任意命令"的风险提示。
- 确认交互结构化：逐功能项一张 ask_clarification fields 表单（每条需求一个 select：采纳/修改/拒绝；修改配 textarea；批量操作用 multi_select），保留自由文本回退路径；智能体人设文件（SOUL.md）的决策协议做最小同步。
- 文档生成完成后强制执行 officecli 布局诊断与 HTML 渲染抽查，发现问题修复后复查（对齐 officecli skill 的自检约定）。
- 校验器新增规则：歧义词 lint（命中已采纳需求描述 → warning）；已采纳需求 ID 必须出现在 SRS 正文与追踪矩阵文档文本中（error，补齐现有"拒绝项不泄漏"单向检查的反向）；需求目录文件存在且 ID 集合与进度状态一致（error）；生成阶段完成态不得残留未决条目（error）。
- 产物与进度文件迁入 `/mnt/user-data/outputs/` 下按任务书名规范化的子目录；恢复规则改为"同线程 + 同任务书子目录存在未完成进度文件才恢复"；校验器兼容嵌套目录。
- 分批确认策略：按章节分批、低风险批量/高风险逐条，与结构化表单衔接。
- 平台级 SRS Result Contract 暂缓：fault-zeroing 已确立"Skill 文本当校验器"为反模式、平台级版本化契约为正例；本轮以 skill 内校验器保底，写一条 ADR 记录权衡与重评触发条件，并在 backlog 登记立项条目。ADR 与 backlog 条目在实施阶段随代码变更一并提交。
- 容器沙箱为正式部署形态；本 spec 全程不触碰 backend/frontend 产品代码。

## Testing Decisions

- 好测试只测外部行为：CLI 退出码与输出、产物文件是否存在及内容断言、HTTP API 响应与 Artifact；不测 prompt 措辞与内部实现。
- 三个测试 seam 全部复用现有 seam（零新增），已与需求方确认：
  1. 校验器 CLI：对校验脚本以子进程方式断言退出码与输出（先例：现有的校验器单元测试）。
  2. 离线冒烟：现有离线冒烟脚本模拟六阶段流程并调用校验器，扩展覆盖按任务书隔离的嵌套输出布局。
  3. 网关 HTTP API：requires_llm 标记的真实模型端到端测试，API 驱动 4~5 轮脚本化对话（映射确认 → 全部采纳 → 生成 → 校验），断言阶段流转、进度文件更新、产物生成、校验器在挂载路径下 exit 0、拒绝项不泄漏（先例：现有集成 API live 测试）。
- 安装器变更不建新测试 seam，用其自带 dry-run / verify-only 模式的输出验证。
- 新增或移动测试后运行测试清单脚本（test_inventory）。
- 验证通道分级报告：聚焦单测 → 离线冒烟 → 标准通道（backend make test）→ 真实模型验收（backend make test-llm，本轮必跑；LLM 凭据已确认配置，若执行时挂起/超时按协议报告 incomplete，不得报 passed）。

## Out of Scope

- 平台级 SRS Result Contract 的实现（涉及 Run 生命周期与后端代码，仅立项，见 ADR）。
- 需求类型扩展开关（可靠性/维修性/保障性/设计约束等）。
- 需求↔测试用例追踪层级（当前保持功能↔需求两级）。
- 智能体模型配置（model_settings 低温等）。
- 一切 backend/frontend 产品代码改动；前端表单卡片复用既有 Human Input Card 渲染，不做新交互开发。
- GitHub issue 发布（本仓库约定：本地 spec 文件即发布物）。

## Further Notes

- 本 spec 即需求澄清（Q1-B）确定的正式需求文档，取代此前被驳回的内联实施计划作为范围基准。
- 范围由一次 grilling 式需求澄清收敛：产出物（实施+文档）、验收基准（必做一次真实模型 test-llm）、部署形态（容器沙箱为正式、安装器降级）、校验架构（本轮快修 + Result Contract 立项）、P1 五项全做、文档落点、测试 seam 方案。
- bundled skill 源变更后，存量开发库需刷新（override 策略重 seed 或删除该资源后重启网关）才能生效。
- 术语遵循仓库 CONTEXT.md 词汇表：Agent（用户侧称 Expert）、Skill、Run、Thread、Bundled resource seed；Result Contract 沿用 fault-zeroing 先例术语。
- 后续可由 to-tickets 将本 spec 拆解为实施工单。
