# 归零智能体建设进展汇报

---

## 一、前期建设进程

### 1.1 调研工作

#### 1.1.1 归零智能体案例调研

项目组对国内外归零排故领域的智能化实践进行了系统调研，重点考察了以下方向：

- **航天领域归零实践**：梳理了航天型号质量问题归零的标准流程（问题定位→机理分析→措施制定→举一反三），形成了智能体工作流设计的基础框架。
- **AI辅助故障分析案例**：调研了大语言模型在故障诊断、根因分析领域的应用案例，评估了LLM在证据提取、逻辑推理和报告生成方面的能力边界。
- **智能体架构模式**：研究了多智能体协作架构在复杂分析任务中的应用模式，确定了"主智能体调度+专业子智能体分工"的技术路线。

#### 1.1.2 归零问题调研

针对归零分析任务的特殊性，项目组深入调研了以下关键问题：

- **证据处理难点**：归零分析涉及多源异构资料（问题描述、日志、试验记录、设计文档、历史案例），需要智能体具备跨文档证据抽取和关联能力。
- **逻辑严谨性要求**：归零报告要求每个结论必须绑定证据来源，证据不足时需明确标记"待验证"，不能凭空推断。
- **行业规范约束**：归零报告需遵循结构化模板（问题概述、故障树分析、底事件评估、根因归因、验证计划等），输出格式有严格要求。

### 1.2 平台与模型选型

#### 平台选型

经过综合评估，项目组选择基于 **iDeer（Deep Exploration and Efficient Research Flow）** 开源超级智能体框架进行建设。该平台由字节跳动开源，具备以下核心优势：

| 能力维度 | 平台特性 | 对归零分析的支撑 |
|---------|---------|----------------|
| 多智能体编排 | 支持custom agent、subagents配置 | 可定义归零专用智能体和5类子智能体 |
| Skill系统 | 模块化Markdown工作流 | 可固化归零排故8阶段执行流程 |
| 文件处理 | sandbox工具（glob/grep/read/write） | 支持多源资料读取和产物生成 |
| 知识管理 | 文件型知识源 + 外部RAG集成 | PoC阶段用文件源，后续可扩展向量库 |
| 产物展示 | artifacts + present_files | 支持报告和可视化产物的交互展示 |

#### 模型选型

- **基座模型**：采用大语言模型作为推理引擎，支持上下文窗口足以处理完整故障资料包。
- **模型能力要求**：具备跨文档证据抽取、逻辑推理、结构化报告生成能力。
- **后续规划**：预留模型升级接口，中期可接入更强推理模型或领域微调模型。

### 1.3 智能体与Skill开发

#### 1.3.1 归零排故智能体（fault-zeroing agent）

完成了归零排故智能体的完整配置，包括：

- **智能体身份定义**（`SOUL.md`）：明确智能体为"归零排故智能体"，定义了6条工作原则和8个固定执行阶段。
- **工作原则**：
  1. 先读取用户输入、上传资料和目录结构，再形成分析结论
  2. 不得凭空给出底事件概率、根因判断或验证结果
  3. 每个关键结论必须绑定证据来源；证据不足时标记"待验证"
  4. 明确区分事实、推断、假设和验证建议
  5. 对冲突证据保留双方来源，不强行合并
  6. 输出报告前必须检查章节完整性和证据闭环

#### 1.3.2 归零排故Skill

开发了完整的归零排故Skill（`skills/custom/fault-zeroing/SKILL.md`），包含：

- **输入资料读取规则**：8条规则，涵盖资料优先级、目录扫描、长文档分段读取、缺失资料处理等。
- **固定执行阶段**：8个阶段严格顺序执行——资料盘点→证据台账→故障树构建→底事件评估→根因归因→验证计划→报告生成→报告审查。
- **证据处理规则**：定义了证据等级（A/B/C/D）、证据台账字段、证据引用规范。
- **故障树构建规则**：顶事件来源、中间事件逻辑、底事件可验证性要求。
- **子智能体协作规则**：5类子智能体职责边界和协作约束。
- **输出规则**：五件套输出要求和自检清单。

#### 1.3.3 子智能体体系

设计并配置了5类专业子智能体：

| 子智能体 | 职责 | 工具 |
|---------|------|------|
| evidence-reader | 读取资料、抽取关键证据、标注文件和行号 | glob、grep、read_file |
| fault-tree-builder | 根据顶事件和证据构建故障树 | read_file、write_file |
| probability-assessor | 评估底事件概率、置信度和验证状态 | read_file、write_file |
| root-cause-analyst | 综合底事件概率和证据强度形成归因 | read_file、write_file |
| report-reviewer | 检查报告章节、证据引用和待验证项 | read_file、write_file |

职责边界约束：evidence-reader不输出根因，fault-tree-builder不给最终归因，report-reviewer不新增技术结论。

### 1.4 知识库构建

#### 1.4.1 PoC阶段知识源方案

```
  fault_tree.json                # 故障树JSON
  fault_tree.svg                 # 故障树可视化

  analysis_process.svg           # 分析过程可视化

```

#### 1.4.2 输出模板体系

已完成全套输出模板开发：

- **故障树JSON模板**（`fault_tree.json`）：定义了顶事件、中间事件、底事件、逻辑关系的完整结构，符合JSON Schema规范。
- **故障树JSON Schema**（`fault_tree.schema.json`）：用于校验故障树JSON的结构完整性。
- **底事件评估表模板**（`bottom_event_assessment.md`）：包含底事件、证据、概率判断、置信度、验证状态、后续动作等字段。
- **归零报告模板**（`zeroing_report.md`）：10章节结构化模板，包含资料覆盖矩阵、证据台账摘要、待验证项和遗留风险。
- **证据规则参考**（`evidence_rules.md`）：定义证据等级和引用规范。

## 二、未来工作流程设想

### 2.1 新发质量问题归零分析流程

当新发生需归零的质量问题时，依托该平台进行智能体归零分析的工作流程如下：

#### 第一步：问题录入与资料上传

- 用户在iDeer平台选择"归零排故智能体"
- 上传问题描述、相关日志、试验记录、设计文档等资料
- 智能体自动识别资料类型并建立资料清单

#### 第二步：智能体自动分析

智能体按8个固定阶段顺序执行：

1. **资料盘点**：自动扫描上传目录，输出已读取、未读取和缺失资料清单，形成资料覆盖矩阵。
2. **证据台账**：从多源资料中抽取关键证据，标注证据等级（A/B/C/D）、来源、支撑结论和反证对象。
3. **故障树构建**：基于证据台账构建故障树，包含顶事件、中间事件、底事件和逻辑关系。
4. **底事件评估**：逐项评估证据强度、机理一致性、反证情况和复现实验情况，形成概率判断和置信度。
5. **根因归因**：综合底事件评估结果，形成根因归因结论，只允许A/B级证据支撑闭环根因。
6. **验证计划**：为所有待验证底事件、冲突证据和低置信根因生成验证项。
7. **报告生成**：生成五件套输出（fault_tree.json、fault_tree.svg、bottom_event_assessment.md、analysis_process.svg、zeroing_report.md）。
8. **报告审查**：自检报告结构完整性、证据闭环、过度归因、SVG安全性和遗留风险。

#### 第三步：人工审查与交互

- 智能体展示五件套产物，供人工审查
- 用户可针对特定底事件或根因结论追问证据来源
- 智能体补充证据或调整结论
- 用户确认后输出最终归零报告

#### 第四步：报告导出与归档

- 导出Markdown格式归零报告
- 可扩展支持Word/PDF格式
- 报告归档至知识库，供后续案例检索

### 2.2 预期效果

| 效果维度 | 具体表现 |
|---------|---------|
| 分析效率 | 将传统数天的人工归零分析缩短至小时级 |
| 证据追溯 | 每个结论绑定证据来源，支持行号级追溯 |
| 逻辑严谨 | 强制8阶段顺序执行，避免跳步和先写结论再补证据 |
| 知识积累 | 每次归零分析的产物可纳入知识库，形成组织知识资产 |
| 标准化输出 | 统一报告格式和质量标准，减少人为差异 |
