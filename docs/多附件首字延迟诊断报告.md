# 多附件对话首字延迟诊断报告

## 当前结论

本工作区已把测量口径改为“本次流中的助手正文增量”。脚本会忽略用户、系统、空片段、工具结果和不同 `run_id` 的事件，并单独记录首个 SSE、首个工具事件、流错误和首个助手正文。本地数据库中能看到一组探索性运行（`lead_agent`，0/1/5/10 文件）；5 文件样本为 error，其余为 success，单次运行约 4–19 秒。这些线程不是用户标识的业务智能体，且数据库没有模型首增量时间，因此本报告不宣称已经复现现场 1–2 分钟等待，也不把历史 102–756 ms 结果当作 TTFT。

当前脱敏配置指纹：`config_version=41`；`lead_agent` 默认模型为 `deepseek-v4-flash`；`fault-zeroing` 配置为继承父 Agent 模型。知识库工具启用，但地址、数据集和凭据不写入报告。代码基线为 `ca65c577`，工作区存在未提交改动。

## 可复现实验

生成合法的合成 PDF/DOCX/XLSX/TXT/MD 夹具：

```bash
python scripts/benchmark/generate_fixtures.py /tmp/agentplatform-ttft-fixtures
```

对已启动且已配置真实模型的网关，使用新线程运行交错的数量基线（0/1/5/10/20）：

```bash
python scripts/benchmark/multi_attachment_ttft.py \
  --thread-id <NEW_THREAD_ID> --assistant-id <BUSINESS_AGENT> \
  --fixture-dir /tmp/agentplatform-ttft-fixtures \
  --count 0 --count 1 --count 5 --count 10 --count 20 \
  --header 'Authorization=Bearer <REDACTED>' \
  --output dev-log/ttft-<timestamp>.json
```

每次运行必须使用新线程；多轮复用另建专用线程。保存输出 JSON 和对应的服务日志摘要，不覆盖既有样本。脚本结果中的 `run_to_first_token_ms` 仍是网关流到达时间；浏览器“首次显示本次助手正文”需要 Playwright 或前端性能标记配对记录。HTTP 200 但 `stream_error=true` 的样本计为失败。

完成至少 5 次有效样本后，用以下命令生成按文件数分组的中位数、范围和失败数：

```bash
python scripts/benchmark/summarize_ttft.py dev-log/ttft-<timestamp>.json
```

## 阶段与归因

上传响应返回 `trace_id`，网关日志以同一 ID 记录附件数量、大小、类型、逐文件转换耗时、Sandbox 准备/同步耗时。Run preparation 记录依赖解析、Snapshot（现已在快照函数返回后立即结束）、知识准备和 preparation 总时长；运行日志记录模型边界的 TTFT。阶段在同一进程使用单调时钟计算；并行阶段只能按关键路径归因，不能简单相加。

模型 HTTP 发出仍需通过模型客户端回调或网关出口日志记录；浏览器侧已在 `useThreadStream` 写入 `deerflow:send:<trace_id>` 和首个新助手正文的 `deerflow:display:<trace_id>` Performance marks/measure。两端应使用 `trace_id`、`run_id`、消息 ID 对齐；不要把单个 SSE 首事件当作模型首字。

## 候选因素与现状

| 因素 | 当前判定 | 下一步单变量实验 |
| --- | --- | --- |
| 点击后上传/转换 | 证据不足 | 立即发送与预处理完成后发送配对 |
| 文件数、大小、格式 | 证据不足 | 固定总字节改变文件数，再固定文件数改变大小；扫描 PDF 单独标注 |
| Sandbox 同步/事件循环 | 有埋点，未归因 | 查看逐文件同步和事件循环延迟；确认 20 文件是否支持分批 |
| Snapshot/依赖/知识/Memory | 有阶段日志，未归因 | 冷启动、预热、同 Agent 首轮/后续轮各至少 5 次 |
| 模型调用与 Prompt | 仅有运行级时间 | 记录首正文前所有调用、输入 token、重试和模型边界时间 |
| 工具/多 Agent 编排 | 未确认 | 记录首正文前节点，区分隐藏输出与正文 |
| SSE/代理/浏览器缓冲 | 未确认 | 网关直连、实际代理、浏览器显示三路配对 |

在获得真实慢样本前，所有因素均为未确认；不能据此宣称优化收益。每个关键条件至少 5 次有效测量，波动显著的条件扩展到 20 次，并报告中位数、范围和失败率。

## 方案边界

现有上传并行同步和前端预上传改动必须在真实业务智能体、权限、Skill、知识库、Sandbox 和代理路径下重新测量。任何缓存、并发或禁用模块的收益都只能作为带约束的诊断对照；上线前须验证附件可访问性、授权、业务语义、缓存失效和回滚。

## 实施方案清单

| 方案 | 修改位置 | 收益如何确认 | 约束与回滚 |
| --- | --- | --- | --- |
| 上传阶段异步化并限制并发 | `backend/app/gateway/routers/uploads.py` | 对同一文件集合比较 Sandbox 同步关键路径；报告中位数、范围和失败率 | 远端 Sandbox 吞吐、配额和顺序语义可能限制收益；通过恢复串行同步回滚 |
| 选择文件后预上传/预转换 | `frontend/src/components/workspace/input-box.tsx`、`frontend/src/core/threads/hooks.ts` | 比较“立即发送”和“预处理完成后发送”的点击后关键路径；检查附件授权和可访问性 | 预上传失败必须在发送前重试或显式失败；移除预上传调用即可回滚 |
| 精确阶段与跨端关联 | `trace_context.py`、Gateway 日志、`useThreadStream` Performance marks | 用 `trace_id`、`run_id`、消息 ID 对齐 T0/T15/T16；验证浏览器显示晚于上游正文的缓冲量 | 不记录凭据、Prompt 或完整正文；删除观测输出不改变业务语义 |
| Snapshot 计时边界修正 | `backend/app/gateway/run_preparation.py` | 回归测试中的延迟元数据不得计入 `snapshot_freeze_ms` | 仅影响指标定义；若日志解析依赖旧口径，需同步迁移报表 |

目前没有任何方案可填写收益区间：真实业务 Agent、模型、附件集合和代理路径尚未在本环境运行。只有完成配对实验后，才可给出绝对耗时、关键路径占比、缓存失效条件和发布建议。
