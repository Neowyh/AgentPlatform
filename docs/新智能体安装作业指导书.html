全新智能体配置开发作业指导书

适用于 iDeer 本地验证环境。按本文操作，可以从 0 准备配置文件、编写智能体模板、安装到指定用户账号，并确认它能在页面中看到、能正常调用。

一、作业目标

完成一个全新智能体的配置开发全流程：准备基础配置、编写智能体文件、按需编写 Skill 和子智能体、安装到用户运行目录、启动服务并验收。

本指导书默认你已经在项目根目录操作： 
cd /home/wangyh/workspace/ideer

如果目录不对，后面的命令可能找不到文件。

二、先准备这些信息

目标用户 ID

智能体安装给哪个用户，就要使用哪个用户 ID。

示例：7c5af71e-0069-4712-bf16-c54cd35639aa

智能体名称

用英文小写、数字和横线，例如 quality-reviewer。名称要和智能体配置里的 name 一致。

Skill 名称

如果智能体需要固定流程或模板，准备一个 Skill 名称，例如 quality-review。不需要 Skill 时可以跳过。

是否需要子智能体

如果要拆成多个角色处理任务，例如“资料读取员”“报告审查员”，就需要准备 subagents.yaml。

三、配置文件清单

先看清哪些文件是基础运行必需，哪些是开发某类智能体时才需要。

文件 是否必需 模板或示例位置 用途
config.yaml 必需 config.example.yaml 应用主配置。模型、工具组、Skill 路径、数据库、subagents 都从这里生效。
.env 必需 .env.example 放 API Key、数据库地址等本地密钥。不要提交。
frontend/.env 必需 frontend/.env.example 前端本地配置。本地用 localhost:2026 时通常不用改。
extensions_config.json 按需 extensions_config.example.json 接 MCP 服务或控制 Skill 启用状态时使用。普通本地验证可不创建。
docs/<agent-name>/agent/config.yaml 必需 本指导书提供通用模板；示例见 docs/fault-zeroing-agent/agent/config.yaml 单个智能体的名称、描述、工具权限和 Skill 白名单。
docs/<agent-name>/agent/SOUL.md 必需 本指导书提供通用模板；示例见 docs/fault-zeroing-agent/agent/SOUL.md 定义智能体身份、工作原则、输入输出要求和禁止事项。
skills/custom/<skill-name>/SKILL.md 按需 本指导书提供通用模板；示例见 skills/custom/fault-zeroing/SKILL.md 固化专业流程、规则和报告模板。
docs/<agent-name>/subagents.yaml 按需 本指导书提供通用模板；示例见 docs/fault-zeroing-agent/subagents.yaml 定义 task 可调用的 custom subagents。
不要把模板和实际配置混在一起：

config.example.yaml、.env.example 只是模板；真正运行时读取的是 config.yaml、.env、frontend/.env。

四、准备基础运行配置

这一步是让 iDeer 本身能运行。先做它，再开发智能体。

1生成基础配置文件

如果没有 config.yaml、.env、frontend/.env，运行：

make config

如果已经有这些文件，不要覆盖，先备份主配置：

cp config.yaml config.yaml.bak-before-agent

2检查基础文件是否齐全

ls config.yaml
ls .env
ls frontend/.env

三条命令都能看到对应文件名，才继续。

3填写模型密钥

打开 config.yaml，确认 models: 下面至少有一个可用模型。模型里如果写了 api_key: $OPENAI_API_KEY，就在 .env 里填写：

OPENAI_API_KEY=这里换成你的真实密钥

如果用的是其他供应商，就按 config.yaml 里引用的变量名填写，例如 VOLCENGINE_API_KEY、GEMINI_API_KEY、DEEPSEEK_API_KEY。

4确认本地数据库

本地验证建议使用默认 sqlite，不需要手动配置 Postgres。看到或默认具备下面配置即可：

database:
  backend: sqlite
  sqlite_dir: .ideer/data

5确认 Skill 路径

本地默认从项目里的 skills/ 读取 Skill。一般保留默认配置即可：

skills:
  container_path: /mnt/skills

6什么时候需要 extensions 配置

如果只是开发普通智能体，不需要创建 extensions_config.json。如果要接 MCP 服务，再从模板复制：

cp extensions_config.example.json extensions_config.json

复制后只启用你真正需要的 MCP 服务，并把密钥写进 .env。

五、新建智能体配置包

一个智能体至少需要两个文件：config.yaml 和 SOUL.md。下面以 quality-reviewer 为例，你可以换成自己的名称。

1创建目录

mkdir -p docs/quality-reviewer/agent

2填写智能体 config.yaml

新建 docs/quality-reviewer/agent/config.yaml，内容可以从下面开始改：

name: quality-reviewer
description: 质量审查智能体，用于读取资料、检查问题并生成审查报告
tool_groups:
  - file:read
  - file:write
skills:
  - quality-review
字段 填写说明
name 智能体唯一名称。建议只用小写英文、数字和横线。
description 一句话说明智能体用途，会展示给用户看。
tool_groups 限制智能体能用哪些工具。越少越安全。
skills 只加载指定 Skill。不需要 Skill 时可以删掉这一段。

3选择工具权限

工具组 什么时候使用 建议
file:read 需要读取上传资料、日志、文档。 大多数资料分析类智能体都需要。
file:write 需要生成报告、表格、JSON 或中间文件。 需要输出文件时再开启。
web 需要联网搜索或读取网页。 没有外部检索需求时不要开启。

4填写 SOUL.md

新建 docs/quality-reviewer/agent/SOUL.md，内容可以从下面开始改：

# Quality Reviewer Agent SOUL

## 身份

你是质量审查智能体，负责根据用户提供的资料检查问题、形成结论并输出审查报告。

## 目标

1. 读取用户提供的资料。
2. 找出事实问题、风险点和待确认事项。
3. 生成结构清晰的审查结果。

## 工作原则

1. 先读资料，再下结论。
2. 每个关键结论都要说明依据。
3. 证据不足时写“待确认”，不要猜测。
4. 区分事实、推断和建议。

## 输出要求

默认使用中文。最终输出应包含问题清单、依据说明、风险等级和建议动作。

## 禁止事项

不得编造不存在的资料、数据或结论。

5检查 YAML 是否能解析

python3 -c "import yaml; yaml.safe_load(open('docs/quality-reviewer/agent/config.yaml', encoding='utf-8')); print('agent config ok')"

看到 agent config ok 才继续。

六、按需新建 Skill 模板

如果智能体只是普通对话和文件处理，可以跳过本节。如果它需要固定流程、规则、报告模板，就创建 Skill。

1创建 Skill 目录

mkdir -p skills/custom/quality-review

2填写 SKILL.md

新建 skills/custom/quality-review/SKILL.md，内容可以从下面开始改：

---
name: quality-review
description: 用于资料质量审查、问题识别和审查报告生成
---

# Quality Review Skill

## 使用场景

当用户要求审查资料、检查问题、生成质量报告时，使用本技能。

## 工作步骤

1. 读取用户提供的资料和目录。
2. 摘要说明资料范围。
3. 按问题类型列出发现。
4. 为每个问题标注依据。
5. 输出审查报告。

## 输出格式

- 问题编号
- 问题描述
- 依据来源
- 风险等级
- 建议动作

3确认 Skill 文件存在

ls skills/custom/quality-review/SKILL.md

如果智能体 config.yaml 里写了 skills: [quality-review]，这里必须能找到文件。

七、按需新建 subagents 模板

如果主智能体要把任务拆给多个角色，例如“资料读取员”“报告审查员”，才需要本节。普通智能体可以跳过。

1编写 subagents.yaml

新建 docs/quality-reviewer/subagents.yaml，内容可以从下面开始改：

subagents:
  custom_agents:
    evidence-reader:
      description: 读取资料并抽取关键证据
      system_prompt: |
        你是资料读取子智能体。只负责读取资料、抽取证据和标注来源，不做最终结论。
      tools:
        - read_file
        - grep
      skills:
        - quality-review
      model: inherit
      max_turns: 30
      timeout_seconds: 600

    report-reviewer:
      description: 检查报告是否完整、清晰、有依据
      system_prompt: |
        你是报告审查子智能体。只检查报告质量，输出问题清单和修改建议。
      tools:
        - read_file
        - write_file
      skills:
        - quality-review
      model: inherit
      max_turns: 30
      timeout_seconds: 600

2字段说明

字段 填写说明
description 说明什么时候应该调用这个子智能体。
system_prompt 定义子智能体的角色、边界和输出要求。
tools 子智能体可用工具。按最少够用原则填写。
skills 子智能体可加载的 Skill。没有 Skill 时可以删掉。
model 通常写 inherit，表示沿用主智能体模型。

3检查 YAML

python3 -c "import yaml; yaml.safe_load(open('docs/quality-reviewer/subagents.yaml', encoding='utf-8')); print('subagents ok')"
重要：

仅创建 subagents.yaml 还不够。custom subagents 必须合并进应用级 config.yaml 的 subagents.custom_agents 后，运行时才能通过 task 调用。

八、手工安装到目标用户运行目录

iDeer 前端只会显示安装到用户运行目录里的智能体。放在 docs/ 下只是源码模板，不会自动出现在页面中。

1设置名称和用户 ID

AGENT_NAME=quality-reviewer
USER_ID=7c5af71e-0069-4712-bf16-c54cd35639aa
RUNTIME_BASE=backend/.ideer

如果你设置了 IDEER_HOME，则把 RUNTIME_BASE 改为该目录。

2创建目标目录

mkdir -p "$RUNTIME_BASE/users/$USER_ID/agents/$AGENT_NAME"

3复制智能体文件

cp "docs/$AGENT_NAME/agent/config.yaml" "$RUNTIME_BASE/users/$USER_ID/agents/$AGENT_NAME/config.yaml"
cp "docs/$AGENT_NAME/agent/SOUL.md" "$RUNTIME_BASE/users/$USER_ID/agents/$AGENT_NAME/SOUL.md"

4确认已安装

ls "$RUNTIME_BASE/users/$USER_ID/agents/$AGENT_NAME/config.yaml"
ls "$RUNTIME_BASE/users/$USER_ID/agents/$AGENT_NAME/SOUL.md"
不要直接覆盖已有目录：

如果目标目录已经存在，先人工确认是否是旧版本或本地定制。确认无用后再处理。

5fault-zeroing 示例的专用安装方式

如果安装的是示例智能体 fault-zeroing，可以使用已有脚本：

python3 scripts/install_fault_zeroing_agent.py --user-id "$USER_ID"

其他新智能体不要使用这个脚本，因为它是 fault-zeroing 专用。

九、合并并检查 custom subagents

没有使用 subagents 的智能体可以跳过本节。使用了 subagents 的智能体，必须把 docs/<agent-name>/subagents.yaml 合并进应用级 config.yaml。

1先备份应用配置

cp config.yaml config.yaml.bak-before-subagents

2手工合并位置

打开 config.yaml，把 subagents.yaml 中的内容合并到下面位置：

subagents:
  custom_agents:
    evidence-reader:
      ...
    report-reviewer:
      ...

如果 config.yaml 里已经有同名 subagent，不要直接覆盖，先确认是否是旧配置。

3检查 registry 是否能识别

把下面命令里的名字换成你自己的 subagent 名称：

python3 -c "
import sys
from pathlib import Path
sys.path.insert(0, str(Path('backend/packages/harness').resolve()))
from ideer.config.app_config import reload_app_config
from ideer.subagents.registry import get_subagent_config
cfg = reload_app_config('config.yaml')
names = ['evidence-reader','report-reviewer']
missing = [n for n in names if get_subagent_config(n, app_config=cfg) is None]
print('missing=', missing)
raise SystemExit(1 if missing else 0)
"

正确结果是：

missing= []

十、启动服务并页面验收

1启动服务

scripts/run-local-services.sh restart

看到下面结果，表示服务已经起来：

OK Gateway
OK Frontend
OK Unified entrypoint
iDeer is running: http://localhost:2026

2浏览器检查

  1. 打开 http://localhost:2026。
  2. 登录 iDeer。
  3. 进入智能体列表或智能体选择入口。
  4. 确认能看到你的智能体，例如 quality-reviewer。
  5. 进入该智能体，发起一次简单对话。
  6. 如果用了 custom subagents，确认没有出现 Unknown subagent type。
接口检查说明：

/api/agents 需要登录态。未登录时返回 not_authenticated 是正常的，不代表安装失败。

十一、开发完成检查

  • config.yaml、.env、frontend/.env 都存在。
  • config.yaml 中 models: 至少有一个可用模型。
  • 模型需要的 API Key 已写入 .env。
  • docs/<agent-name>/agent/config.yaml 能被 YAML 解析。
  • docs/<agent-name>/agent/SOUL.md 已写明身份、原则和输出要求。
  • 如果配置了 Skill，对应 skills/custom/<skill-name>/SKILL.md 存在。
  • 如果配置了 subagents，已合并进应用级 config.yaml 并通过 registry 检查。
  • 智能体文件已复制到 backend/.ideer/users/<user-id>/agents/<agent-name>/。
  • 服务脚本输出 iDeer is running: http://localhost:2026。
  • 浏览器登录后能看到新智能体，并能完成一次简单对话。

十二、常见问题处理

现象 原因 处理方法
提示 config.yaml not found 项目配置文件不存在。 运行 make config 生成基础配置；如果已有文件，先备份再检查。
页面看不到新智能体 文件只放在 docs/ 下，未安装到用户运行目录。 把 config.yaml 和 SOUL.md 复制到 backend/.ideer/users/<user-id>/agents/<agent-name>/。
提示模型不可用或模型名不在列表 请求使用的模型没有写进 config.yaml 的 models:。 把请求模型改成已有模型，或在 config.yaml 中补充模型配置和对应密钥。
出现 Unknown subagent type 子智能体没有合并进应用级 config.yaml。 把 docs/<agent-name>/subagents.yaml 合并到 config.yaml，再运行 registry 检查。
/api/agents 返回 not_authenticated 当前请求没有登录态。 先在浏览器登录，再检查智能体列表。
页面打不开 本地服务没有启动或端口被占用。 运行 scripts/run-local-services.sh restart，再访问 http://localhost:2026。
YAML 检查失败 缩进、冒号或列表格式写错。 对照模板检查缩进。YAML 中列表项要以 - 开头，冒号后通常要留空格。

十三、停止服务

验证完成后，如果不再使用本地服务，可以停止：

scripts/run-local-services.sh stop

看到 Stopped. 即表示后台服务已关闭。
