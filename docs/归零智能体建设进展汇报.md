# 归零智能体建设进展汇报

## 一、前期建设进程

### 1.1 前期调研

#### 1.1.1 归零智能体案例调研

前期对国内外基于大模型的故障分析与归零智能体实践进行了系统调研，重点关注以下方向：

- **开源智能体框架调研**：评估了 LangGraph、LangChain、AutoGen 等主流智能体框架在复杂推理任务中的表现，重点考察其多智能体编排、工具调用、文件系统访问和长期记忆能力。
- **归零排故领域实践调研**：梳理了航天、航空等领域归零排故的标准流程（故障现象确认→证据收集→故障树构建→底事件评估→根因归因→验证计划→报告生成），明确了智能体需要固化的关键步骤和约束条件。
- **企业级智能体平台调研**：调研了 iDeer（Deep Exploration and Efficient Research Flow）框架，确认其具备自定义智能体、Skill 行为固化、文件资料读取、子智能体委托、报告产物输出等核心能力，可作为归零智能体的底座平台。

#### 1.1.2 归零问题调研

针对归零排故业务场景，完成了以下调研工作：

- **归零流程标准化**：梳理了五类核心输入资料（问题描述、设计约束、试验记录或日志、总结报告、历史或复核记录），明确了资料覆盖矩阵的检查规范。
- **证据等级体系设计**：建立了 A/B/C/D 四级证据分类标准——A 级为原始日志、试验记录等一手数据，B 级为专家记录、会议纪要等，C 级为间接描述，D 级为无来源假设。规定根因结论必须由 A/B 级证据支撑，证据不足时必须标记"待验证"。
- **故障树构建规范**：定义了顶事件、中间事件、底事件的层级结构和逻辑关系，要求底事件必须可验证、可追溯，禁止将笼统原因写成底事件。
- **典型场景梳理**：收集了高焓风洞热流测量漂移、热真空控温超调、电弧加热烧蚀异常等典型归零场景，形成了评测案例集。

### 1.2 平台与模型选型

#### 1.2.1 平台选型

经综合评估，选用 **iDeer 2.0** 作为归零智能体的底座平台，主要依据：

| 能力维度 | 平台能力 | 归零场景需求匹配度 |
|---------|---------|------------------|
| 自定义智能体 | 支持 Agent 配置、SOUL.md 身份定义、工具白名单、Skill 白名单 | 高：可直接定义归零排故智能体身份和行为边界 |
| Skill 机制 | 结构化能力模块，按需渐进加载，支持 frontmatter 元数据 | 高：可将归零流程、证据规则、报告模板固化为 Skill |
| 文件系统 | 沙箱内文件读写、glob/grep 搜索、按行读取 | 高：支持读取用户上传的问题描述、日志、试验记录等资料 |
| 子智能体 | 自定义子智能体，独立上下文、工具和终止条件，支持并行 | 高：可拆分为证据读取、故障树构建、概率评估等专业子智能体 |
| 产物输出 | write_file 写入 outputs 目录，present_files 展示 | 高：可生成故障树 JSON、SVG、评估报告、归零报告等标准产物 |
| 模型接入 | 支持 OpenAI-compatible、DeepSeek、Claude 等多种模型 | 高：可根据任务复杂度灵活选择基座模型 |
| 企业扩展 | RBAC 权限、工作流引擎、企业工具集、内网部署 | 中：为后续生产级集成预留能力 |

#### 1.2.2 模型选型

当前配置使用 Codex GPT-5.4 作为主模型，同时评估了以下候选模型：

- **GPT-5.4**：推理能力强，适合复杂故障树构建和多源证据综合分析，当前作为主模型。
- **DeepSeek V3**：长上下文窗口（128K+ tokens），适合处理大规模试验数据和多份文档，可作为备选。
- **Claude 3.5 Sonnet**：在结构化输出和代码生成方面表现稳定，适合故障树 JSON 生成和报告模板填充。
- **本地部署模型**（Ollama/vLLM）：Qwen3-32B 等本地模型可用于成本敏感的日常分析任务，降低 API 调用开销。

模型选型原则：优先选择长上下文窗口（100K+ tokens）、推理能力强、tool use 能力稳定的模型。

### 1.3 智能体与 Skill 开发

#### 1.3.1 归零排故智能体（fault-zeroing agent）

已完成归零排故智能体的配置开发，包括：

**智能体身份定义（SOUL.md）**：
- 明确智能体角色为"归零排故智能体"，目标是基于用户证据资料完成故障树构建、底事件评估、根因归因、验证计划和归零报告生成。
- 定义六项工作原则：先读资料再形成结论、不得凭空给概率、每个结论绑定证据来源、区分事实/推断/假设、冲突证据保留双方、输出前检查闭环。

**智能体配置（config.yaml）**：
- 工具权限：限定 file:read、file:write、web 三类工具组。
- Skill 绑定：仅加载 fault-zeroing 专属 Skill。
- 模型：继承主智能体模型配置。

**固定执行阶段**：严格定义八步执行流程，不得跳步、不得先写根因再补证据：

```
资料盘点 → 证据台账 → 故障树构建 → 底事件评估 → 根因归因 → 验证计划 → 报告生成 → 报告审查
```

#### 1.3.2 子智能体体系

设计并实现了五个专业子智能体，各司其职、边界清晰：

| 子智能体 | 职责 | 工具权限 | 约束 |
|---------|------|---------|------|
| evidence-reader | 读取归零资料、抽取关键证据、标注文件和行号 | glob, grep, read_file | 不输出根因 |
| fault-tree-builder | 根据顶事件和证据构建故障树 | read_file, write_file | 不给最终归因 |
| probability-assessor | 评估底事件概率、置信度和证据等级 | read_file, write_file | 无依据不写数值概率 |
| root-cause-analyst | 综合底事件概率和证据强度形成归因 | read_file, write_file | 只引用 A/B 级证据 |
| report-reviewer | 检查报告章节、证据引用和待验证项 | read_file, write_file | 不新增技术结论 |

子智能体编排规则：复杂资料包最多进行一轮核心委托，子任务返回后主智能体必须直接进入产物生成和自检，防止过度委托导致不收敛。

#### 1.3.3 fault-zeroing Skill

已完成归零排故 Skill 的开发（`skills/custom/fault-zeroing/SKILL.md`），固化了：

- **工作目标**：基于用户上传的资料完成故障树构建、底事件评估、根因归因、验证计划和归零报告生成。
- **输入资料读取规则**：八条规则覆盖路径确认、优先读取目录、长文档按章节读取、缺少关键输入时调用澄清等。
- **证据处理规则**：要求执行前读取 evidence_rules.md，每条结论绑定 evidence id 或明确资料来源。
- **故障树构建规则**：六条规则覆盖顶事件来源、中间事件用途、底事件可验证性、字段记录要求等。
- **底事件评估规则**：使用"证据强度 + 机理一致性 + 反证情况 + 复现实验情况"四维评估模型。
- **输出规则**：五件套输出（fault_tree.json、fault_tree.svg、bottom_event_assessment.md、analysis_process.svg、zeroing_report.md），写完后必须自检八项检查点。

配套文件：
- `references/evidence_rules.md`：证据等级和引用规范，定义 A/B/C/D 四级标准。
- `templates/fault_tree.schema.json`：故障树 JSON Schema，确保结构化输出的规范性。
- `templates/zeroing_report.md`：归零报告 Markdown 模板，包含十个标准章节。
- `templates/bottom_event_assessment.md`：底事件评估模板。
- `templates/evidence_table.md`：证据台账模板。

| 案例 | 场景 | 主要验证点 |

3. 故障现象
4. 故障树分析
5. 底事件概率评估
6. 根因归因
7. 验证计划与结果
8. 纠正措施
9. 遗留风险
10. 附录：证据引用

### 1.5 前期验证成果

已完成 case_01（高焓风洞热流测量漂移）的完整执行验证，关键成果：

- **执行闭环**：智能体成功完成从文件读取、证据抽取、故障树构建、底事件评估到三份报告输出的全流程闭环。
- **子智能体协作**：evidence-reader、fault-tree-builder、probability-assessor 三个子智能体均正常执行并返回结构化结果。
- **分析正确性**：智能体将"HF-07 测量链路异常导致单点读数漂移"作为主判断，与案例资料中的数据、设计判据和专家复核记录一致。未误判为真实热环境异常。
- **边界控制**：HF-07 传感器本体漂移（高倾向）和 CH-07 采集通道异常（中倾向）被正确列为待验证底事件，未过度归因。
- **证据引用**：关键结论均绑定文件路径、章节或 evidence_id，满足可追溯性要求。
- **概率表达谨慎性**：未使用无依据数值概率，仅使用高/中/低倾向和置信度。

## 二、未来工作流程设想

当新发生需归零的质量问题时，依托该平台进行智能体归零分析的工作流程如下：

### 2.1 问题受理与材料准备

**触发条件**：试验过程中或试验后发现异常现象，需要进行归零排故分析。

**操作步骤**：
1. 在 iDeer 平台选择"fault-zeroing"归零排故智能体。
2. 上传问题资料包，包含：
   - 问题描述（顶事件、发生条件、影响范围、当前状态）
   - 设计方案和测点布置
   - 试验大纲和工况矩阵
   - 试验总结报告
   - 试验数据（CSV、日志等）
   - 历史复核记录（如有）
3. 输入分析提示词（可使用推荐模板）。

### 2.2 智能体自动分析流程

智能体接收到材料后，按以下固定阶段自动执行：

**阶段一：资料盘点**
- 自动读取上传目录中的所有文件。
- 输出已读取、未读取和缺失资料清单。
- 形成资料覆盖矩阵（五类资料逐项检查）。

**阶段二：证据抽取**
- 委托 evidence-reader 子智能体读取资料、抽取关键证据。
- 每条证据标注来源文件、行号或章节、证据等级（A/B/C/D）。
- 区分事实、推断、假设和待验证项。
- 输出结构化证据台账。

**阶段三：故障树构建**
- 委托 fault-tree-builder 子智能体构建故障树。
- 确定顶事件（来自资料原文）。
- 构建中间事件（故障传播链、功能失效链）。
- 构建底事件（必须可验证，不写笼统原因）。
- 输出故障树草案。

**阶段四：底事件评估**
- 委托 probability-assessor 子智能体评估底事件。
- 使用四维评估模型：证据强度 + 机理一致性 + 反证情况 + 复现实验情况。
- 输出每个底事件的倾向（高/中/低）、置信度和验证状态。

**阶段五：根因归因**
- 主智能体综合子智能体结果形成归因。
- 根因结论必须由 A/B 级证据支撑。
- 证据不足时标记"待验证"。
- 保留冲突证据的双方来源。

**阶段六：验证计划**
- 为待验证项、冲突证据、低置信根因生成验证项。
- 明确验证目的、方法、期望结果。

**阶段七：报告生成**
- 生成五件套标准产物：
  1. `fault_tree.json`：结构化故障树数据（机器可读，支持后续校验）
  2. `fault_tree.svg`：故障树可视化框图（展示顶事件、中间事件、底事件、逻辑门和状态）
  3. `bottom_event_assessment.md`：底事件评估报告（逐项说明证据、机理、反证和结论）
  4. `analysis_process.svg`：分析过程流程图（展示从证据读取到报告审查的完整链路）
  5. `zeroing_report.md`：正式归零报告（十个标准章节，含资料覆盖矩阵和证据台账摘要）

**阶段八：报告审查与自检**
- 检查五份文件全部存在。
- 检查报告章节完整性、证据闭环、过度归因。
- 检查 JSON 与报告一致性。
- 检查 SVG 安全性（仅使用静态元素）。
- 提示用户可运行离线 validator 进行进一步校验。

### 2.3 预期效果

| 效果维度 | 具体表现 |
|---------|---------|
| 分析效率 | 传统人工归零分析需要数天至数周，智能体可在数小时内完成初步分析框架 |
| 流程规范性 | 八步固定流程确保不跳步、不先写结论再补证据，符合归零标准 |
| 证据可追溯性 | 每个结论绑定证据来源，支持事后审查和验证 |
| 过度归因控制 | 严格区分事实/推断/假设，证据不足时标记待验证，避免误导性结论 |
| 报告标准化 | 五件套标准产物确保输出格式一致、内容完整 |
| 知识沉淀 | 分析过程和产物可复用，为后续案例提供参考 |
| 人机协同 | 智能体提供初步分析框架和验证方向，最终归因仍由领域专家确认 |

### 2.4 典型应用场景

**场景一：试验过程中发现异常**
- 试验进行中发现测量数据异常，现场人员上传问题描述和实时数据。
- 智能体快速完成初步故障树构建和底事件评估，为现场决策提供参考。

**场景二：试验后归零分析**
- 试验结束后，上传完整资料包（问题描述、设计方案、试验记录、数据、历史复核）。
- 智能体完成全流程分析，输出标准化归零报告，供评审使用。

**场景三：历史案例对比分析**
- 上传当前问题资料和历史相似案例资料。
- 智能体在分析过程中参考历史案例，辅助判断和验证方向。

### 3.2 中期计划（3-6 个月）

**目标**：综合多个历史归零案例，将历史归零数据纳入知识库，并根据案例分析思路提炼智能体工作流。

| 任务 | 具体内容 | 预期成果 |
|------|---------|---------|
| 历史归零案例入库 | 收集、脱敏、结构化处理 20-30 个历史归零案例，建立案例库 | 形成可检索的历史案例知识库，支持相似案例匹配 |
| 知识库构建 | 建立故障模式库、证据规则库、验证方法库，接入向量检索 | 智能体在分析过程中可检索历史相似案例和领域知识 |
| 工作流提炼 | 基于多个案例的分析过程，提炼差异化的分析策略和分支判断逻辑 | 针对不同故障类型（测量异常、机械失效、热控异常等）形成专用分析路径 |
| 多模型协同 | 引入轻量模型处理证据抽取，重量模型处理根因归因，降低分析成本 | 分析成本降低 40%，同时保持分析质量 |
| 任务实例管理 | 实现归零任务的创建、状态跟踪、报告版本管理和历史查询 | 支持任务全生命周期管理，报告可追溯到输入材料和分析过程 |

**所需资源**：
- 领域专家投入：3-4 人月，提供历史案例、校验知识库、验证工作流。
- 知识库建设投入：约 2 人月开发工作量，包括数据治理、向量检索接入、知识条目管理。
- 历史案例数据：需要从质量管理系统导出 20-30 个归零案例的脱敏数据。
- 服务器资源：1 台 16 vCPU/32 GB 内存服务器，用于向量数据库和批量知识入库。
