# 归零智能体工作流引擎重构设计方案

## 1. 概述

将当前依赖 SOUL.md 提示驱动的归零排故自定义智能体，重构为一套基于 Workflow V2 引擎的 DAG 工作流。核心变更：

- **执行序列由工作流图拓扑强制**，不再依赖 LLM 遵守提示中的阶段描述
- **9 个工作流节点**，每节点是独立的 LLM 推理会话，专注单一认知活动
- **监督-评估-反思-优化循环**嵌入故障树构建和底事件评估两个关键阶段
- **演绎与证据分离**：故障树构建以 fork 分支与证据提取并行，从纯机理演绎开始，证据仅在接合后的检漏和评估阶段介入
- **显式状态传递**：中间产物写入 `outputs/artifacts/`，状态只携带轻量摘要
- **节点文件最小权限**：Agent Action 可声明可选 `file_access.read/write`，由工具调用中间件独立于 sandbox provider 强制执行

## 2. 当前架构的问题

### 2.1 当前架构

```
用户 → 「归零智能体」(Custom Agent) → 单个 LLM，带有 SOUL.md + SKILL.md 提示
        8 个阶段完全靠提示控制，无强制执行顺序
```

SOUL.md 定义了 8 个阶段（资料盘点→证据台账→故障树→底事件评估→根因归因→验证计划→报告生成→报告审查），但 LLM 可能跳过、颠倒或偏离这些阶段。

### 2.2 从认知活动角度的根本缺陷

8 个阶段实际只包含 3 种认知活动，但被人为切碎：

| 认知活动 | 当前划分 | 问题 |
|----------|---------|------|
| **证据提取**（读取→提取→结构化） | 阶段1+2 | 盘点和提取不可分割 |
| **因果推理**（建树→评估→归因→行动） | 阶段3+4+5+6 | 推理链被切成 4 段，上下文断裂 |
| **文档生产**（综合→格式→自检） | 阶段7+8 | LLM 自我审查有效性存疑 |

### 2.3 故障树构建的概念混淆

当前方案中，故障树构建受证据台账影响——LLM 倾向于"有证据的节点建得细，没证据的忽略"。但故障树的正确作用是列出**所有理论上可能的根因**，证据只影响概率和状态判断，不应决定节点存在性。

## 3. 核心设计原则

### 原则 1：演绎与证据分离

故障树构建是**纯演绎**过程——从顶事件出发，基于工程机理和系统知识列出所有可能的故障路径。证据台账只在以下两个时机介入：

- **证据检漏**（review_and_crosscheck）：逐条对照证据台账，发现树中遗漏的故障模式
- **证据评估**（evidence_assessment）：用证据决定每个底事件的概率、置信度和状态

证据在任何情况下**不缩小**故障树——无证据的节点标记 `to_verify`，有反证的节点降低概率，都不删除。

### 原则 2：监督-评估-反思-优化循环

对于两个核心推理阶段（故障树构建、底事件评估），引入固定两轮的审核-优化循环：

```
正向推理 → 独立审查 → 定向优化
```

审查者与执行者是**不同的系统提示词角色**。问题清单以结构化 JSON 显式传递，不依赖 LLM 隐式记忆。

两轮固定而非动态循环：LLM 自我评估不可靠，固定轮次保证可预测的 token 消耗和质量控制。

### 原则 3：关注点分离

| 阶段 | 职责 | 不允许做 |
|------|------|---------|
| 证据提取 | 阅读文件、提取证据 | 做根因判断 |
| 演绎建树 | 纯机理推导 | 参考证据台账 |
| 审查检漏 | 发现问题 | 做修正 |
| 整合裁决 | 四象限规则做决策 | 引入新推理 |
| 证据评估 | 匹配证据与节点 | 删除节点 |
| 纠正措施 | 定义修复方案 | 改变根因判断 |
| 文档生产 | 格式化输出 | 改变分析数据 |

### 原则 4：磁盘持久化 + 轻量摘要

每个阶段的完整产物写入磁盘（JSON/MD），状态（state）只携带 200-500 字的摘要。后续阶段通过 `read_file` 按需读取完整内容。避免提示膨胀导致 LLM 忽略 prompt 尾部内容。

## 4. 目标架构

```
输入: upload_dir, problem_description, output_base_dir
  │
  │  ╔══════════════════════════════════════════════════════╗
  │  ║  fork: 两条并行分支，物理隔离                       ║
  │  ║                                                    ║
  │  ║  分支A（证据提取）          分支B（演绎建树）        ║
  │  ║    证据分析师                 系统安全分析师(演绎)    ║
  │  ║    artifacts/evidence/        artifacts/tree/        ║
  │  ║                                                    ║
  │  ╚════════════════════╤═══════════════════════════════╝
  │                       │
  │                  join（两路都完成）
  │                       │
  ├── ▶ review_and_crosscheck（机理审查+证据交叉检漏）
  ├── ▶ integrate_tree（四象限裁决，整合终版树结构）
  ├── ▶ evidence_assessment（对照证据评估每个底事件+根因+验证计划）
  ├── ▶ assessment_review（审核评估结果）
  ├── ▶ assessment_refine（优化评估结果）
  ├── ▶ corrective_actions（生成纠正措施）
  └── ▶ generate_outputs（生成 4 个输出文件，不覆盖 fault_tree.json）
```

## 5. 节点详细设计

### 阶段 1: 证据提取（fork 分支 A）

| 属性 | 值 |
|------|-----|
| 节点 ID | `evidence_collection` |
| 角色 | 证据分析师 - 只负责读取文件和提取证据 |
| 输入 | `upload_dir`, `problem_description` |
| 输出 | `artifacts/evidence/evidence_table.json`, `artifacts/evidence/coverage_matrix.md` |
| State 写入 | `evidence_summary: { total, grade_distribution, coverage_status }` |
| 约束 | 不做根因判断，只做"从文件中提取了哪些事实" |

**system_prompt**：你是证据分析师。只负责读取资料、抽取证据、标注来源。不做根因判断。每条证据必须包含 id、source（文件路径+行号/章节）、grade（A/B/C/D）、type、summary、supports、contradicts。

**prompt** 中的关键指令：
```
1. 使用 glob 扫描 {{inputs.upload_dir}}
2. 读取关键文件，逐条提取证据
3. 形成资料覆盖矩阵（五类：问题描述、设计约束、试验记录或日志、总结报告、历史或复核记录）
4. 写入 {{inputs.output_base_dir}}/artifacts/evidence/evidence_table.json
5. 写入 {{inputs.output_base_dir}}/artifacts/evidence/coverage_matrix.md
```

### 阶段 2: 演绎建树（fork 分支 B）

| 属性 | 值 |
|------|-----|
| 节点 ID | `deductive_tree` |
| 角色 | 系统安全分析师（演绎模式）——不看任何证据，纯机理推导 |
| 输入 | `problem_description` |
| 输出 | `artifacts/tree/fault_tree_structure.json` |
| State 写入 | `tree_structure: { top_event, depth, node_count }` |
| 约束 | 不读 evidence 目录的文件；不做概率/状态判断 |

**system_prompt**：你是系统安全分析师（演绎模式）。基于工程机理做纯演绎推导。不看任何证据台账。列出所有理论上可能的故障原因。不要因为"没有证据"就忽略某个分支。

**prompt** 中的关键指令：
```
1. 确认顶事件
2. 逐层推导中间事件（故障传播链、功能失效链、条件组合）
3. 细化到底事件
4. 标注逻辑关系（AND/OR）
5. 不填充 evidence_ids、probability、confidence、status
6. 写入 {{inputs.output_base_dir}}/artifacts/tree/fault_tree_structure.json
```

### 阶段 3: 审查与检漏（join 后第一个节点）

| 属性 | 值 |
|------|-----|
| 节点 ID | `review_and_crosscheck` |
| 角色 | 审查与检漏分析师——两遍扫描 |
| 输入 | fault_tree_structure.json + evidence_table.json |
| 输出 | 不写文件，仅输出 `state.all_findings` |
| State 写入 | `all_findings: { structure_issues[], evidence_gaps[] }` |

第一遍（机理审查）：忽略证据表，只从机理角度检查树结构完整性。
第二遍（证据交叉检漏）：逐条对照 evidence 表，发现 "证据指向的故障模式在树中无对应路径" 的遗漏。

检漏只做 ADD 不做 DELETE。证据永远不会缩小故障树。

### 阶段 4: 整合裁决

| 属性 | 值 |
|------|-----|
| 节点 ID | `integrate_tree` |
| 角色 | 整合分析师——用四象限矩阵规则做最终决策 |
| 输入 | fault_tree_structure.json + all_findings |
| 输出 | 覆盖 `artifacts/tree/fault_tree_structure.json` |
| State 写入 | `tree_structure`（更新） |

四象限裁决矩阵：

| | 有证据支持 | 无证据支持 |
|---|---|---|
| **树中有该节点** | 保留 | 保留，评估阶段标记 to_verify |
| **树中无该节点** | 裁决是否添加 | 忽略 |

检漏遗漏节点的分层裁决：
- 第 1 层：机理评估——遗漏路径在理论上是否可能？
- 第 2 层：证据可信度——证据场景与当前故障是否匹配？
- 第 3 层：决定添加（标记 to_verify）或不添加（记录为遗留风险）

### 阶段 5: 证据评估

| 属性 | 值 |
|------|-----|
| 节点 ID | `evidence_assessment` |
| 角色 | 评估分析师——对照证据台账评估每个底事件 |
| 输入 | fault_tree_structure.json + evidence_table.json |
| 输出 | `outputs/fault_tree.json`（完整版，含评估+根因+验证计划） |
| State 写入 | `assessment_summary` |

关键规则：
- 保留所有底事件，不做删除
- 无直接证据支持 → to_verify, probability: null
- 有反证 → 保留节点，降低概率（不删除）
- 根因必须有 A/B 级证据；否则 to_verify
- 数值概率必须有明确依据；否则 null

### 阶段 6: 评估审核

| 属性 | 值 |
|------|-----|
| 节点 ID | `assessment_review` |
| 角色 | 审核专家——标准比评估分析师更严格 |
| 输入 | fault_tree.json |
| 输出 | `state.assessment_review: { issues[] }` |
| 约束 | 只发现问题，不做修正 |

### 阶段 7: 评估优化

| 属性 | 值 |
|------|-----|
| 节点 ID | `assessment_refine` |
| 角色 | 评估分析师（优化模式） |
| 输入 | fault_tree.json + assessment_review |
| 输出 | 覆盖 `outputs/fault_tree.json` |
| 约束 | 逐条回应审查意见：同意则修正，不同意则说明理由 |

### 阶段 8: 纠正措施

| 属性 | 值 |
|------|-----|
| 节点 ID | `corrective_actions` |
| 角色 | 纠正措施分析师 |
| 输入 | fault_tree.json |
| 输出 | `artifacts/corrective_actions.json` |
| State 写入 | `corrective_actions_summary` |

纠正措施 ≠ 验证计划：
- 纠正措施：针对已确认的根因，修复问题
- 验证计划：针对待验证底事件，验证假设

### 阶段 9: 文档生产

| 属性 | 值 |
|------|-----|
| 节点 ID | `generate_outputs` |
| 角色 | 文档工程师 |
| 输入 | 所有产物 |
| 输出 | 4 个文件到 `outputs/` |
| 约束 | 不覆盖 fault_tree.json |

生成的 4 个文件：
1. `fault_tree.svg` — 故障树静态 SVG 框图
2. `bottom_event_assessment.md` — 底事件评估表
3. `analysis_process.svg` — 分析链路 SVG
4. `zeroing_report.md` — 10 章节完整归零报告

## 6. 工作流 YAML

```yaml
schema_version: 2
name: fault-zeroing
description: 归零排故工作流 — 基于证据资料完成故障树构建、底事件评估、根因归因、纠正措施和归零报告生成

inputs:
  upload_dir:
    type: string
    required: true
    description: "用户上传资料的目录路径"
  problem_description:
    type: string
    default: ""
    description: "问题/顶事件描述"
  output_base_dir:
    type: string
    default: "/tmp/opencode/fault-zeroing-outputs"
    description: "产物输出基础目录"

state:
  evidence_summary:
    type: object
    default: {}
  tree_structure:
    type: object
    default: {}
  all_findings:
    type: object
    default: {}
  assessment_summary:
    type: object
    default: {}
  assessment_review:
    type: object
    default: {}
  corrective_actions_summary:
    type: object
    default: {}

entrypoint: fork_preparation

nodes:
  # ── 准备节点：创建输出目录 ──
  - id: fork_preparation
    type: action
    action:
      kind: tool
      name: mkdir
      params:
        path: "{{inputs.output_base_dir}}/artifacts/evidence;{{inputs.output_base_dir}}/artifacts/tree"
    writes:
      - "$.state.tree_structure"

  # ── fork: 证据提取 与 演绎建树 并行 ──
  - id: fork_start
    type: fork
    branches:
      - evidence_collection
      - deductive_tree
    join: join_review

  - id: evidence_collection
    type: action
    action:
      kind: agent
      name: fault-zeroing
      params:
        system_prompt: |
          你是证据分析师。只负责读取资料、抽取证据、标注来源，不做根因结论。
        prompt: |
          任务：读取归零资料，提取证据，形成证据台账。

          上传目录：{{inputs.upload_dir}}
          问题描述：{{inputs.problem_description}}

          1. 使用 glob 扫描 {{inputs.upload_dir}}，了解文件结构
          2. 读取关键文件，抽取每一条证据
          3. 检查五类资料覆盖情况：问题描述、设计约束、试验记录或日志、总结报告、历史或复核记录
          4. 生成证据台账

          输出：
          a) 写入 {{inputs.output_base_dir}}/artifacts/evidence/evidence_table.json
            每条证据包含 id、source（文件路径#行号或章节）、grade（A/B/C/D）、
            type、summary、supports（可支撑的事件ID）、contradicts（反证对象ID）
          b) 写入 {{inputs.output_base_dir}}/artifacts/evidence/coverage_matrix.md
          c) 输出摘要：总证据数、A/B/C/D 各级分布、覆盖情况
    writes:
      - "$.state.evidence_summary"

  - id: deductive_tree
    type: action
    action:
      kind: agent
      name: fault-zeroing
      params:
        system_prompt: |
          你是系统安全分析师（演绎模式）。基于工程机理做纯演绎推导。
          不看任何证据台账。列出所有理论上可能的故障原因。
        prompt: |
          任务：基于工程机理，从顶事件出发构建完整的故障树。

          问题描述：{{inputs.problem_description}}

          工作目录：{{inputs.output_base_dir}}/artifacts/tree/（不需要关心其他目录）

          1. 确认顶事件（必须来自问题描述）
          2. 逐层推导中间事件（故障传播链、功能失效链、条件组合）
          3. 细化到底事件（可验证的最小单元）
          4. 标注逻辑关系（AND/OR）

          约束：
          - 不依赖任何来源文件或证据台账
          - 不做概率判断，不给状态标记
          - 列出所有理论上可能的路径

          输出：写入 {{inputs.output_base_dir}}/artifacts/tree/fault_tree_structure.json
          参考 fault_tree.schema.json 格式，但不填充 evidence_ids、probability、
          probability_basis、confidence、status 字段（留 null 或空数组）
    writes:
      - "$.state.tree_structure"

  # ── join: 等待两路完成 ──
  - id: join_review
    type: join
    fork: fork_start

  # ── 审查与检漏 ──
  - id: review_and_crosscheck
    type: action
    action:
      kind: agent
      name: fault-zeroing
      params:
        system_prompt: |
          你是故障树审查与证据检漏分析师。做两遍独立扫描：
          第一遍从机理检查结构完整性；第二遍从证据反向检查遗漏。
        prompt: |
          任务：审查故障树 + 证据交叉检漏。

          读取：
          a) {{inputs.output_base_dir}}/artifacts/tree/fault_tree_structure.json
          b) {{inputs.output_base_dir}}/artifacts/evidence/evidence_table.json

          第一遍（机理审查）：
          忽略证据表，仅检查：
          - 是否遗漏了理论上可能的故障分支？
          - 逻辑门是否正确反映故障传播关系？
          - 底事件是否可验证（避免笼统描述）？

          第二遍（证据交叉检漏）：
          逐条对照证据台账：如果某条证据指向的故障模式在树中无对应路径，
          记录为"遗漏"。只做添加不做删除。

          输出（仅写入 state，不写文件）：
          ```json
          {
            "structure_issues": [
              {"node_id": "...", "issue": "...", "severity": "error|warning", "suggested_fix": "..."}
            ],
            "evidence_gaps": [
              {"evidence_id": "...", "evidence_summary": "...",
               "suggested_path": ["顶事件", "...", "..."],
               "suggested_event": "建议新增节点描述",
               "reason": "遗漏原因"}
            ]
          }
          ```
    writes:
      - "$.state.all_findings"

  # ── 整合裁决 ──
  - id: integrate_tree
    type: action
    action:
      kind: agent
      name: fault-zeroing
      params:
        system_prompt: |
          你是故障树整合分析师。使用四象限裁决矩阵规则对发现问题做最终决策。
        prompt: |
          读取：
          a) {{inputs.output_base_dir}}/artifacts/tree/fault_tree_structure.json
          b) 审查发现（state 中的 all_findings）

          裁决规则（四象限矩阵）：

          |                    | 有证据支持 | 无证据支持 |
          |--------------------|-----------|-----------|
          | 树中有该节点       | 保留       | 保留       |
          | 树中无该节点       | 需要添加   | 忽略       |

          关键原则：
          - 证据永远不会缩小树结构
          - 检漏发现的遗漏，分层裁决：
            第1层：机理评估——该路径在理论上是否可能？
            第2层：证据可信度——证据场景与故障是否匹配？
            第3层：决定添加（to_verify）或不添加（记录遗留风险）

          输出：覆盖写入 {{inputs.output_base_dir}}/artifacts/tree/fault_tree_structure.json
    writes:
      - "$.state.tree_structure"

  # ── 证据评估 ──
  - id: evidence_assessment
    type: action
    action:
      kind: agent
      name: fault-zeroing
      params:
        system_prompt: |

## 8. 引擎变更

### 8.1 _AgentAdapter 增加 system_prompt 覆盖

文件：`backend/packages/harness/ideer/workflows/v2/adapters.py`

```python
class _AgentAdapter:
    def __init__(self, name: str, user_id: str) -> None:
        self.name = name
        self.user_id = user_id

    async def run(self, context: ActionContext, params: dict[str, Any]) -> Any:
        from ideer.config import get_app_config
        from ideer.config.agents_config import load_agent_config, load_agent_soul
        from ideer.subagents.config import SubagentConfig
        from ideer.subagents.executor import SubagentExecutor, SubagentStatus
        from ideer.tools.tools import get_available_tools

        config = load_agent_config(self.name, user_id=self.user_id)
        if config is None:
            raise ActionResolutionError(f"agent '{self.name}' not found")

        # ── system_prompt 覆盖 ──
        soul = load_agent_soul(self.name, user_id=self.user_id) or ""
        override = params.get("system_prompt", "")
        if soul and override:
            system_prompt = f"{soul}\n\n## 当前阶段指令\n\n{override}"
        else:
            system_prompt = soul or override
        # ─────────────────────────

        subagent = SubagentConfig(
            name=self.name,
            description=f"Workflow node: {context.node_id}",
            system_prompt=system_prompt,
            tools=config.tool_groups,
            skills=config.skills,
            model=config.model or "inherit",
        )
        executor = SubagentExecutor(
            subagent,
            get_available_tools(app_config=get_app_config()),
            app_config=get_app_config(),
        )
        prompt = params.get("prompt", params.get("input", params))
        result = await executor._aexecute(str(prompt))
        if result.status == SubagentStatus.COMPLETED:
            return result.result
        raise RuntimeError(result.error or f"agent '{self.name}' failed with status {result.status}")
```

**向后兼容**：当 workflow YAML 不传 `system_prompt` 时，`override` 为空字符串，`system_prompt = soul`，行为完全不变。

### 8.2 Agent Action 文件访问契约

Workflow V2 的 Agent Action 支持可选策略：

```yaml
action:
  kind: agent
  name: fault-zeroing
  file_access:
    read:
      - "{{inputs.upload_dir}}"
    write:
      - "{{inputs.output_base_dir}}/artifacts/evidence"
```

策略经编译器模板渲染后写入 `ActionContext`，再由 `_AgentAdapter` 传给 `SubagentConfig`。`SubagentExecutor` 仅在策略存在时挂载文件访问中间件，因此旧工作流不声明策略时保持原行为。

中间件约束如下：

- 读工具：`read_file`、`ls`、`glob`、`grep`、`view_image`；
- 写工具：`write_file`、`str_replace`；
- 路径必须为绝对路径，拒绝 `..`、反斜杠穿越和相似前缀绕过；
- 不修改全局 `validate_local_tool_path()`，节点策略与既有 sandbox 校验形成两层边界。

九个归零 Agent 节点均声明最小文件集合。`deductive_tree` 只读 `/mnt/skills/custom/fault-zeroing`，只写自己的 `fault_tree_structure.json`，不具备上传目录或 `artifacts/evidence` 的读取权限。

### 8.3 生产 Worker 单任务边界

`backend/app/workflow_worker.py` 将单个已领取任务的执行抽取为 `execute_workflow_task()`。生产 `run_worker()` 仍使用相同入口；集成覆盖可在不复制业务闭包的前提下组合真实 `WorkflowV2Store`、`WorkflowWorker`、编译器、Checkpointer 和持久事件链。Adapter 运行时使用 run id 作为 sandbox thread id，并绑定工作流创建者的用户上下文，使 `/mnt/user-data/...` 映射落在对应用户、对应运行目录。
