# 归零智能体建设 — 对抗式审查评估报告

> 审查日期: 2026-07-06
> 审查范围: 归零智能体建设三份核心文档（分析方案、可行性与实现路径、进展汇报）
> 审查方式: 基于三份文档的交叉对比与对抗式审查

---

## 一、审查概述

本报告以对抗式审查视角，对归零智能体建设的三份核心文档进行系统性审查，旨在发现文档中的问题、矛盾、漏洞或不合理之处，评估需求合理性、内部逻辑一致性、实现方案有效性和计划必要性，并提出具体改进建议。

**审查文档清单：**

| 文档编号 | 文档名称 | 文档类型 |
|---------|---------|---------|
| D1 | 基于 deer-flow 框架开发归零排故智能体的分析方案 | 需求分析与任务拆解 |
| D2 | 归零排故智能体可行性与实现路径（代码探索版） | 技术可行性与实现路径 |
| D3 | 归零智能体建设进展汇报 | 建设进展与未来规划 |

## 二、需求合理性评估

### 2.1 需求完整性评估

**问题 2.1.1: 需求粒度不一致**
- **严重度**: 中
- **描述**: D1 文档将需求拆解为 10 个需求点（工作台入口、问题单结构化、智能体流程等），但 D2 文档将需求聚焦于 4 项核心技术能力（Skill 配置、文件系统访问、工具调用、报告生成）。两者粒度差异较大，D1 的需求更偏业务视角，D2 的需求更偏技术视角，但缺乏从业务需求到技术需求的映射关系。
- **影响**: 可能导致业务需求与技术实现脱节，业务团队和技术团队对需求的理解产生偏差。
- **改进建议**: 建立需求映射矩阵，将 D1 的业务需求逐条映射到 D2 的技术能力，确保每项业务需求都有对应的技术实现方案。

**问题 2.1.2: 需求优先级缺乏依据**
- **严重度**: 中
- **描述**: D1 文档将需求分为三个阶段（阶段一：归零智能体 PoC、阶段二：业务 MVP、阶段三：生产级增强），但未说明阶段划分的依据。D2 文档将需求分为 P0（PoC 必做）、P1（MVP 必做）、P2（生产增强），同样缺乏优先级排序的明确标准。
- **影响**: 可能导致资源分配不合理，关键需求被延迟，非关键需求被过度投入。
- **改进建议**: 引入需求优先级评估模型（如 MoSCoW 方法），明确每项需求的业务价值、技术复杂度和依赖关系，为优先级排序提供量化依据。

**问题 2.1.3: 缺乏非功能性需求定义**
- **严重度**: 高
- **描述**: 三份文档均聚焦于功能性需求（智能体流程、子智能体、报告生成），但对非功能性需求（性能、可靠性、安全性、可维护性）缺乏明确要求。例如：
  - 智能体分析的响应时间要求（单次分析需多长时间完成？）
  - 系统并发能力（同时支持多少个归零任务？）
  - 数据安全要求（归零数据的保密等级、访问控制粒度）
  - 系统可用性要求（SLA 目标、故障恢复时间）
- **影响**: 可能导致系统在生产环境中无法满足性能和安全要求，影响用户体验和数据安全。
- **改进建议**: 补充非功能性需求定义，包括性能指标、安全要求、可用性目标和可维护性要求。

### 2.2 需求合理性评估

**问题 2.2.1: 模型选型缺乏量化依据**
- **严重度**: 中
- **描述**: D3 文档提到"当前配置使用 Codex GPT-5.4 作为主模型"，但未说明选择 GPT-5.4 的具体依据。D2 文档提到"模型选型原则：优先选择长上下文窗口（100K+ tokens）、推理能力强、tool use 能力稳定的模型"，但未提供对 GPT-5.4 在这些维度上的具体评估数据。
- **影响**: 可能导致模型选型主观化，无法在后续评估中客观比较不同模型的性能差异。
- **改进建议**: 建立模型评估基准，提供 GPT-5.4 在归零分析场景中的具体性能数据（如准确率、响应时间、token 消耗），为后续模型升级提供对比基准。

**问题 2.2.2: 子智能体划分合理性存疑**
- **严重度**: 中
- **描述**: D1 和 D2 文档设计了 5 类子智能体（evidence-reader、fault-tree-builder、probability-assessor、root-cause-analyst、report-reviewer），但未说明划分依据。例如：
  - 为什么 evidence-reader 和 fault-tree-builder 是分离的，而不是合并为一个"分析子智能体"？
  - root-cause-analyst 与 probability-assessor 的职责边界是否清晰？根因归因是否需要底事件概率作为输入？
- **影响**: 可能导致子智能体职责重叠或遗漏，增加编排复杂度，降低系统可维护性。
- **改进建议**: 基于归零分析流程的任务依赖关系，重新评估子智能体划分的合理性，确保每个子智能体的职责边界清晰且无重叠。

**问题 2.2.3: 证据等级体系缺乏验证**
- **严重度**: 中
- **描述**: D1 文档定义了 A/B/C/D 四级证据分类标准，但未说明该分级体系的来源和验证情况。例如：
  - 该分级体系是否参考了航天/航空领域的归零标准？
  - 是否在历史案例中验证过分级的合理性？
  - 不同领域的归零分析是否需要不同的分级标准？
- **影响**: 可能导致证据分级主观化，影响智能体分析结论的可靠性。
- **改进建议**: 补充证据等级体系的来源说明，并在历史案例中验证分级的合理性，必要时根据领域特点进行调整。

## 三、内部逻辑矛盾与冲突评估

### 3.1 文档间矛盾

**问题 3.1.1: 阶段划分不一致**
- **严重度**: 高
- **描述**: D1 文档将建设分为三个阶段（阶段一：归零智能体 PoC、阶段二：业务 MVP、阶段三：生产级增强），D2 文档也分为三个阶段（阶段一：配置型 PoC、阶段二：结构化业务层、阶段三：生产级集成），但两者的阶段划分标准和交付内容存在差异：
  - D1 阶段一强调"通用 Agent 与 Skill 模板"，D2 阶段一强调"不改框架核心"
  - D1 阶段二包含"知识检索与长期记忆"，D2 阶段二包含"历史案例检索的最小实现"
  - D3 文档的短期/中期/长期计划与 D1、D2 的阶段划分也不完全对应
- **影响**: 可能导致团队对建设目标和交付标准产生误解，影响项目管理的统一性。
- **改进建议**: 统一三份文档的阶段划分标准，明确每个阶段的交付物、验收标准和资源需求，确保团队对建设目标有一致理解。

**问题 3.1.2: 资源需求描述不一致**
- **严重度**: 中
- **描述**: D1 文档的资源需求表（3.4 节）提到"短期：领域专家 2-3 人月"，D3 文档的人力需求表（3.4 节）提到"AI 工程师 2-3 人"，两者在角色定义和资源粒度上存在差异。D1 使用"人月"作为单位，D3 使用"人数"作为单位，缺乏统一的资源计量标准。
- **影响**: 可能导致资源分配困难，无法准确评估项目成本和工期。
- **改进建议**: 统一资源需求的描述格式，明确每个阶段的角色、人数、工作时间和技能要求，提供详细的资源分配计划。

**问题 3.1.3: 验收标准不统一**
- **严重度**: 中
- **描述**: D1 文档的交付标准描述较为模糊（如"完成通用 Agent 模板、SOUL.md 配置规范"），D2 文档的验收标准较为具体（如"给定一组样例材料，可以完成故障现象 → 故障树 → 底事件评估 → 归因结论 → 归零报告的闭环"），D3 文档的预期效果更偏业务价值（如"将传统数天的人工归零分析缩短至小时级"）。三者的验收标准粒度和类型不统一。
- **影响**: 可能导致团队对"完成"的定义产生分歧，影响项目验收的客观性。
- **改进建议**: 建立统一的验收标准体系，区分技术验收、功能验收和业务验收，明确每项标准的具体验收方法和通过条件。

### 3.2 文档内矛盾

**问题 3.2.1: D2 文档内阶段目标与工作内容不完全匹配**
- **严重度**: 低
- **描述**: D2 文档阶段一的目标是"不改框架核心，验证完整归零闭环"，但工作内容中包含"配置 3-5 个 custom subagents"，而 custom subagents 的配置本身可能涉及框架配置文件的修改，与"不改框架核心"的目标存在一定张力。
- **影响**: 影响较小，但可能在执行过程中引发对"框架核心"边界的争议。
- **改进建议**: 明确"框架核心"的定义边界，区分配置修改和代码修改，确保阶段目标与工作内容一致。

**问题 3.2.2: D3 文档内知识库方案前后不一致**
- **严重度**: 中
- **描述**: D3 文档 1.4.1 节明确表示"当前采用文件型知识源，不建设正式 RAG 或向量知识库"，但 3.2 节中期计划中提到"从文件型知识源升级为向量知识库（支持 RAGFlow/Qdrant/Milvus）"。虽然这是不同阶段的方案，但文档未说明从文件型到向量库的迁移条件和时机。
- **影响**: 可能导致团队对知识库建设的时机产生困惑，影响技术选型的一致性。
- **改进建议**: 明确知识库升级的触发条件（如数据量、检索性能需求），提供从文件型到向量库的迁移路径和评估标准。

## 四、实现方案有效性评估

### 4.1 技术方案可行性

**问题 4.1.1: 知识库能力缺口未充分评估**
- **严重度**: 高
- **描述**: D2 文档明确指出"知识库不是现成能力：当前只有 Memory、Skill、Uploads 和 MCP 接入通道，没有内置 RAG/向量库"，但三份文档均未评估这一缺口对归零分析质量的具体影响。例如：
  - 缺乏知识库时，智能体如何处理需要参考历史案例的归零分析？
  - 文件型知识源在处理大规模资料时的性能瓶颈如何？
  - 后续迁移到向量库时，现有文件型知识源的数据如何迁移？
- **影响**: 可能导致 PoC 阶段无法验证需要历史知识参考的复杂归零场景，影响分析结论的可靠性。
- **改进建议**: 评估知识库缺口对不同归零场景的影响程度，制定临时替代方案（如 MCP 接入外部知识库），并规划数据迁移路径。

**问题 4.1.2: 故障树结构化约束不足**
- **严重度**: 高
- **描述**: D2 文档指出"故障树需要结构化约束：如果只依赖 prompt，复杂故障树容易出现字段漂移和前后矛盾"，但 PoC 阶段的解决方案仅提供了 JSON Schema 模板，未说明如何确保智能体生成的故障树符合 Schema 约束。例如：
  - 智能体生成的故障树 JSON 如何自动校验？
  - 校验失败时的降级策略是什么？
  - 故障树的版本管理如何实现？
- **影响**: 可能导致故障树输出格式不一致，影响后续的故障树可视化和分析过程追溯。
- **改进建议**: 在 PoC 阶段增加故障树 JSON 的自动校验工具，制定校验失败时的降级策略，并规划故障树的版本管理方案。

**问题 4.1.3: 概率评估的领域规则缺失**
- **严重度**: 高
- **描述**: D2 文档指出"概率评估需要领域规则：底事件概率不能只靠模型猜测，需要明确证据等级、历史频次、试验结果和专家规则"，但三份文档均未提供具体的领域规则定义。例如：
  - 底事件概率的评估标准是什么？（如：A 级证据支撑的底事件概率如何计算？）
  - 无历史数据时的默认概率值是什么？
  - 不同故障类型的概率评估是否有差异？
- **影响**: 可能导致概率评估主观化，影响根因归因的可信度。
- **改进建议**: 与领域专家合作，制定底事件概率评估的领域规则，提供历史数据参考和默认概率值，建立概率评估的校准机制。

### 4.2 方案完整性评估

**问题 4.2.1: 错误处理机制不完善**
- **严重度**: 中
- **描述**: D2 文档定义了 5 类错误处理场景（缺少关键输入、找不到文件、证据冲突、概率依据不足、子智能体失败），但未说明这些错误场景在实际执行中的处理优先级和恢复策略。例如：
  - 多个子智能体同时失败时，主智能体如何降级？
  - 证据冲突时，是否需要人工介入？
  - 概率依据不足时，是否影响后续根因归因？
- **影响**: 可能导致智能体在复杂错误场景下无法正常执行，影响分析流程的稳定性。
- **改进建议**: 补充错误处理的优先级和恢复策略，制定子智能体失败时的降级方案，明确证据冲突时的人工介入条件。

**问题 4.2.2: 评测体系缺乏具体指标**
- **严重度**: 中
- **描述**: D3 文档提到"建立覆盖流程完整率、证据引用率、结论准确率、报告合规率的指标看板"，但未定义这些指标的具体计算方法和阈值。例如：
  - 流程完整率的计算公式是什么？（如：8 个阶段全部完成的比例？）
  - 证据引用率的阈值是多少？（如：90% 的结论需要有证据引用？）
  - 结论准确率如何验证？（如：与专家结论的一致率？）
- **影响**: 可能导致评测体系无法量化执行，影响智能体分析质量的持续监控和优化。
- **改进建议**: 定义每个指标的具体计算方法、阈值和验证方式，提供评测工具和基准数据，建立持续监控机制。

**问题 4.2.3: 安全与审计方案缺乏细节**
- **严重度**: 中
- **描述**: D1 和 D3 文档提到"高风险控制：命令执行、外部系统写入、Skill 自演化默认关闭，按审批启用"和"工具调用审计、敏感信息脱敏、模型调用留痕"，但未提供具体的实现方案。例如：
  - 高风险操作的审批流程是什么？
  - 工具调用审计的日志格式和存储方式是什么？
  - 敏感信息脱敏的规则是什么？
- **影响**: 可能导致安全与审计功能无法按时交付，影响系统的安全合规性。
- **改进建议**: 补充安全与审计的详细设计方案，明确审批流程、日志格式、脱敏规则和存储方案，确保满足企业安全要求。

## 五、计划必要性与精炼度评估

### 5.1 计划必要性评估

**问题 5.1.1: 阶段二"业务 MVP"范围过大**
- **严重度**: 中
- **描述**: D1 文档阶段二包含 9 个任务包（通用配置入口、任务实例与流程配置、产物模板与引用关系、知识检索与长期记忆、企业工具接入、权限与基础审计、多场景评测集等），涵盖前端、后端、平台集成、测试等多个领域，可能导致阶段二的交付周期过长、资源需求过大。
- **影响**: 可能导致阶段二的交付风险增加，影响项目整体进度。
- **改进建议**: 将阶段二进一步拆分为多个子阶段，按优先级和依赖关系分批交付，降低单次交付的风险。

**问题 5.1.2: 阶段三"生产级增强"缺乏明确边界**
- **严重度**: 中
- **描述**: D1 和 D3 文档的阶段三包含企业系统集成、审批流程、安全审计、评测体系等多个大型任务，但未明确阶段三的完成标准和交付边界。例如：
  - 接入 PLM、缺陷系统、测试平台等企业系统的优先级是什么？
  - 审批流程需要支持多少种审批模式？
  - 安全审计需要满足哪些合规要求？
- **影响**: 可能导致阶段三的范围蔓延，无法按时交付。
- **改进建议**: 明确阶段三的完成标准和交付边界，按优先级和业务价值排序，制定分批交付计划。

### 5.2 计划精炼度评估

**问题 5.2.1: 任务分解粒度不一致**
- **严重度**: 低
- **描述**: D1 文档的任务分解粒度较粗（如"通用 Agent 与 Skill 模板"），D2 文档的任务分解粒度较细（如"创建 fault-zeroing custom agent"、"编写 fault-zeroing skill"），D3 文档的任务分解粒度介于两者之间（如"PoC 验证闭环"）。三者的任务分解粒度不统一。
- **影响**: 影响较小，但可能导致任务分配和进度跟踪的粒度不一致。
- **改进建议**: 建立统一的任务分解标准，按 WBS（工作分解结构）方法将任务分解到可执行的工作包级别。

**问题 5.2.2: 任务依赖关系不明确**
- **严重度**: 中
- **描述**: 三份文档均未明确任务之间的依赖关系。例如：
  - "知识库构建"任务是否依赖"企业工具接入"任务？
  - "审批流程"任务是否依赖"权限与基础审计"任务？
  - 子智能体配置是否依赖 Skill 开发？
- **影响**: 可能导致任务执行顺序不合理，影响项目进度和资源利用效率。
- **改进建议**: 建立任务依赖关系图，明确任务之间的前置关系和并行关系，优化任务执行顺序。

## 六、其他问题

**问题 6.1: 文档版本管理缺失**
- **严重度**: 低
- **描述**: 三份文档均未标注版本号，无法追踪文档的变更历史。D1 文档标题为"分析方案"，D2 文档标题包含"代码探索版"，但未说明与正式版本的关系。
- **影响**: 可能导致团队使用不同版本的文档，影响信息一致性。
- **改进建议**: 为每份文档添加版本号和变更日志，建立文档版本管理机制。

**问题 6.2: 术语定义不统一**
- **严重度**: 低
- **描述**: 三份文档中部分术语的使用不统一。例如：
  - D1 使用"归零排故"，D3 使用"归零分析"，两者是否为同一概念？
  - D1 使用"问题单"，D2 使用"问题描述"，两者是否为同一概念？
  - D1 使用"证据台账"，D3 使用"证据台账"，但 D2 使用"证据引用"，三者是否为同一概念？
- **影响**: 可能导致团队对术语的理解产生偏差，影响沟通效率。
- **改进建议**: 建立术语表，统一关键术语的定义和使用，确保文档间术语一致。

**问题 6.3: 依赖外部资源的风险未充分评估**
- **严重度**: 中
- **描述**: D1 和 D3 文档提到需要"领域专家投入"、"历史归零案例数据"、"企业系统 API 接口"等外部资源，但未评估这些资源的获取风险和备选方案。例如：
  - 领域专家无法按时投入时，如何调整计划？
  - 历史案例数据获取困难时，是否有替代方案？
  - 企业系统 API 接口不兼容时，如何应对？
- **影响**: 可能导致项目因外部资源不足而延期或无法交付。
- **改进建议**: 评估外部资源的获取风险，制定备选方案和应急预案，降低外部依赖对项目的影响。

### 7.4 总体结论

归零智能体建设的三份核心文档在需求分析、技术方案和建设规划方面提供了较为完整的框架，但在以下方面存在需要改进的空间：

1. **文档一致性**: 三份文档在阶段划分、资源需求、验收标准等方面存在矛盾，需要统一。
2. **需求完整性**: 缺乏非功能性需求定义，需求优先级缺乏量化依据。
3. **技术可行性**: 知识库、故障树约束、概率评估等领域规则存在关键缺口，需要补充。
4. **计划可执行性**: 阶段二范围过大、任务依赖关系不明确，需要优化。

建议在启动正式开发前，先完成上述 P0 级改进项，确保团队对建设目标、技术方案和执行计划有一致理解，降低项目风险。
